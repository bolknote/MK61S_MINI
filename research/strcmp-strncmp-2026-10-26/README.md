# strcmp / strncmp: подготовка M4 и M0+

Подготовлены кандидаты и проверки для прошивки, runtime и автономных APP.
M4 измерен на Classic, результаты приняты и закрыты. Выбранный байтовый
`strcmp` включён для обычных GNU Cortex-M4 native/SDK путей: 20 байт,
−7,96% времени в прошивке и −2,22% в APP. `strncmp` остаётся исходным.
M0+ пока подготовлен и проверен только на HOST; аппаратного победителя нет.
Работа сделана в отдельном worktree от принятого strlen-коммита
`6e814dd7bb8b12c8700bbb9ad3817a20ceb8800e`. Основной checkout и принятый
worktree strlen во время измерений не менялись. После прямого поручения
пользователя изменения готовятся к слиянию только в собственном узком scope.

`MK61_STRCMP_VARIANT` и `MK61_STRNCMP_VARIANT` выбираются независимо.
Оба исследовательских селектора по умолчанию равны **0**. Явный
`-DMK61_STRCMP_VARIANT=0` в эксперименте сохраняет старое контрольное тело. Эти селекторы действуют только в `fixture-root/`, где сохранён исходный
снимок подготовки на6e. Обычный GNU M4 получает выбранный 20-байтный
`strcmp` из production `memory_string_compare_arm.h`; M0+ сохраняет
прежние defaults. Экспериментальные варианты в production TU не включаются. Для M0+
`MK61_STRING_COMPARE_PICO_SRAM` дополнительно помещает выбранные функции
в секции `.time_critical`. Полная прошивка Pico с ними ещё не проверялась.

| ID | Вариант | M4 | M0+ |
|---|---|---|---|
| 1 | Побайтовый цикл с одним чтением каждого байта | да | да |
| 2 | Развёрнутый цикл по четыре байта | да | да |
| 3 | Выровненные слова по 32 бита, битовая проверка NUL | да | да |
| 4 | Два последовательных 32-битных шага | да | да |
| 5 | 32-битный шаг, DSP `UQSUB8` для поиска нулевого байта | да | — |
| 6 | Два последовательных шага с `UQSUB8` | да | — |

Word-варианты читают только выровненные слова. Они могут прочитать до трёх
байтов после NUL внутри содержащего его слова; до начала входа и за предел
`strncmp(..., n)` не читают. При разных классах выравнивания используется
побайтовый путь. Следующее слово читается после проверки предыдущего.
Эти функции предназначены для обычных строк SRAM/Flash.

Таблица runtime сохраняет 26 слотов; `strncmp` занимает слот 19. Отдельного
слота `strcmp` нет. Экспериментальный
`MK61_APP_STRCMP_USE_STRNCMP_RUNTIME` в shared APP вызывает существующий
`strncmp(left, right, SIZE_MAX)`. Локальный strcmp и этот мост проверяются
раздельно. На окончательном M4 мост оказался на 30,08% медленнее local20B
и оставлен только явным исследовательским opt-in. В shared APP выбор `MK61_STRNCMP_VARIANT` не создаёт локальную
функцию вместо runtime-перехода.

У текущего freestanding SDK нет собственного `strncmp` при варианте 0:
обычный APP без дополнительной библиотеки с таким вызовом не линкуется.
Поэтому эталонный standalone APP явно подключает newlib (`-lc`), а варианты
1–6 предоставляют локальное тело. Остальные настройки SDK не менялись.

В [RESULTS-HOST.json](RESULTS-HOST.json) сохранены счётчики, размеры тел,
пути и SHA-256 подробных результатов. Проверено **2 003 744 сравнения**:

- 410 464 вызова ARM-кода во Flash/SRAM и через реальные runtime-переходы;
- 1 580 320 сравнений в 26 настоящих упакованных APP;
- 12 960 вызовов публичных точек входа из настоящих source-файлов прошивки.

Все APP прошли штатные проверку заголовка, ZX0/BCJ, CRC и релокации по трём
адресам, затем запуск через SDK entry, включая повторный запуск из кеша.
Получено 78 успешных инициализаций, 166 запусков и 48 отрицательных проверок
(отсутствующий runtime-слот и заведомо неверная функция сравнения).
Самый большой тестовый APP: 1436 байт файла / 2664 байта RAM; это размеры
данного теста, а не доказательство бюджета всех системных APP.

Байтовый оракул, unsigned-порядок, NUL, нулевой/ограниченный/MAX-предел,
нетерминированные ограниченные буферы, все 16 сочетаний выравнивания,
границы чтения/записи, неизменность входа и AAPCS проверены в Unicorn 2.1.4.
Модель Cortex-M0 проверяет ISA ARMv6-M для M0+; скорость, Flash wait states,
кеш и прерывания реальных плат не моделируются. Только query/capabilities
внешнего API являются заглушками; SDK startup, bind, trampolines и тела
сравнения исполняются как ARM-код. Эталон newlib относится к ARM GCC 14.2.1
этой сборки, а не к ещё не привязанной будущей прошивке Pico.

Для эталонного M4 newlib strcmp разрешено его фактическое выравнивание вниз
до восьми байтов и чтение содержащей NUL восьмёрки. Более строгий контракт
собственных кандидатов проверяется отдельно. Повторная сборка финальных
источников дала шесть ELF, байт в байт совпадающих с исполненными тестами.
В исходной HOST-квалификации шесть прежних default-тел совпали с исходной базой;
Pico-вариант 0 не экспортирует новых функций сравнения.

`bench.c` — ядро будущего аппаратного измерения. Оно принимает поставленные
снаружи функции, входы и квалифицированный таймер, проверяет знак результата
до/после каждой серии, сохраняет семь сырых длительностей полного цикла
косвенных вызовов и останавливается при первой обнаруженной ошибке.
Вычитания пустого вызова нет. Проверены фактическое число вызовов,
переполнение счётчика, n=0, неверный оракул/функция и остановившийся таймер.
ARM-объекты обоих ядер содержат реальные косвенные вызовы и не маскируют IRQ.

`prepare.py` создаёт независимый от конкретной прошивки план: 288 случаев
strcmp и 516 strncmp, включая SRAM/SRAM, SRAM/Flash и Flash/Flash. Это
HOST-подготовка, а не готовый допуск к устройству: фактические target, clock,
carrier, таймер, число повторов и внешний сценарий возврата должны быть
привязаны после подключения. Полные firmware-сборки и окончательный бюджет
Flash/RAM проверяются перед внедрением выбранных по железу вариантов.

Для воспроизведения нужен Python с Unicorn 2.1.4 и каталог ARM GCC 14.2.1
в `SC_TC`. Запускать из корня этого checkout с новыми выходными каталогами:

```sh
python3 -B tests/string_compare_arm_self_test.py --toolchain-bin "$SC_TC" --output-dir /tmp/sc-core
python3 -B tests/string_compare_app_self_test.py --toolchain-bin "$SC_TC" --core-dir /tmp/sc-core --output-dir /tmp/sc-apps
python3 -B research/strcmp-strncmp-2026-10-26/prepare.py --toolchain-bin "$SC_TC" --output-dir /tmp/sc-plan
python3 -B research/strcmp-strncmp-2026-10-26/verify_defaults.py --toolchain-bin "$SC_TC" --final-core-dir /tmp/sc-core-rebuilt --output-dir /tmp/sc-defaults
```

Ни один из этих скриптов не открывает serial/USB и не загружает прошивки.
Для аппаратного этапа Classic требуется свежая identity/baseline и отдельный
конкретный допуск координатора; старые порты/образы не считаются текущими.
Внешний сценарий Pico и RTC-helper остаются у NativePico. Ранее согласованное
окно strlen M0+ сохраняется перед новой кампанией strcmp/strncmp.

Финальные результаты M4 сохранены в [RESULTS-M4.json](RESULTS-M4.json) и
[RESULTS-M4-FINAL.md](RESULTS-M4-FINAL.md). В `evidence/` находятся оба
независимо принятых анализа и полные сырые длительности в deterministic gzip:
17688 групп первого сравнения и 2592 окончательного статического контроля.
Пользовательские файлы, typed state и дампы исходной Flash в Git не включаются.
`RESULTS-HOST.json` сохраняет исторический результат исходной подготовки на6e;
новое включение M4 по умолчанию проверяется отдельно в `verify_defaults.py`.
Результат приёмки аппаратных сценариев не заменяет CI объединённого shipping commit.

`fixture-root/` содержит исходные comparison TU и их локальные
include-зависимости из подготовленного checkpoint1fdc92e67 на6e. Единственная
поправка снимка — bridge требует значение1; явно заданный0 его не включает.
Ранее квалифицированное тело при1 не меняется. Тестовый
compiler-adapter подставляет этот снимок; production `code/`, SDK и Pico
не содержат селекторов1–6, исследовательского моста и SRAM hook.
Нормальные source defaults проверяются на настоящих production TU отдельно.

Проверка `verify_defaults.py` без `--tested-core-dir` использует сохранённые
ожидаемые SHA шести квалифицированных ELF из `evidence/host-core-build.json`;
сами ELF пересобираются из fixture source. Git-объект6e для запуска не нужен.
Исторические абсолютные пути в RESULT-файлах — происхождение исходного
измерения, а не требования к новому checkout.
