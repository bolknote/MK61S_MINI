# RP2040 / Cortex-M0+: выбор memset по аппаратным замерам

21 октября 2026. Для автономных APP выбран локальный ARMv6-M `memset`:
154 байта кода, выравнивание начала, цикл `STMIA` по 64 байта, точный хвост
и отдельный путь 0–7 байт. Он не требует адресов BootROM, разрешения таблицы
функций или таблицы runtime. Тело прежней функции занимало 22 байта; цена
выбранного ускорения — 132 байта до упаковки APP.

В SDK это [memory.c](../../sdk/portable/memory.c) и
[memset_m0.inc](../../sdk/portable/memset_m0.inc). ARM GCC использует этот
путь при `__ARM_ARCH_6M__`, включая Pico APP с прежним экранным ABI. M4 и
прочие цели сохраняют прежнюю ветку. Уже установленные APP нужно пересобрать.

Для `--shared-runtime` также сокращён ISO C переход:
`ldr r3 / ldr r3 / ldr r3 / bx r3`, без сохранения `r4`. Вызовы EABI,
использующие все четыре регистра аргументов, сохраняют прежний переход.
На коротких операциях экономится примерно **40 нс** при 125 МГц; один ISO C
переход вместе с литералом занимает 12 вместо 20 байт.

Resident по-прежнему использует Pico SDK → ROM. Здесь измерено исполнение
локальных функций из SRAM, где действительно работает обычный APP. Эти
числа не доказывают преимущество локальной функции из XIP Flash resident;
прошивка устройства в этой работе не менялась.

## Результат

Время в микросекундах после вычитания пустого вызова. Для каждого сочетания
взята медиана семи серий, затем медиана трёх прогонов. В таблице дополнительно
взята медиана по смещениям 0–3 и значениям заполнения `0`/`0xA5`.

| Размер | Прежний код APP | ROM напрямую | ROM через сохранённый указатель в memset | Старый runtime | Новый runtime | Новый локальный SDK |
|---:|---:|---:|---:|---:|---:|---:|
| 4 | 0,312 | 0,152 | 0,200 | 0,304 | 0,264 | **0,160** |
| 16 | 0,888 | 0,340 | 0,388 | 0,492 | 0,452 | **0,320** |
| 64 | 3,192 | 0,576 | 0,624 | 0,728 | 0,688 | **0,576** |
| 256 | 12,408 | 1,344 | 1,392 | 1,497 | 1,455 | **1,136** |
| 4096 | 196,719 | 16,938 | 16,781 | 17,000 | 17,000 | **12,172** |

На 4 КиБ локальный код примерно в **16,2 раза** быстрее прежнего побайтового
и сокращает время против ROM примерно на **27–28%**. В каждом из 320
проверенных сочетаний он быстрее ROM с обычной обёрткой `memset`, которая
загружает заранее сохранённый указатель. Поиск ROM-функции не входит ни в
один замер.

Это не утверждение о победе во всех возможных условиях. Прямой вызов ROM
через уже находящийся в регистре указатель на 3–7 байтах быстрее выбранного
кода примерно на 8 нс. Обычная ROM-обёртка добавляет около 48 нс, поэтому
такой путь для самостоятельного `memset` проигрывает. Первый локальный
кандидат `own64` на 0/1 байте быстрее выбранного на 16 нс, но проигрывает
на большинстве остальных размеров, в том числе больших блоках. Выбран
вариант с быстрыми общими короткими и длинными путями. Копирование точного
120-байтного тела ROM в SRAM само по себе не даёт заметного ускорения.

На длинных сериях небольшие разности между ROM и его обёртками перекрываются
фоновыми прерываниями и их фазой относительно измерения: это видно в сырых
сериях. Например, равные округлённые 17 мкс для двух runtime-путей на 4 КиБ
не отменяют достоверную разность около 40 нс на коротких блоках. Основной
выигрыш локального цикла намного больше этого разброса.

## Устройство и методика

- PicoCalc + Pico H, RP2040, UID `E6657CD423721C35`, 125 МГц в режиме RUN.
- Resident `BUILD=5F1E85DF`, CRC32 `3C044212`, 746544 байта; сверены manifest,
  адрес runtime-функции и ELF установленной release-сборки.
- BootROM v3, `MS=0x26B9`, resident `__wrap_memset=0x1008EA7D`.
  [Дамп 16 КиБ](capture/bootrom.bin) ранее дважды считан с того же устройства;
  SHA-256 `ef07d54bdd259c7858483606118a3c704976801823c38ac5a2fcdffacd2d83fe`.
  Каждый запуск APP сверяет скопированное тело MS с этими байтами.
- [Дизассемблирование ROM memset](capture/memset.disasm.txt): выравнивание,
  цикл по 16 байт, хвост 8/4/2/1, отдельная последовательность для 0–7 байт.
  Публичный код функции `MS` разрешается через ROM lookup до измерений.
- APP исполняется в SRAM; прямой resident-путь проходит настоящую обёртку
  из Flash, затем ROM. Таймер `TIMERAWL` даёт микросекунды. Частота, PLL,
  IRQ и конфигурация периферии не изменяются бенчмарком.
- 40 размеров: 0–17, 23, 24, 31, 32, 33, 47, 48, 63, 64, 65, 95, 96,
  127, 128, 129, 255, 256, 257, 511, 512, 1024, 4096. Четыре смещения и
  два значения дают 320 сочетаний. Три прогона дают 960 строк измерений.
- Семь серий с вращением порядка девяти кандидатов, один контрольный пустой
  вызов той же сигнатуры на серию. Количество вызовов в серии:
  `max(32, 131072 / (size + 16))`. После открытия APP — секунда прогрева.
  Обслуживание USB/интерфейса выполняется между измерениями; IRQ включены.
- Сравниваются прежний байтовый код, прямой ROM, resident entry, прежний
  и новый runtime-переходы, сохранённый ROM-указатель, тело ROM в SRAM,
  выбранный SDK и первый локальный цикл по 64 байта.
- Отдельно обычным SDK собран и запущен APP с `--shared-runtime`.
  Его настоящий `memset` совпадает по инструкциям с измеренным новым
  переходом. Медианная разность на размерах до 256 байт — 0 нс.

Для справки: [официальное описание pico_mem_ops](https://www.raspberrypi.com/documentation/pico-sdk/runtime.html#pico_mem_ops).
В локальном SDK 2.2.0 маршрутизацию задаёт
`src/rp2_common/pico_mem_ops/mem_ops_aeabi.S`. Прямые ROM, resident и runtime
в таблице — разные измеренные пути, а не оценка из эмулятора.

## Корректность и сохранность

- Окончательный автономный APP: **234441** аппаратная проверка без ошибки.
  Проверяются возвращаемый указатель, все байты результата и охранные зоны;
  полный набор включает размеры 0–257, смещения 0–7, значения 0, 1,
  `0x1234`, `-1`, а также крупные границы до 8192 байт и `NULL,0`.
- Отдельный shared APP: **75339** аппаратных проверок без ошибки.
- [ARMv6-M тест](../../tests/system_memset_m0_arm_self_test.py): по 10353
  случая с LTO и без LTO, включая 65536 байт, случайные размеры/значения,
  запрет невыровненных записей, точные границы и сохранение `r4–r11`/SP.
- [Тест runtime](../../tests/portable_runtime_trampoline_arm_self_test.py):
  все 26 слотов на M0+ и M4, аргументы до четырёх регистров, результаты
  `r0–r3`, сохранение регистров, SP и LR.
- Собраны native Pico, legacy Pico и STM32 APP. Старый байтовый кандидат
  побайтно совпадает с прежним SDK; выбранный `memset` побайтно совпадает
  с квалифицированным кандидатом, SHA-256 тела:
  `2785002841720b464a5f94e9b9857ccf86edabd6b01ec881ea98fb2d735ace11`.
- Каждый основной HIL-сеанс сравнил `reg`, `stk`, `hout`, `pwd` и список
  корня до/после, удалил только свою временную директорию и закрыл viewer.
  Итоговые статусы подтверждают валидный CRC, отсутствие crash и активного
  APP. Сброса, прошивки, изменения пользовательских файлов и настроек нет.
  Первому исследовательскому прогону потребовалось отдельно закрыть экран
  завершения APP; это отмечено в его отчёте. Окончательные сеансы очищены
  автоматически и завершены с `PASS`.

## Артефакты и повторение

В `evidence/{initial,fast,standalone,shared}` лежат точные APP/ELF, размеры,
сырые измерения в `measurements.json.gz` и результаты проверок. Основная
сводка — [standalone/summary.json](evidence/standalone/summary.json).
Сырые отчёты содержат все семь времён каждой серии; терминальные логи с
пользовательскими регистрами в репозиторий не включены.

Пример повторения из корня репозитория (`TC` — каталог ARM GCC):

```sh
python3 research/rp2040-memset-2026-10-21/build.py --arm-toolchain-bin "$TC" --output .build/memset-repeat --directory /MK61S-MEMSET-REPEAT --variant standalone
python3 research/rp2040-memset-2026-10-21/run.py --port /dev/cu.usbmodem21301 --uid E6657CD423721C35 --app .build/memset-repeat/app/MEMBENCH.APP --directory /MK61S-MEMSET-REPEAT --output .build/memset-repeat/hil --candidate sdk --runs 3
python3 research/rp2040-memset-2026-10-21/analyze.py .build/memset-repeat/hil/result.json --output .build/memset-repeat/summary.json
```

Устройство должно быть свободно и находиться в калькуляторе, без выполняемой
программы, dirty editor или USB disk. HIL соблюдает эксклюзивную блокировку
CDC. Для shared-проверки используется `--variant shared`; для первых
кандидатов — `initial`/`fast` и соответственно `--candidate own16`/`own_fast`.
`build.py` сохраняет каталог и SHA-256 APP в `benchmark.json`.

Для тестов машинного кода нужен Python с Unicorn 2.1.4. Они проверяют
корректность исполнения, но их счётчик инструкций не используется как время:

```sh
python tests/system_memset_m0_arm_self_test.py --arm-toolchain-bin "$TC"
python tests/portable_runtime_trampoline_arm_self_test.py --arm-toolchain-bin "$TC"
```
