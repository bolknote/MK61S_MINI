# memcpy: аппаратный выбор для M4, M0+ и автономных APP

21 октября 2026. Приоритет — скорость. Выбраны собственные реализации:
[M4](../../code/memcpy_m4.inc) и [M0+](../../code/memcpy_m0.inc), подключённые
через общий [memory_copy_arm.h](../../code/memory_copy_arm.h) к resident
и SDK. Автономный APP содержит собственное тело; `--shared-runtime`
использует обычный 12-байтный переход SDK к функции resident.

M4: 292 байта кода во Flash resident или SRAM автономного APP. Короткие
копии используют начало и конец диапазона; большие — выровненное чтение
`LDM` и обычные `STR`, блоки по 64 байта. M0+: 568 байт в SRAM resident
и автономного APP. При одинаковом выравнивании работают `LDMIA/STMIA`,
при разном — сборка слов сдвигами из выровненных чтений. На коротком
диапазоне стоимость подготовки избегается отдельным байтовым путём.
Обе функции обходятся без глобального состояния и занимают до 12 байт стека.

`memmove` сохраняет отдельную реализацию с поддержкой перекрытия.
Fallback C для остальных целей и Clang остаётся прежним. Уже собранные
автономные APP нужно пересобрать; runtime APP получает новый код при
обновлении resident, без изменения ABI.

## Результаты

Копирование **4096 байт RAM → RAM**, такты после вычитания пустого вызова.
`0/0` — оба адреса выровнены, `0/1` — назначение смещено на один байт.
Числа округлены; полные серии сохранены в `evidence`.

| CPU | Смещения src/dst | ROM | Прежний resident | Новое тело | Прежний автономный APP | Новый автономный APP |
|---|---|---:|---:|---:|---:|---:|
| M4 | 0/0 | 11330 | 4142 | **2786** | 6711 | **3824** |
| M4 | 0/1 | 13378 | 6446 | **5094** | 9530 | **6064** |
| M0+ | 0/0 | 3367 | 3367 | **2797** | 40969 | **2797** |
| M0+ | 0/1 | 28688 | 28688 | **8039** | 40969 | **8039** |

На M4 новое тело resident во Flash быстрее прежнего во всех **832**
измеренных сочетаниях размера, выравнивания и RAM/Flash-источника.
Автономный APP также быстрее своей прежней реализации во всех 832 случаях.
На выровненных 4 КиБ это **1,49×** для resident и **1,75×** для автономного
APP; на невыровненных — 1,27× и 1,57×. Flash и SRAM дают разное время
исполнения одного и того же машинного кода, поэтому они измерены отдельно.

На M0+ автономный APP быстрее прежнего во всех **928** случаях:
на 4 КиБ — **14,6×** при выравнивании и **5,1×** при смещении назначения.
Относительно прежней ROM-обёртки выигрыш на этих блоках — **1,20×** и
**3,57×**. При Flash-источнике выигрыш сохраняется: 4 КиБ занимают
примерно 2867/8117 тактов для `0/0` и `0/1`.

Это не обещание минимального времени на каждом размере. В основном
M0-прогоне два сочетания Flash → RAM со смещениями `2/2` дали небольшой
проигрыш ROM-обёртке: 64 байта — 101,77 против 99,02 такта; 127 байт —
152,29 против 151,20. Прямой ROM без обёртки также иногда быстрее на
коротких копиях. Все серии и эти различия сохранены в сводке; выбранный
код устраняет крупные потери побайтового цикла и ускоряет основной диапазон.

Настоящий SDK `--shared-runtime`, выбранное тело в памяти resident:

| CPU | Размер, src/dst=0/0 | Прежний runtime, такты | Новый runtime, такты |
|---|---:|---:|---:|
| M4 | 16 | 66,04 | **37,01** |
| M4 | 4096 | 4151,19 | **2794,50** |
| M0+ | 16 | 62,01 | **56,03** |
| M0+ | 4096 | 3382,81 | **2804,69** |

В каждом shared-прогоне проверено **256** сочетаний × 3 запуска;
проигрышей прежнему runtime свыше одного такта нет. Добавочная стоимость
перехода на коротких копиях — примерно **9 тактов M4 / 8 тактов M0+**.
На длинных копиях микросекундное разрешение M0-таймера и IRQ дают разброс
в несколько тактов; небольшая отрицательная разность двух серий не означает
отрицательную стоимость вызова. Ускорение больших блоков существенно больше
этого разброса.

Цена ускорения локального тела: M4 — 292 вместо 204 байт, M0+ — 568 вместо
18 байт до упаковки APP. Для Pico resident 568 байт размещены в SRAM;
для M4 resident дополнительная SRAM не нужна. Отдельная новая обёртка
runtime не добавляется.

## Что находится в ROM

У STM32F411 исследованная функция по адресу `0x1FFF0A4D` — 34-байтный
цикл копирования слов загрузчика. Это не полноценный ISO C `memcpy`:
не кратная четырём длина обрабатывается неверно. В измерениях `rom`
означает безопасный адаптер: ROM получает только `n & ~3`, остаток
копируется побайтно. Адрес применим только к проверенному дампу этого
F411; в production код он не попадает. Дамп —
[ROM Classic](../stm32f411-rom-2026-10-21/capture/rom-a.bin), CRC32 `9F8F7DED`.

В RP2040 BootROM v3 `MC=0x261D`, `C4=0x2605`. Для несовпадающего
выравнивания источника и назначения ROM использует побайтовый цикл.
Копирование того же ROM-кода в SRAM не исправляет этот алгоритм.
Собственный путь со сдвигами устраняет основную потерю скорости.
[Дамп ROM](../rp2040-memset-2026-10-21/capture/bootrom.bin), SHA-256:
`ef07d54bdd259c7858483606118a3c704976801823c38ac5a2fcdffacd2d83fe`.
Каждый запуск APP сверяет ROM перед обращением к нему.

## Подключение к прошивке

STM32 определяет тело прямо в `memcpy`, без дополнительной C-обёртки;
таблица runtime ссылается на него. На Pico SDK 2.2.0 применяется штатный
выбор `pico_set_mem_ops_implementation(... mk61)`. `__wrap_memcpy`
попадает в `.time_critical.memcpy`; `__aeabi_memcpy`, `memcpy4` и `memcpy8`
получают настоящие aliases на это тело, без промежуточного перехода.

Pico [memory_fill.S](../../ports/picocalc/memory_fill.S) сохраняет ROM
`memset`, перестановку аргументов EABI, таблицу из четырёх ROM-функций,
инициализатор `__aeabi_mem_init` и переключатель `PICO_MEM_IN_RAM`.
Лицензия адаптированного кода SDK сохранена рядом. Копирование `.data`
при старте SDK выполняется собственным циклом `data_cpy` в `crt0.S`,
поэтому не требует ещё не перенесённого SRAM `memcpy`.

## Методика

- Classic V3 UC1609, STM32F411, 96 МГц, исходный resident `3AB3DD45`.
  PicoCalc Pico H, RP2040, 125 МГц RUN, исходный resident `D26E5DE0`.
  Компилятор ARM GCC 14.2.1, Pico SDK 2.2.0.
- Источник — RAM либо Flash; назначение — RAM. Все 16 сочетаний
  смещений 0–3. До измерений 200 мс прогрева. Кэши прогреты; данные
  не являются измерением первого холодного обращения к Flash.
- Основные размеры M4: 0, 1, 2, 3, 4, 7, 8, 15, 16, 17, 31, 32, 33,
  63, 64, 65, 127, 128, 129, 255, 256, 257, 511, 512, 1024, 4096.
  На M0+ дополнительно проверены 23, 24, 25 — граница короткого пути.
  Shared-прогоны: 0, 1, 3, 8, 16, 64, 256, 4096.
- M4: аппаратный DWT, такты. M0+: `TIMERAWL`, микросекунды с переводом
  в такты по проверенной частоте 125 МГц. IRQ включены. `service()`
  выполняется между сериями, а обработчики прерываний могут влиять на время.
- Семь серий с вращением порядка функций; из каждой вычитается её
  контрольный пустой вызов той же сигнатуры. Число повторений:
  `max(16, 16384 / (n + 16))` для M4,
  `max(16, 32768 / (n + 16))` для M0+.
  Итог — медиана семи серий, затем медиана трёх независимых прогонов.
  Отрицательные выбросы парного вычитания сохраняются в сырых данных.
- `baseline` — прежний C-код, собранный в том же месте исполнения;
  `rom` — ROM напрямую (M4 через точный адаптер);
  `resident` — реальный указатель из таблицы установленной прошивки;
  `runtime` — переход SDK к прежнему resident;
  `own16/own64` — кандидаты; `sdk` — настоящий символ `memcpy` SDK.
  Дополнительный M0-вариант `rom_sram` — неизменённое тело ROM в SRAM.
- Для M4 отдельно измерены SRAM APP и Flash resident. Тот же машинный код
  исполняется из разных шин; результаты нельзя подменять друг другом.
  Flash-кандидаты помещены в проверенно свободный диапазон `0x08062000`,
  вне исходного sealed image. Весь Flash дважды сохранён перед опытом,
  затем восстановлен и проверен полным CRC.
- В отдельных shared APP настоящий SDK trampoline привязан к локальной
  копии таблицы с выбранным `memcpy`: к Flash-коду на M4, SRAM-коду на M0+.
  Таблица установленной прошивки не изменяется. Это аппаратная проверка
  нового runtime-пути без установки целой экспериментальной прошивки.
  Побайтовое совпадение с телами полных сборок и указатели их настоящих
  runtime-таблиц проверяются отдельно в `evidence/code-proof.json`.

## Корректность и сборки

[system_memcpy_arm_self_test.py](../../tests/system_memcpy_arm_self_test.py)
исполняет production-код на моделях M0+/M4: по 4837 случаев для четырёх
вариантов с LTO и без LTO. Проверяются размеры 0–257, крупные границы до
65536, 500 случайных диапазонов, `NULL,0`, возвращаемый указатель,
SP и `r4–r11`. Хуки запрещают чтение за концом источника, запись за
пределами назначения и невыровненные обращения M0+. Чтение ROM-страниц
или случайно доступной соседней памяти не скрывает ошибку границ.

Аппаратный APP проверяет содержимое, охранные зоны, неизменность источника
и возвращаемый указатель для всех кандидатов: размеры 0–257 и все
выравнивания, крупные размеры 511–4096 из Flash, затем каждую измеряемую
строку. Проверяется также `NULL,0` при каждом запуске.

Окончательные аппаратные сеансы, все `PASS`:

| Сеанс | Сочетаний × прогонов | Проверок корректности |
|---|---:|---:|
| M4, тело во Flash | 832 × 3 | 123792 |
| M4, автономный APP в SRAM | 832 × 3 | 123792 |
| M4, SDK runtime → новое тело | 256 × 3 | 108816 |
| M0+, автономный APP / тело SRAM | 928 × 3 | 126288 |
| M0+, SDK runtime → новое тело | 256 × 3 | 108816 |

Всего **591504 проверки без ошибок**. Предыдущий M0-кандидат также
сохранён в `evidence/m0-before-short-fix`: после его измерений порог
байтового пути поднят с 16 до 24 и сокращён вход в общий длинный путь.

[picocalc_memory_arm_self_test.py](../../tests/picocalc_memory_arm_self_test.py)
проверяет полный linked ELF: SRAM-адрес, EABI aliases, runtime-слоты,
настоящий ROM lookup при инициализации и 19988 случаев всех четырёх
`memset`-входов. Отдельно проходят все 26 runtime-слотов на M0+/M4
и host-тесты памяти с ASan/UBSan, включая перекрывающийся `memmove`.

Полные сборки F411 Classic V3 UC1609, F401 WS0010 + USB и PicoCalc
проходят. Проверка F401 сохраняет 16164 байта свободной Flash при требуемых
512. Сборки выполнены на текущем рабочем дереве; общий размер Pico включает
параллельные изменения других задач и не является ценой этой оптимизации.
Тела `memcpy` совпадают побайтно между квалифицированными APP, Flash-кандидатом
и полными прошивками.

HIL удаляет собственную временную папку, сверяет состояние калькулятора,
файлы и итоговый CRC/status. Терминальные логи, пользовательские данные
и резервные копии прошивки остаются в `.build`; в `evidence` публикуются
только результаты, проверочные APP/ELF и контрольные суммы.
После M4-опытов исходный полный Flash восстановлен, CRC32 `61CCEBFC`.
PicoCalc не прошивался и не перезагружался: `D26E5DE0`, CRC valid,
CRASH NONE, данные/IP/файлы сохранены, RTC продолжал идти. Serial закрыт,
устройство освобождено для следующего согласованного опыта.

## Повторение

Из корня репозитория, `TC` — каталог ARM GCC, Python для ARM-тестов
должен содержать Unicorn 2.1.4. Устройство должно быть свободно,
без выполняемой программы, APP, dirty editor или USB disk.
С другим экспериментом на том же устройстве необходимо согласовать очередь.

```sh
python3 research/memcpy-2026-10-21/build.py --target picocalc-pico-h --arm-toolchain-bin "$TC" --output .build/memcpy-repeat --directory /MCPY-REPEAT
python3 research/memcpy-2026-10-21/run.py --cpu m0 --port /dev/cu.usbmodem21301 --app .build/memcpy-repeat/app/COPYBEN.APP --directory /MCPY-REPEAT --output .build/memcpy-repeat/hil --runs 3 --sizes 0 1 2 3 4 7 8 15 16 17 23 24 25 31 32 33 63 64 65 127 128 129 255 256 257 511 512 1024 4096
python3 research/memcpy-2026-10-21/analyze.py .build/memcpy-repeat/hil/result.json --output .build/memcpy-repeat/summary.json
python tests/system_memcpy_arm_self_test.py --arm-toolchain-bin "$TC"
python tests/portable_runtime_trampoline_arm_self_test.py --arm-toolchain-bin "$TC"
python tests/picocalc_memory_arm_self_test.py path/to/mk61s-picocalc-pico-h.elf
bash tests/run_system_memory_tests.sh
```

Для самостоятельного M4 APP: `--target stm32`, затем `--cpu m4` и его CDC
порт. Для выбранного runtime: добавить к сборке `--shared --selected-runtime`,
к запуску `--selected-runtime`. M4 Flash-опыт воспроизводится через
`build-flash.py`, проверку `verify.py` и `run-flash.py`; он намеренно привязан
к точной исходной прошивке/USB identity и откажется при несовпадении.
