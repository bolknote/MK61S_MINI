# Механическая проверка, формальные спецификации и DeepSeek

На этом этапе веса не обучались и не заменялись. Проверяющий действительно выполняет программы на ROM МК-61; его ответы не являются оценкой нейросетевого критика. Главный результат: независимая правильная спецификация убрала 37 ложных DONE у неизменённой 3M, сохранив все 14 правильных завершений на 64 диагностических эпизодах.

32 условия × правильный/неверный старт дают 64 эпизода на строку. Это 32 группы наблюдений, а не 64 независимых задачи. Есть унарные, бинарные, составные вычисления и записи в память; ветвлений и циклов нет. В каждом эпизоде до 12 действий. Актор видит только исходную задачу, текущий код и реальные публичные факты. После изменения кода прежние публичные результаты аннулируются. Порог/веса по этому набору не выбирались.

| 3M Q4, обычный русский запрос | Правильных завершений | Принято DONE | Ложных DONE по исходной задаче |
|---|---:|---:|---:|
| Без проверки смысла | 14/64 | 51 | 37 |
| Проверка по собственной формальной гипотезе | 8/64 | 20 | 12 |
| Проверка по независимой формуле DeepSeek | 14/64 | 14 | 0 |

При замене поставщика спецификации 64/64 контрольных raw-потоков действий и HEX совпали целиком с предыдущим запуском. Начальный промпт маленькой модели не содержит формулу учителя и не менялся. Спецификация находится у механического проверяющего; актор получает только контрпример к ней после отклонённого DONE. Скрытые ответы исходной задачи актору и runtime в natural не передаются.

В варианте с формулой DeepSeek итоговый правильный код остался в 17/64 эпизодах, а завершение осталось правильным в 14/64. Проверка изменила принятие результата, а не способность модели исправлять программу: успешных исправлений неверного старта 7/32 до и 7/32 после. UNSURE вырос с 13 до 50; ошибок генерации и переполнений контекста в этом контроле нет.

Собственная гипотеза получена из goal-only HEX, сгенерированного до показа текущей программы, и восстановлена консервативным символьным декодером. Это проверка цепочки «условие → собственный код → подразумеваемая формула», а не чистая оценка понимания русского языка. У 3M такая гипотеза была доступна для 29/32 условий; с исходной задачей совпала для 6/32. Именно поэтому проверка по ней может принять неправильное решение и отклонить правильное. При неподдерживаемом коде гипотеза остаётся неизвестной, эталон её не заменяет.

Парное снижение доли ложных DONE с независимой спецификацией: -57.8 п.п.; 95% bootstrap-интервал по 32 условиям: -75.0 … -40.6 п.п. Это неопределённость малого диагностического набора, не гарантия нуля ошибок на новых задачах.

DeepSeek V4.1 Flash (так модель называется в доступном API) использовалась в двух разных ролях. В переводе русского условия в ограниченную формулу не требовались HEX или знание МК-61:

| Отдельный переводчик DeepSeek | Результат |
|---|---:|
| Формула и требуемые записи совпали с исходным условием | 32/32 |
| Детерминированно собранный код прошёл проверку своей спецификации | 32/32 |
| Тот же код прошёл независимую проверку исходной задачи | 32/32 |

Это гибрид «большой переводчик → компилятор → эмулятор», отдельно от работы 3M и её DONE. Он пока не является автономным агентом на PicoCalc: большая модель нужна здесь как исследовательский учитель. Результат относится только к данным 32 задачам. Правильность перевода проверена офлайн, а в произвольной новой задаче формула учителя также остаётся гипотезой.

В роли агента DeepSeek получила тот же снимок сессии и действия, а также отдельный справочник кодов. Это проверка протокола, не равное сравнение без справочника. Число ходов и факты эмулятора совпадают:

| DeepSeek, исходный протокол | Правильный итоговый код | Принято DONE | Повторные действия до лимита |
|---|---:|---:|---:|
| natural | 60/64 | 0 | 64/64 |
| formal | 58/64 | 0 | 64/64 |

Во всех этих 256 эпизодах DeepSeek повторяла WRITE и не вызвала DONE. Ноль ложных DONE здесь означает нулевое покрытие, а не надёжность. В двух дополнительных задачах вне набора явное описание продолжения сессии дало DONE для обоих правильных стартов, но также ложный DONE для одного из двух неверных стартов. Например, при просьбе R7−R8 программа `68 67 11 50` вычисляла R8−R7; учитель принял её после такого уточнения протокола. Эти четыре первых решения не являются полноценным экзаменом. Они показывают, что выбор DONE чувствителен к протоколу и не заменяет внешней проверки.

Проверяющий использует обычный математический вычислитель и фактическое состояние ROM. Проверяются останов, X, изменения памяти, сохранение остальных регистров и режим углов. Есть 24 проверочных входа и отдельные 32 аудиторских входа; проверены граничные значения и случайные внутренние точки в зафиксированных областях определения. Допуск 2e-6 абсолютный/относительный. TESTED означает конечные тесты, не математическое доказательство. Символьный декодер поддерживает только оговорённые прямолинейные формы; неподдерживаемое и ошибки области дают UNKNOWN.

Для компьютерного прототипа добавлена политика завершения в `ax_completion.py`: совпадение кода с неподтверждённой собственной или учительской формулой даёт `CODE_TESTED_AGAINST_UNCONFIRMED_SPEC`, а не разрешение завершить исходную задачу. Подтверждение спецификации поступает от harness отдельно от текста модели. Для принятия дополнительно нужны актуальные публичные исполнения и успешные численные проверки. Пять случаев этой политики проверены, включая самосогласованную неправильную формулу.

Первый пилот сохранён отдельно в `SPEC_DIAGNOSTIC_RESULTS.md`. Он добавлял формальную гипотезу во вход и использовал длинные контрпримеры; это ухудшало чтение условия маленькой сетью и приводило к переполнению 1024 токенов. Поэтому выполнен отдельный контроль с исходным AQ-промптом: 192 посимвольных сравнения прошли, в начальных снимках 704–863 токена. Набор при этом уже был открыт: этот контроль нельзя называть новым финальным тестом. Qwen без справочника плохо формировала HEX и давала незавершённые ответы; её нулевые гипотезы не трактуются как оценка общего интеллекта или доказательство превосходства другой архитектуры. В отдельном префлайте Qwen со справочником правильно решила 1/2 задач: во втором ответе перезаписала неназванные R0 и R1. Полный прогон этого варианта не запускался; оба ответа и неудачный префлайт сохранены в spec-diagnostic-reference-v1. Небольшая проблема параллельной записи одинаковых запросов в кеш исправлена отдельной транспортной обёрткой; замороженные промпты, веса и HTTP-параметры старых прогонов не менялись.

Следующий учебный эксперимент:

1. Отдельно обучать перевод русского условия в компактное дерево выражения и требуемых изменений состояния. Сравнить такую цель с прежним HEX на одинаковых 3M, данных и бюджете; преимущество новой формы пока не доказано.
2. Генерировать составные деревья, проверять компиляцию ROM и получать от учителя русские формулировки. Проверять обратный перевод; удерживать в тесте сами сочетания операций и структуры деревьев, а не только слова. Не переносить нынешние 32 задачи в новый финальный тест.
3. Учить переходы WRITE → недостающие RUN → проверка → исправление/UNSURE. DONE в учебных траекториях давать только после реальной проверки подтверждённой спецификации. Самооценку большой LLM не использовать как метку истины.
4. Отдельно считать исходную генерацию, правильный код после исправления, корректное завершение и риск среди принятых ответов. На новом закрытом тесте проверять Q4, покрытие и интервалы по независимым задачам.

В сумме завершено 1408 диагностических эпизодов, без единого обновления оптимизатора. Градиенты, прошивка и основной профиль модели не менялись; устройство не подключалось. Большая модель не заменяет локальную 3M: она дала проверенные семантические цели для следующего этапа.
