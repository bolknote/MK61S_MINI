# Один принудительный WRITE после DONE_REJECTED

Оба прогона завершены 8 ноября 2026 года. Обучения не было. Один принудительный
WRITE вернул часть успешных исправлений, но одновременно увеличил порчу верного
кода и число ложных DONE. Безусловное правило не удовлетворяет прежнему критерию
приёмки: улучшать исправления без роста двух видов ошибок.

## Что сравнивали

- Две последние фактически обученные BH-ветки: `fixed6000_lora` и
  `fixed6000_full`, по 3 022 080 параметров, упакованные веса Q4, вычисления и KV FP32.
  Это диагностические веса шага 6000; основной выбранный профиль не менялся.
- На ветку: 256 условий прежнего BH-экзамена, каждое с правильной программой
  и с детерминированным ошибочным вариантом. Итого 512 эпизодов на каждый режим,
  2048 эпизодов для двух веток и двух режимов.
- Контроль: прежний обычный цикл с механической самопроверкой.
- Вмешательство: после первого фактического DONE_REJECTED следующий выбор
  действия заменяется на WRITE ровно один раз за эпизод. SPEC для WRITE генерирует
  сама модель из обычного текущего промпта. Затем она снова сама выбирает действия.
- Как и прежде, WRITE автоматически исполняет текущий публичный случай; оставшийся
  RUN и DONE не навязываются. Сохраняются 12 действий и контекст 1024 токена.
  Дополнительного бюджета, подстановки эталонного кода и замены исходной SPEC нет.
- Включены все причины отказа: COUNTEREXAMPLE, EXECUTION, SPEC_DOMAIN и PUBLIC_RUNS.

Это диагностика на уже открытом экзамене, а не новый закрытый тест и не выбор
чекпойнта. Эталон условия используется только после взаимодействия для оценки.
Веса и градиенты не обновлялись; число шагов оптимизатора — ноль.

## Основные результаты

Стрелка означает «обычный цикл → один принудительный WRITE после отказа».
Успешное исправление требует правильного кода, завершённого DONE и выполненных
публичных запусков. Порча означает неправильный итоговый код при правильном старте,
даже если модель затем отказалась от DONE.

| Метрика | LoRA | Полная 3M |
|---|---:|---:|
| Успешные исправления, из 256 ошибочных стартов | 169 → 190 (+21) | 170 → 194 (+24) |
| Порча верного начального кода, из 256 | 28 → 32 (+4) | 32 → 39 (+7) |
| Ложные DONE, из 512 | 13 → 19 (+6) | 18 → 24 (+6) |
| Все успешные завершения, из 512 | 365 → 390 (+25) | 368 → 395 (+27) |
| Верный итоговый код независимо от завершения, из 512 | 406 → 421 | 406 → 423 |
| Правильные старты, успешно завершённые, из 256 | 196 → 200 | 198 → 201 |
| UNSURE, из 512 | 115 → 72 | 117 → 80 |
| Незавершённые эпизоды без UNSURE, из 512 | 19 → 31 | 9 → 13 |
| Эпизоды с ошибкой генерации, из 512 | 17 → 27 | 9 → 13 |
| Из них переполнение контекста | 9 → 9 | 9 → 9 |

Ни одно прежде успешно завершавшееся решение не потеряно. Это не означает
отсутствия порчи: часть ранее сохранявшегося правильного кода, с которым модель
не завершала задачу, теперь испорчена. В парном сравнении LoRA добавила восемь
таких ошибок и устранила четыре старых; полная модель добавила десять и устранила
три. Все шесть дополнительных ложных DONE в каждой ветке — новые, старые не исчезли.

## Где вмешательство помогает и где вредит

Принудительный WRITE был запрошен в 122 эпизодах LoRA и 126 полной модели.
В 17 и 13 случаях соответственно генерация этого WRITE закончилась ошибкой;
это включено в общие метрики. Нельзя считать все попытки выполненной записью.

Разделение ниже сделано **после прогона по эталону**, недоступному упряжи.
«Верная исходная SPEC» означает совпадение с условием на аудиторской выборке.

| Сработавшие вмешательства | LoRA | Полная 3M |
|---|---:|---:|
| С верной исходной SPEC | 39 | 44 |
| Успешно завершились после вмешательства | 25 | 27 |
| Новые ложные DONE в этой группе | 0 | 0 |
| С неверной исходной SPEC | 83 | 82 |
| Успешно завершились после вмешательства | 0 | 0 |
| Новые ложные DONE в этой группе | 6 | 6 |

В группе с неверной исходной SPEC в каждой ветке осталось по 28 эпизодов
с правильным итоговым кодом, но без завершения: проверка продолжает сравнивать
код с неверной гипотезой. Непосредственно принудительный WRITE испортил
правильный на момент вмешательства код в 12 эпизодах каждой ветки; все они
относятся к неверной исходной SPEC. Это другая метрика, чем порча правильных
начальных программ в основной таблице.

Часть потерь действительно вызвана выбором следующего действия: без новых
весов удалось вернуть 21 и 24 успешных исправления. Но переписывание программы
не исправляет неверное понимание условия. Проверка по ошибочной SPEC может
отклонить правильную программу и принять неправильную. Определять правильность
SPEC по скрытому эталону в рабочей упряжи нельзя.

## Проверка воспроизводимости

- Повторный контроль совпал с историческим Q4-прогоном во всех 512 эпизодах
  каждой ветки: промпты, сгенерированные токены, действия и итоговые поля.
- Во всех 122 и 126 затронутых эпизодах префикс траектории и промпт перед
  принудительным WRITE точно совпали с контролем.
- Все 390 и 386 незатронутых эпизодов точно совпали с контролем.
- В каждом эпизоде не более одного принудительного WRITE. Дальнейшие WRITE,
  RUN, DONE, UNSURE и остальные действия выбирала сеть.
- Хеши параметров до и после прогона совпали, градиенты отсутствовали.
  Проверены неизменность замороженных исходников, данных и экспортов,
  целостность Q4 и точность его загрузки. Нативный экспорт уже был проверен
  предыдущим экспериментом; физическая скорость PicoCalc здесь не измерялась.
- Оба собственных процесса завершены; обе B200 освобождены.
- Начальная попытка запуска остановилась до инференса из-за метаданных:
  локальный manifest содержал дополнительные поля нативного MKA-экспорта,
  отсутствовавшие на сервере. Проверено точное совпадение всех входов инференса;
  до получения ответов зарегистрирована поправка только для этих метаданных.
  Начальный протокол и аудит сохранены.

Основной профиль, прошивка и счётчик обучения не менялись. Безусловный WRITE
после любого отказа в основной профиль не перенесён.
