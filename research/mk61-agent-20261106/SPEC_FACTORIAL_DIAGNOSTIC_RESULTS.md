В режиме агента эталон меняет только приватную спецификацию механического проверяющего. Само условие и исходный промпт не меняются; правильная формула может попасть в контекст после настоящего DONE_REJECTED как обычная обратная связь. Механический контроллер проверяет текущий код по предоставленной ему SPEC на обычных входах проверяющего. Если код не проходит, он компилирует эту SPEC детерминированно, выполняет недостающие RUN актуальной редакции и запрашивает DONE через прежний gate. Если SPEC недоступна или проверка не проходит, отвечает UNSURE. Эталон условия и аудиторские входы не используются в выборе его действий вне явно эталонного режима. Бюджет остаётся 12 действий.

## Практический вывод

В пределах данного набора компилятор и механический контроллер обеспечили 256/256 правильных завершений при заданной правильной SPEC. С собственной верной SPEC они завершили 220/220 стартов. Следовательно, для поддерживаемой прямолинейной арифметики полезно сосредоточить модель на переводе условия в SPEC, а механические действия выполнять кодом.

Автоматическое завершение по неподтверждённой SPEC ухудшило ложные DONE с 18 до 30. Поэтому готовность исполнения и подтверждение смысла условия должны учитываться отдельно. Наличие независимой правильной SPEC здесь является диагностическим вмешательством; сам эксперимент не создал автономный проверяющий русского языка.

Следующий учебный эксперимент: сначала очистить формулировки и выделить однозначные условия; затем сравнить узкое обучение переводу в SPEC текущими адаптерами и полное дообучение тех же 3M при одинаковых данных и новой заранее закрытой оценке. В этом диагностическом раунде эти обучения не запускались.
