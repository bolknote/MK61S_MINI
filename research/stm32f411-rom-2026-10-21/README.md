# Исследование System ROM STM32F411 — 21 октября 2026

Дамп снят дважды, совпал побайтно и дизассемблирован. По итогам аппаратных замеров выбран **свой вариант алгоритма из ROM, исполняемый из внутренней Flash**. Он внесён в большой путь `memset` в [memory_word_ops.h](/Users/bolk/Projects/MK61S_MINI/code/memory_word_ops.h). Короткие пути 0..15 байт сохранены. В тёплом микротесте Classic F411 новый вариант тратит на **27–61% меньше тактов**, чем прежний, и выигрывает у вызова ROM во всех 88 проверенных больших случаях. Его машинный код занимает 82 байта против прежних 88, без учёта выравнивания.

**Приоритет пользователя — скорость.** Итоговый выбор основан на исполнении из Flash, с полным диспетчером `memset` и переходником у варианта ROM. Предварительные результаты из SRAM давали другой порядок кандидатов. Ниже сохранены эти этапы исследования; окончательные данные — в разделе «Итоговые замеры из Flash». Вызов заводского ROM в производственный код не добавлен.

Исследован один подключённый **Classic V3 UC1609 / STM32F411**, public ID `AEB505B6E0067623`, прошивка `3AB3DD45`. Другие Classic/Mini, в том числе STM32F401, этим исследованием не проверены. Адреса ниже относятся к конкретному дампу.

Первоначальное чтение выполнено маленьким временным APP из SRAM через существующие файловые службы прошивки. Ограничение бинарного файла 4096 байт учтено разбиением дампа на восемь частей. На этом этапе внутренняя Flash не программировалась, сброс и переход в загрузчик не выполнялись. После чтений и первых замеров временные файлы удалены; хеши исходных файлов, регистры, стек калькулятора, программа и текущий каталог совпали. Позднейшие эксперименты с записью Flash и восстановлением описаны в конце отчёта.

Основные артефакты: [дамп ROM](/Users/bolk/Projects/MK61S_MINI/research/stm32f411-rom-2026-10-21/capture/rom-a.bin), [полный линейный листинг](/Users/bolk/Projects/MK61S_MINI/research/stm32f411-rom-2026-10-21/rom-full.S), [выделенные функции с комментариями](/Users/bolk/Projects/MK61S_MINI/research/stm32f411-rom-2026-10-21/rom-helpers.S), [код установленного memset](/Users/bolk/Projects/MK61S_MINI/research/stm32f411-rom-2026-10-21/resident-memset.S), [машиночитаемые выводы](/Users/bolk/Projects/MK61S_MINI/research/stm32f411-rom-2026-10-21/findings.json).

Внутри — код загрузчика, обработчики интерфейсов, операции Flash и небольшие служебные функции. Есть сжатый блок: выполнение только scatter initializer `0x1FFF41D4` в эмуляторе распаковывает 2113 байт в `0x20000000`; файл с тремя байтами дополнения занимает 2116 байт. Там находятся в том числе RAM-функции операций Flash и USB-дескрипторы `STM32  BOOTLOADER`, Internal Flash, OTP и Option Bytes. Периферийная инициализация загрузчика при распаковке не запускалась.

Диапазон `0x1FFF4864..0x1FFF76BF` заполнен `FF` — 11 868 байт. Нельзя считать весь 30-КиБ диапазон исполняемым кодом: в линейном листинге также дизассемблированы векторы, данные, сжатый поток и заполнение. Консервативная инвентаризация дала 229 возможных точек входа; среди них встречаются внутренние фрагменты функций. Косвенные переходы покрыты не полностью. При просмотре полученного кода библиотеки математических функций, заменяющей наши `double`, тригонометрию или логарифмы, не обнаружено; это не доказательство отсутствия любого неразобранного фрагмента.

| Адрес кода | Содержимое | Пригодность |
|---|---|---|
| `1FFF3BD4` | Заполнение, 102 байта; `r0=dest, r1=size, r2=value`, возврат `dest` | Кандидат для больших блоков; порядок аргументов отличается от ISO C |
| `1FFF0A4C` | Копирование словами, 34 байта | Не обычный `memcpy`: при длине 1 пишет 4 байта, 5 → 8, 257 → 4 |
| `1FFF27C0` | Старшие hex-цифры числа в UTF-16LE, 40 байт | Узкий USB-формат без завершающего NUL; не замена нашему обычному форматированию |
| `1FFF3A60` | Перестановка байтов 16-битного числа, 10 байт | Вызов дороже встроенной инструкции `REV16` |
| `1FFF102E` | Обнуление по таблице scatter loading | Специальный интерфейс инициализации памяти |
| `1FFF3FDA` | Распаковка scatter-блока | Собственный формат и окружение runtime; не готовая замена ZX0 |

У копирования длина, не кратная четырём, превращается в `(n & 0xFC) + 4`: проблема не ограничивается округлением. Длины, кратные четырём, прошли выбранные проверки до 1024 байт, но общую семантику `memcpy`/`memmove` функция не обеспечивает.

Заполнение из ROM пишет с конца, выравнивает конец до слова, затем использует `STMDB {r2,r3,r4,r5}` по 16 байт. Зависимостей от периферии и глобальных переменных у выделенной функции не найдено. Сохраняет `r4/r5`, стек занимает 8 байт. Вызываемый Thumb-указатель — **`0x1FFF3BD5`**. Переходник меняет местами аргументы размера и значения:

```c
return ((void *(*)(void *, size_t, int))(uintptr_t)0x1FFF3BD5u)(p, n, value);
```

Проверки корректности: 4432 случая заполнения в Unicorn, включая случайные 32-битные значения, длины до 8192 и смещения до 31; сравнивается вся SRAM кроме 8 байт использованного стека, проверяются указатель возврата и callee-saved регистры. На устройстве каждый из двух запусков прошёл 2416 проверок: 2112 для ROM на длинах 0..65 и смещениях 0..7 плюс 304 проверки функций перед замерами. Для других кандидатов выполнены 45 случаев hex, все 65 536 значений u16 и контрпримеры копирования. [Результат эмуляции](/Users/bolk/Projects/MK61S_MINI/research/stm32f411-rom-2026-10-21/validation.json).

В используемом Unicorn 2.1.4 включение memory hooks приводило к неверному исполнению цикла `SUBS/IT/STMDB`. Поэтому hooks выключены, проверка записей делается сравнением памяти после возврата; корректность отдельно подтверждена физическим F411. Временные характеристики получены исключительно на устройстве.

Сравнение скорости сделано с **функцией из установленной прошивки**, полученной через runtime-таблицу SDK: `memset = 0x08008A21`. Считан и её реальный машинный код. Большой путь делает четыре 32-битные записи за проход по 16 байт; короткие пути обрабатывают 1..3 и 4..15 байт отдельно. Сравнение с простой побайтной библиотечной реализацией здесь не использовалось.

Стенд работает из SRAM. DWT CYCCNT измеряет 9 серий по 128 вызовов, перед каждой серией — обслуживание устройства и 8 прогревочных вызовов. Берётся медиана. Для каждого размера и смещения порядок: пустой вызов, наш A, ROM B, повтор нашего A. Прерывания включены. `FLASH_ACR = 0x703`. Максимальное расхождение A с повтором — 0,508 такта на вызов.

## Итоговые замеры из Flash

Все три локальных варианта и переходник к ROM размещены во внутренней Flash по адресу `0x08062000`. Каждый вызывается через полный 24-байтный диспетчер с прежними короткими функциями. Для локальных вариантов проверены два размещения тела: смещение 0 и 4 относительно 16-байтной границы. Исходный публичный `memset` вызывается до и после группы кандидатов; порядок кандидатов вращается. Выполнены три полных прогона по 152 случая: длины 0..4096, четыре смещения указателя. Метод — DWT, медиана девяти серий по 128 вызовов, после восьми прогревочных вызовов; вычитается одинаковый пустой вызов. Прерывания включены, `FLASH_ACR=0x703`.

Свой вариант, наиболее близкий к алгоритму ROM (`local_bulk_style`), выиграл у прежнего кода и у вызова ROM во всех **88 случаях длиной от 16 байт**. Его преимущество перед прежним кодом — 27,4–61,3% по числу тактов, перед ROM — 11,2–18,9%. Все 64 коротких случая сохранили прежнее время. Более компактные локальные варианты тоже ускорились во Flash, но уступили выбранному на длинных блоках. Данные сравнения всех кандидатов: [flash-comparison.json](/Users/bolk/Projects/MK61S_MINI/research/stm32f411-rom-2026-10-21/flash-comparison.json), [исходные три прогона](/Users/bolk/Projects/MK61S_MINI/research/stm32f411-rom-2026-10-21/flash-hil-3/report.json).

Затем выбранная функция внесена в `memory_word_ops.h` для GCC ARMv7E-M. Скомпилированные 82 байта **побайтно совпали** с измеренным кандидатом (`SHA256 80fed491ad7215983572676f94dd3bdde8bb134e4ae2fc09a0a4b35adccd5ebf`). Они установлены вместо прежней bulk-функции по адресу `0x08008934` в копии исходного резидента. Остальные функции и их адреса сохранены, footer CRC/build пересчитаны: проверочная сборка `ACCFE6FD`. Это позволяет измерить именно штатный публичный `memset`, включая вызовы из самой прошивки, без примеси других текущих изменений рабочего дерева.

**Границы результата.** Это замер прогретого `memset` на одном Classic F411, а не ускорение всей прошивки на 27–61%.
