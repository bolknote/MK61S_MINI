# Сохраняющая подготовка Y/T вместо скрытых V/W

Продолжение 27 сентября: [V прочитана, найден сохраняющий выход из этой
ветви](k1-y-t-swap-v.md). Ниже сохранён исходный договор подготовительного
этапа; его ограничения не означают отказ последующего проверенного блока.

26 сентября 2026. Новая клавиатурная ветвь на неизменённом эталонном
ядре и ПЗУ. **Это подготовка следующего доступа, не новая замкнутая
пара, не законченный выход и не полный К1.**

## Что изменилось

В конце глубокого префикса вместо K5 используется `↔`, без префикса K
и без дополнительного фазового кадра. Это не простая замена двух чисел
в стеке: смещённый запрос меняет фактический источник вторичной операции.
Её точный результат — копирование U в X и прежней X-метки в Y.

Обозначения — исходные числа: p из обычного П0; u/v/w/q из нижней Ms;
a/b/c/d из верхней. `m=9990FFFFFFF0`, `INV0=00008FFFFFFF`.

| Места | До последней ↔ | После последней ↔ |
|---|---|---|
| Обычный П0 | w | w |
| X1 | INV0 | q |
| X / Y / Z / T | m / u / q / m | v / m / q / m |
| Ms U / V / W / Q | v / u / q / p | v / u / q / p |
| Верхние P7 / P8 / P9 / P10 | a / b / c / d | a / b / c / d |
| Лишние метки | X, T | Y, T |

Все 23 исходника находятся именно в 15 обычных и восьми Ms-словах,
а не удерживаются только на индикаторе или в стеке. Последняя операция
вообще не меняет эти 23 числовых слова. В Ms нет ложных меток; настоящий
маркер цел. Это **не означает рабочее завершение**: Y/T ещё содержат метки.

Весь префикс задаёт перестановку `(П0 → Ms Q → Ms W → П0)` и
`(Ms U ↔ Ms V)`. Это точная перестановка на проверенных наборах, а не
предписанные восемь пар К1 и не доказанная повторяемая подпрограмма.

## Почему именно Y важна

[Разбор штатного сканера 9B](k1-nop-earlier-reserve.md) показал:
он переходит в 9C лишь после найденной метки. В прежней раскладке
real/T/V желаемая 9C(Z) была недоступна из этого сканера независимо
от ожидания: для неё требовалась Y-метка. Теперь такая метка достигнута
обычными клавишами с сохранением данных.

Но нельзя автоматически соединить результат с
[условным читателем p при real/Y/T/V](k1-y-v-lastx.md). Там нужны
X=u и V=m, здесь X=v и V=u. Превращение V в метку без предварительного
резерва уничтожило бы единственное хранимое u. Наличие Y снимает
**один** структурный барьер, а не все условия следующей операции.

## Точная трасса последней операции

На базовом наборе:

```
768897 9C(control) принимает запрос
768905 EE(W=q) → A1
768913 E9(X1) ← q
768915 A3(Y) меняет только M2[28,31,34] на 8/4/1
768927 9C(control) принимает следующий запрос
768930 ИК1303:4E(X) ← v из U
768931 ИК1303:2A(Y) ← прежнее m из X
768944 EE(X=v) → E3
768993 E7(U) ← v, идемпотентно
```

Вторичная операция **не** меняет X и Y местами: Y перед её выходом
содержит `148912345678`, а X получает число v из U. Проверщик сравнивает
все 630 тетрад до и после двух выходных команд и все 24 места записи.
Отдельная вторичная запись 27(control)[31] идемпотентна.

Для E9 проверены все 12 записей и все 630 тетрад; для A3 — ровно три
тетрады заголовка. Поздняя E7 имеет точный 12-тетрадный идемпотентный
выход. Полный журнал запрещает любые неучтённые изменения на этом этапе.

Весь префикс прошёл контроль 123 границ действий: ни один исходник
не отсутствует среди 23 хранимых слов и X1/X/Y/Z/T. Сохранность программы,
служебных полей, остальных 14 обычных регистров и всех четырёх верхних
Ms проверена по **всем записям**, не только конечным снимкам.
Это не отдельная теорема о присутствии всех чисел в хранимых словах
в каждый микротакт префикса.

Протокол — 171 клавиша / 1383 кадра при одном успешном чтении каждого
префиксного читателя. Подготовка фикстуры и начальная фаза не включены.
Контроллер использует лишь клавиши, ожидания и публичный индикатор
для существующих читателей; не читает скрытую память и не подставляет
исходные числа. Пустой `clonePrefix` сохраняет восемь кадров ожидания
вызова `stack.act`, а не удаляет этот этап времени.

## Проверки и числовой охват

Полные трассы пройдены на двух наборах верхних слов:

- a/b/c/d = −1E−99 / 9022 / 9033 / 9044;
- a/b/c/d = −2E−50 / −7.654321E23 / 1.2345678E42 / 8.7654321E−17.

В обоих p=201, u=−12345678, v=−9.8765432E−17,
w=−7.654321E−23, q=−1.2345678E−42. Изменение верхних чисел не
проверяет произвольные нижние числа или все начальные фазы.

Оба полных повтора без пассивного наблюдателя совпали по всем
сериализованным полям. SHA256 конечных состояний:

```
base f4d43c2c73a239c3ba1e6ca17f0e7a1bd16765878a124ce13ff7469eb8b594cd
wide b6deedd8eadaf8b4b98ea1ed97f57dd0e4f8ad4354cc7fe1bafd4abd15dad6c2
```

```sh
K1_Y_T_UNOBSERVED=1 node tmp/ms-rom-reachability/k1-y-t-entry-check.cjs
K1_Y_T_OPTIONS='{"fullUpper":["-2E-50","-7.654321E23","1.2345678E42","8.7654321E-17"]}' K1_Y_T_UNOBSERVED=1 node tmp/ms-rom-reachability/k1-y-t-entry-check.cjs
```

## Что не следует приписывать к этому входу

Простое [продолжение `В↑`](k1-y-t-enter-negative.md) проверено отдельно и отвергнуто:
оно сначала поднимает стек, затем поздняя E7(V) пишет v поверх
единственного u. Программа и служебные поля при этом остаются целы,
но числовой договор уже нарушен. Это отрицательный контроль конкретной
последовательности, а не невозможность всех продолжений.

[Связанная карта обычных читателей](k1-y-t-read-map.md) проверяет
ENTER, LastX, чтение/запись П0 для всех трёх допускаемых сканером
позиций принятия: control/Z/U. Ни один ранний читатель не берёт V.
Чтение П0 получает w и для текущего числового класса поздно пишет
его в V; запись П0 перезаписывает единственное хранимое w.
Два пути LastX пишут W/Q/P7/P8, вытесняя b. Третий переносит пустышку
в X; его дальнейший неканонический форматировщик ещё не разобран
полностью. Поэтому общего запрета на любой LastX здесь нет.

Вторая независимо исследованная ветвь — LastX после прежнего НОП —
также не даёт резерв p одним ожиданием. Есть полезный **условный**
суффикс от 9C(Z), но прежние real/T/V не дают входа из обычного 9B.
Нативный вариант с дополнительным кадром читает INV0 из X1 и сдвигает
W/Q/P7/P8, теряя b. См. `k1-nop-lastx-reserve-check.cjs` и
[границы условного пути](k1-nop-earlier-reserve.md).

Наконец, [карта всех первичных писателей V](k1-v-writer-map.md)
разделяет полезные варианты: одиночной E7(V) нужна Z-метка,
E9(V) нужна T-метка. BC(V) не подходит для сохранения начального
служебного байта 00: по прежнему полному reset-reachable инварианту
его нельзя ни сохранить этой записью, ни вернуть позднее.
Это следствие уже доказанного ограничения BC, не новый полный обход графа.

Открытая задача: получить резерв u и согласовать источник, метки и
позднюю запись следующего читателя. Следующее отдельное направление —
проверить перемещение u вторичными операциями ↔/F-комма; сохраняющее
продолжение ими пока не найдено. Затем надо соединить сохраняющий верхний
перенос с выходом. Полный К1, универсальный числовой договор, свободные
паузы и проверка этого нового блока на физическом калькуляторе не получены.
