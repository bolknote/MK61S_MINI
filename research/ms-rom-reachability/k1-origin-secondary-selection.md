# Почему запрос в Q ещё не выбирает W

26 сентября 2026. Связанные локальные проверки исходных ПЗУ, без
перебора клавиатуры и без подстановки состояния в живой эмулятор.

## Два разных выбора метки

Для 14h/25h недостаточно прочитать запрос через пару `W/Q`.
ИК1303 снова ищет метку перед подтверждением и выводом. При сохранённой
V оба эти поиска могут выбрать V, хотя первоначальный запрос прочитан
за W. Это не обычный перенос всей операции на одну позицию.

Условный вход: `6E(W)`, `R29=0`; V и W имеют M22=F, остальные страницы
не имеют этого признака, включая физическое место прежней основной
метки. В W пока старый заголовок 99, в Q задан запрос 14h или 25h.
Для 25h дополнительно нужны сохранённые первые два возвратных байта
ST=3Ah,3Ah. Без этого последняя 61 возвращается в исходный STtop,
а не обязательно в 3A.

14h проходит:

```
6E(W) 5E(Q) 50(P7) 52(P8) 53(P9) 4F(P10)
41(marker) 43(control) 4D(X1) 60(X)
37(Y/Z/T/U/V) 27(W) 61(Q) 4E(P7) 2A(P8) 39(P9)
```

Полные числовые копии: P7 получает старое P9, P8 — старое P7.
Это не обмен P8/P9; старое P8 не возвращается в хранимое слово.
В исходном origin-состоянии оно содержит единственную копию w.
Физическое место с d не читается для вывода и не меняется.

У 25h первый повторный поиск идёт
`D3(X) → 37(Y/Z/T/U/V) → 27(W) → D4(Q)`.
Пять D4 кончаются на P10, **не на физическом marker**.
Затем `60(Y) → 37(Z/T/U/V) → 27(W) → 61(Q)`.
Точный вывод:

```
P7  ← старое P9
P8  ← старое P9
P9  ← старое P10
P10 ← старое P8
```

d снова остаётся в физическом marker. Подтверждение меняет M31 в W,
не в Q; запрос в Q остаётся незавершённым.

Если первичный сканер вместо этого начинает с `6E(V)`, W:99 ведёт
в `5E(W) → 50(Q) → 52(P7) → 53(P8) → 4F(P9) → 24(P10) → 39(marker)`
без записей. Ни наличие 14h, ни наличие 25h в Q не превращает этот
конкретный проход в исполнение запроса Q.

## Условие нормального сдвинутого вращения

Контрольная связанная проверка с **удалённой V-меткой** проходит.
Теперь оба 37 доходят до W, подтверждение 27 попадает в Q, а пять D4
читают P7/P8/P9/P10/marker. Выход 25h:

```
61(P7) → 3A(P8) → 3A(P9) → 3A(P10) → 2A(marker) → 39(control)
P8/P9/P10/marker = прежние P9/P10/marker/P8
```

Именно это выносит d в P10. 14h при той же геометрии меняет P8/P9.
Итак, конкретное недостающее условие — убрать V до соответствующих
повторных поисков либо привести сканер к W уже после проверки V другим
путём. Простая смена начальной фазы 6E не меняет фиксированные внутренние
поиски рассмотренных процедур. Взаимодействие с одновременными записями
ИК1302 эта локальная модель не доказывает.

## Можно ли послать A3 без E9

**На уровне локального ПЗУ да:** существует `AD → A3` напрямую.
Для исполнения AD на физической W и A3 на следующей Q нужны:

| Запрос | R35 перед AD | R30 перед AD | R33 перед AD |
|---|---:|---:|---:|
| 14h | 3 | 4 | 1 |
| 25h | 3 | 5 | 2 |

AD не пишет кольцо. A3 пишет ровно Q[28]=старое R27,
Q[31]=старое R30, Q[34]=старое R33. Это связанный точный контракт
с произвольными остальными данными и сигналами клавиш, а не найденный
клавиатурный вход. Достижимость этих полей вместе с физической фазой
AD(W), а также безопасный возврат после A3 ещё не установлены.

Такой обход **не нейтрален к p**: сам A3(Q) перезаписывает три его
числовые тетрады, даже если E9(Q) вообще не выполнялась. Для origin-входа
с p=`002020100000` запись запроса уже меняет число. Кроме резерва p,
для полезного вращения всё ещё требуется решить выбор V/W выше.

В обычном STORE наблюдённая связка `EE(P7) → AB(P8) → AD(P9)`
не размещает AD на W; один этот локальный обход поэтому нельзя
выдавать за готовую новую клавишную команду.
