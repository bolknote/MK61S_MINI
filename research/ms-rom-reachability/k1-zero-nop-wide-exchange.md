# К1: новый читатель W и обмен трёх пар длинных чисел

19 сентября 2026 года. Цель остаётся прежней: полный восьмисловный К1
на неизменённом штатном МК-61 либо доказательство его невозможности.
Ни один из этих двух исходов пока не получен.

**Продолжение того же дня:** [буфер X1 и безопасный повтор](k1-x1-retry-reader.md)
устраняют разрушительный фазовый отказ в проверенном расписании: новый
тройной обмен прошёл широкий набор во всех трёх начальных фазах. Старый
отрицательный контроль ниже остаётся верным для читателя `zero-nop`.

## Проверенный шаг вперёд

Заменён ограниченный исторический читатель W в чистом цикле
П0→U→V→W→П0. Новый читатель не расходует ни одного обычного регистра.
Композиция четырёх циклов по-прежнему даёт П0↔U, П1↔V, П2↔W,
возвращая рабочий П3.

Пройден полный наблюдаемый тест **двух непрерывных обменов**:

- П0/П1/П2 = −1.2345678E−42 / 12345678 / 9.8765432E73;
- П3 = −6.5432109E65;
- U/V/W/Q = −1.2E−42 / −12345678 / −9.8765432E99 / 1E−99;
- верхние четыре Ms = 9011 / 9022 / 9033 / 9044;
- остальные обычные регистры содержат независимые числа 105…115.

Все 23 исходника различны. Проверен результат **каждого** внутреннего
цикла и обычного обмена, а также результат первого полного обмена до
второго: это не только тест итогового тождественного преобразования.
Остальные 11 обычных регистров и пять Ms удержаны даже временно;
программные и служебные тетрады не меняются в теле обмена. После него
прошли ручное 2 ↑ 3 + → 5, отдельное обнуление X и исполнение прежней
контрольной программы → 5. Все 105 её байтов восстановлены.

11118 наблюдавшихся записей; 110 изменившихся программных тетрад относятся
только к последующему штатному запуску программы, не к обмену.
Полная сериализация **всех** полей совпала с отдельным запуском без
наблюдателя (проверено deepEqual, не только хэшем):

```
c1436a4d3364ded9608b43d77a3c7b38f386c19badbbf2e89dbc21a2a13445dd
```

Новый вариант — 195 клавиш / 1645 кадров на один тройной обмен,
42 клавиши / 367 кадров на один цикл. Входная фаза большого теста — 0.
Однокадровые промежутки между обычным обменом и следующим циклом,
а также двухкадровый промежуток между полными вызовами сохранены.
Это фиксированное расписание модели, не обещание любых человеческих пауз.

## Почему старое ограничение снялось

Прежний логический читатель оставлял метку в Y, затем в Z. При W с
длинной мантиссой последующий форматировщик записывал W поверх U/V.
Новый вход сначала сдвигает классическую метку до T, вводя **нули**,
а уже затем читает настоящее W:

```
Сx В↑ В↑ В↑ +
Сx K − ВП K 0
0 K 0
0 K 0
0 K 0
В↑
```

НОП завершает ввод, поэтому следующий 0 поднимает стек. Нули вводятся
клавишами, а не берутся из заранее обнулённого рабочего регистра.
Рецепт в коде дополнен одним кадром для сохранения фазы композиции;
всего 21 клавиша / 179 кадров.

Перед последним В↑: X/Y/Z/T = 0/0/0/m, m=`0000F0000000`.
При правильном входе:

```
EE(W) → E0(Q) → A7(P7) → E5(P8/P9/P10/marker)
→ E6(control) → E8(X1) → E7(X) → A8(Y) → A8(Z) → A8(T)
→ A9(U) → E1(V)
```

W копируется в X, а единственная дополнительная метка вытесняется из T.
Позднему форматировщику уже некуда ошибочно записывать число в Ms:
он встречает только настоящую метку и возвращает число в X.

`k1-zero-nop-reader-path-check.py` доказал два блока:

1. 14 соединённых команд EE…A9: произвольные 12 тетрад W, точная копия
   в X, нулевые Y/Z/T, сохранение прочих дорожек и служебных полей;
2. стандартный EE(X)/topE3 с единственной настоящей меткой: все 24
   канонических ненулевых класса обоих знаков и отдельный ноль,
   всегда точный возврат 12 тетрад в X.

Это **не** сквозная теорема о всей клавиатурной последовательности:
подготовка, сканер, промежуток между блоками и остальные чипы отдельно
контролируются нативными тестами. Не заявляется универсальность для
всех входных состояний или произвольных нечисловых 12-тетрадных слов.

## Новая явная граница: ложное управление U

При фазе 1 и отрицательном порядке U обнаружен другой отказ.
Сканер 9C принимает U за служебное управление после метки T.
В↑ тогда читает **X=0 вместо W**, а стековый сдвиг идёт по W/Q/P7/P8.
В исходном нулевом W получено Q=0, P7=прежнее Q. Отдельный полный
отрицательный тест с W=12345678 и различными верхними словами подтвердил
потерю прежнего P8: чтение X на команде 94679, сдвиг с 94685,
вытесненное слово `003090220000` (9022). Это отдельный путь,
не возврат прежней ошибки форматировщика длинного числа.

Отрицательный контроль проверяет именно ложное чтение, четыре точные
записи среди всех 630 тетрад, конечный банк и оставшуюся метку T.
Он не превращается в положительный тест ослаблением условий.

Самостоятельный читатель с длинным W и отрицательным порядком U прошёл
точную проверку в фазах 0 (нижняя фикстура) и 2 (все восемь Ms различны).
Все фазы и все числа одновременно этим **не** покрыты.

Самостоятельный нулевой W в фазе 0 также прошёл полный тетрадный контроль
и сравнение всех полей с наблюдателем и без него:
`9e93e9393c666dd8a1ff3140744dbc051885576817c68aa2714737b9837efea0`.
Для широкого четырёхместного цикла в фазе 0 отдельно прошла точная проверка
48 записей среди 630 тетрад; главный сдвиг начинается на команде 182072.

## Что ещё проверялось и не стало решением

Попытка зарезервировать X1 так: заполнить Y/Z/T прежним П3, создать m
в X и выполнить K 5 (знак) — не сохранила П3 в X1. Туда записалась сама
метка m; запрос 32 изменил заголовок Y. Наблюдение не используется как
временный буфер для будущего полного К1.

## Следующий шаг к полной цели

Нужно устранить зависимость входа от ложного управления и получить
сохраняющую связь с Q и верхней четвёркой. Новый читатель снимает
конкретную потерю длинных чисел, но ещё не доказывает числовую и фазовую
универсальность всего тройного обмена. Только три из восьми требуемых
пар готовы в проверенном режиме; невозможность полного К1 не доказана.

## Воспроизведение

```
python3 tmp/ms-rom-reachability/k1-zero-nop-reader-path-check.py
K1_READER_NEGATIVE=1 node tmp/ms-rom-reachability/k1-zero-nop-reader-check.cjs
K1_READER_OPTIONS='{"values":["811","0","-9.8765432E99","-1E-99"],"p3":"-6.5432109E65"}' K1_READER_UNOBSERVED=1 node tmp/ms-rom-reachability/k1-zero-nop-reader-check.cjs
K1_THREE_OPTIONS='{"reader":"zero-nop","bank":["-1.2345678E-42","12345678","9.8765432E73"],"p3":"-6.5432109E65","values":["1E-99","-9.8765432E99","-12345678","-1.2E-42"],"twice":true,"verifyExit":true}' K1_THREE_UNOBSERVED=1 node tmp/ms-rom-reachability/k1-three-pair-check.cjs
```

Прежний читатель остаётся по умолчанию для воспроизводимости старых
отрицательных контролей; новый выбирается `reader:"zero-nop"`.
Прокси клавиатуры проверяет оба варианта, запрет скрытых чтений и
независимость действий от исходных чисел фикстуры.
Хэши эталона и ПЗУ повторно совпали с прежними:

```
mk61.cjs b15bc586ac3804eb5622b8072e88f35bcd2081abbe2195fcefa5a718e56ece0c
rom.cjs  6c3f85b3e942cdd4d4191e46e98a50829eb850011b8b7a3cc01b12e5e2a31a33
```
