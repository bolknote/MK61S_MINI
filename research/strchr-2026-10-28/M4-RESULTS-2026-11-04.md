# M4 strchr selection, 2026-11-04

The default M4 implementation checks the first sixteen bytes individually,
then uses the aligned DSP2 word loop. Native F401 Classic/40th graphics
profiles select the 18-byte byte loop to preserve their firmware Flash
reserve. Standalone SDK APPs use the default body; shared APPs retain the
existing runtime slot-18 veneer. M0+ keeps its previous implementation until
its own hardware window and selection.

## Physical measurements

The device was Classic F411, profile `classic-v3-uc1609`, actual core 96 MHz.
Every APP qualified DWT against the resident millisecond timer, preserved
DWT/DEMCR, required enabled IRQs and unchanged clock/cache/FPU context:
`[50553987, 71315481, 4106, 1795, 512, 15728640]`.
F401 timing equivalence is not claimed.

Each complete route covered 1152 cases: paired SRAM/Flash operands, four
alignments, zero/high-bit/truncated/negative characters, missing and early or
late hits. String lengths were
`0,1,2,3,4,7,8,15,16,31,32,63,64,127,128,255,512`.
Seven raw intervals were retained for every target and case, with fixed
repeat counts. Timing is the whole checked indirect-call loop, including its
overhead; no empty-loop subtraction or emulator timing is used.

The initial SRAM matrix, complete six-candidate SRAM/Flash matrix, and the
two final prefix16 comparisons contain **669312 physical intervals** and
**381702328 checked target calls**. SRAM and Flash code, operand banks, and
standalone/shared routes were analysed separately. All hardware phases were
independently accepted by the coordinator, including file/typed-state/RTC,
APP-cache, process, descriptor, lock and termios closure.

For each positive string length, patterns and alignments have equal weight.
Their arithmetic mean is weighted by `1/length`; zero length is separate.
This is an assumed workload distribution, not observed application traffic.
The measured grid is not an exact geometric `3^k` grid. Exact powers of three
were additionally exercised for HOST correctness, not physical timing.

The following figures are from the standalone route; shared-route direct
candidate measurements agreed closely. Cycles are median raw intervals
divided by the fixed repeats, followed by the weighting above.

| Candidate code | Operand bank | Old same-bank native clone | DSP2 | Prefix16 |
|---|---|---:|---:|---:|
| SRAM | SRAM | 85.644 | 79.118 | 69.715 |
| SRAM | Flash | 84.815 | 76.611 | 69.477 |
| Flash | SRAM | 79.152 | 65.404 | 60.504 |
| Flash | Flash | 79.329 | 65.631 | 60.723 |

Prefix16 was the fastest candidate under `1/n` in all eight final
code/operand/SDK-route contexts. For Flash code it reduced weighted whole-loop
time by about **23.6%** against the actual resident slot-18 target. In all
1152 cases of each final Flash route, its median was at least approximately
three cycles below the old same-bank native clone. The complete regression
maps include short decisive offsets separately.

With weights `n^-alpha`, DSP2 wins at `alpha=0` or `0.5`; prefix16 wins at
`alpha=1`, `1.5` and `2`. DSP2 remains useful for a workload dominated by long
searches. The selection therefore depends on the stated distribution.

The 18-byte compact body also beat the previous native Flash body throughout
the original F411 Flash comparison. It is selected for F401 graphics because
of the existing size contract, not because F401 performance was measured.

## Production bindings and validation

The actual native and standalone SDK bodies are pinned by the ARM tests:

| Body | Bytes | SHA256 |
|---|---:|---|
| Prefix16 | 288 | `039712087ec1e0d66e074780ee8266c4727c2b56e9950c4d13a781bb7e3c59d7` |
| Compact byte1 | 18 | `a02e16347138c513c279df7507c44d919bddf1766ac9ead65a60136f1cef2b71` |

The default body starts on a sixteen-byte boundary. The compact body uses a
two-byte boundary to preserve the F401 budget. Neither reads before the input
pointer. Byte reads stop at the decisive byte; each aligned word is checked
before the next word, and the containing final word can extend by three
bytes. These functions are for ordinary little-endian SRAM/Flash, not MMIO.

Validation on the isolated source based on `ee592b9003bf834f893b3ac15463ea437b0c73ea`:

- 165504 production ARM calls across Flash, SRAM and the real SDK runtime
  veneer, with unsigned-character semantics, unmapped boundaries, memory
  envelopes, input guards, AAPCS/SP/PRIMASK/CONTROL and invalid-access probes.
- Two real packed SDK APPs, relocated to three addresses: 12096 correctness
  checks, 9228 slot-18 forwards, cached reentry and
  invalid-oracle/stopped-timer/wrong-target checks. Their loaded sizes are 1840 and 1664 bytes.
- Thirteen full firmware builds: all eight shipping F411 board profiles and
  five F401 product profiles. Sealed ELF/BIN pairs agree byte-for-byte; every
  real 26-entry runtime table has slot18 pointing at the expected native body.
- F401 Classic v3 image: 258024 bytes, **4120 bytes free**, unchanged minimum
  **4096**. Classic v2: 4176 bytes free. F411 Classic v3: 141436 bytes free.
- Twelve System APPs passed their existing CI size limits. The largest loaded
  image is USBDISK at 20460 bytes, below the unchanged 20480-byte loader cap.
  LANGVM is 20340, BASIC 20028 and SRCEDIT 17664 bytes. No budget was relaxed.
