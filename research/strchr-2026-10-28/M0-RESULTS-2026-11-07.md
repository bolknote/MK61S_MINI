# M0+ strchr selection, 2026-11-07

The RP2040/PicoCalc implementation now uses the measured 58-byte `byte4`
body. It reads bytes in order, stops at the first match or NUL, converts the
search character to unsigned char, and never reads before or beyond that
decisive byte. The native body stays in warm XIP Flash, aligned to 16 bytes;
standalone SDK APPs use identical instructions in SRAM, aligned to 4 bytes.
Shared APPs retain their real runtime slot-18 veneer. M4 bodies are unchanged.

SHA256 of the measured and integrated body:
`cf9c04a95af5355a969542b4cdeb8fc58415d686cab2e712a30b6c2b0f84efec`.

## Physical comparison

The actual resident was D72994DB on PicoCalc/Pico H: SYS 125 MHz, PERI
48 MHz, QPI, LCD chain at 12 MHz, enabled IRQs, warm XIP cache. Four separate
routes covered standalone/shared APPs and SRAM/Flash candidate code. Each
route contained 1152 paired SRAM/Flash input cases, four alignments, lengths
`0,1,2,3,4,7,8,15,16,31,32,63,64,127,128,255,512`, early/late/missing hits,
NUL, high-bit, truncated and negative search characters.

All **464 timed APP runs**, **4608 rows** and **290304 raw intervals** are
retained. Each case/function has seven intervals with frozen repeat counts.
The timer was the readonly RP2040 TIMERAWL at 1 MHz, qualified through its
XOSC/ref/watchdog source and a bounded comparison to API milliseconds.
Context `[0x410cc601,0,0,0,3,0x882a]` was checked within every route. No IRQ,
clock, cache, DWT or SysTick setting was changed. The measurements cover
the checked indirect-call loop; no empty-loop time was subtracted. HOST
elapsed time is not used as MCU timing.

The primary assumed workload gives each input length total frequency
proportional to `1/(length+1)`, with equal pattern/alignment weight within
that length. This is a workload assumption, not measured application traffic.
The numbers below combine equal-sized SRAM/Flash input classes; units are
microseconds per checked indirect-call iteration.

| Route / candidate code | byte4 | Previous actual slot18 | Previous public SDK |
|---|---:|---:|---:|
| Standalone / SRAM | 0.496800 | 0.687116 | 0.530211 |
| Standalone / Flash | 0.495439 | 0.683600 | 0.527331 |
| Shared / SRAM | 0.497564 | 0.682376 | 0.755762 |
| Shared / Flash | 0.496222 | 0.682311 | 0.747785 |

The selected leaf reduces this weighted loop time by about **27–28%** against
the previous native target and about **6%** against the standalone SDK loop.
Shared SDK veneer overhead remains; comparing a direct leaf with that veneer
does not establish a 33% shared-SDK speedup. No application-wide speedup is
claimed. Warm Flash and SRAM candidate results differ by only about 0.3%;
Flash preserves the native SRAM reserve.

Inverse scanned-length weights and geometric bins for bases 2 through 10
also select byte4 in each route/input bank. Equal frequency per input length
selects the previous newlib body instead. The full regression maps include
short strings and long-search slowdowns, including roughly 3.3x regressions
on some cases. No sample or first error was dropped or replayed. These data
do not establish a universal winner or performance under cold XIP.

## Final implementation and verification

The final image B22DBAC8 / CRC 1FDC87DA was built from main e566772 plus the
accepted current AI SWAR/LCD/audio-DMA/Math overlay and only our strchr
changes. A readonly control rebuild first reproduced D729 byte-for-byte.
Reconstruction on newer main changed only five build-ID words and the
sealed CRC. Foreign overlay files are not part of the strchr commit.

The new image was written once and read back byte-for-byte over exactly
1538304 bytes; SHA256
`010976820f50f79c955d2bb9d83f568fde40adff16b7429b70746b75c7e51126`.
The erased prefix ends at 0x10178000, below MathQFP, the existing measurement
fixture, Spectrum and settings reserves. The image retains the accepted
AI/LCD/Math configuration. Static SRAM remains 119304 bytes and the heap
110072 bytes, above the unchanged 108544-byte foreground requirement.

Two final real SDK APPs exercised all 1152 SRAM/Flash cases through native,
public SDK and actual runtime26 slot18: **6912 physical correctness calls**.
Reports were exported before returning through the owned browser. This was
a correctness check, not a repeated performance campaign. The one browser
F8 switch was volatile and scoped to the owned directory. Final clock,
image CRC, crash, physical-input, idle, process, port, descriptor, termios
and lease checks were retained. The coordinator independently accepted both
the full measurement campaign and the final hardware CLOSED. No further
device access was required.

The first post-write completion stopped because its HOST metadata incorrectly
expected cleared diagnostics. The actual retained block kept its address
0x200004c0 and incremented BOOTS 1 to 2, with PREVIOUS_VALID=1 and no crash or
watchdog boot. The coordinator independently accepted this planned-reset
state. That HOLD remains unchanged; a separate strict readonly admission
preceded the two previously unexecuted APPs. Firmware was not rewritten.
Earlier preparation/fixture/browser HOLD records likewise remain intact.

HOST checks include 82752 public ARM calls with read envelopes and AAPCS,
3264 actual final-ELF strchr cases plus existing Pico ROM memory checks,
generic ASan/UBSan tests, two final packed-APP startup/runtime models with
negative controls, full F401/F411 firmware and System APP budgets, and nine
Pico APP builds. F401 Classic retains **5148 bytes free**, above the unchanged
4096-byte minimum. No budget was relaxed.
