# Восстановление скорости постраничной VM — 2026-10-18

Свежая `main` **93e8f846d + изменения этой задачи**, resident **FD1433B6**:
**52,269 с** с компиляцией, **36,995 с** прогретый поиск, **37,063 с** после
MCU reset с уже готовым файловым кешем. Историческая цель около **25 с пока
не достигнута**. Профилированные запуски в эти цифры не включены.

Работа согласована с задачей «Фокал». Classic восстановлен и освобождён:
исходный resident **3AB3DD45**, все **24 файла / 2 каталога**, прежние System
APP и пустое состояние калькулятора проверены. CDC закрыт. Mini/Pico не трогались.

## Что исправлено

1. Поиск кеша больше не строит USB/FAT-проекцию. `fat_find_child()` после
   C9-записи вызывал `c9_build_reverse()` / `c9_build_name_index()`, то есть
   чтение имён приводило к стираниям и записям NOR. Добавлен отдельный
   `program_store::find_child()`: обход штатной цепочки C9, folded hash и
   полное case-insensitive сравнение, без изменения FAT API для USB.
2. Небольшой LBV2-образ до 8192 байт может удерживать соседние кадры прежнего
   page-cache. Код, map и ресурсы читаются напрямую из RAM. Loan живёт весь
   RUN, включая INPUT/выгрузку APP; смена epoch не перезаписывает удерживаемые
   байты. Следующий RUN видит новую версию. Большие образы, отсутствие кеша,
   занятый loan и нехватка места сохраняют постраничный путь. Ошибка I/O не
   превращается в исполнение частичного образа.
3. Для малых образов проверка границ использует 1-КиБ bitmap внутри уже
   существовавшего union с Writer. Максимальный footprint union не вырос.
   Ненужные IndexB/Boundaries-каталоги создаются лениво.
4. Integer span читает raw-операнды без промежуточного копирования; все
   нужные операнды потребляются до первой записи в изменяемые банки.
   При trace сохраняется копирование. Проверены также наложения кода на
   стек, переменные и массив: результат, изменённые байты и ошибки совпадают
   со скалярным исполнением.

Нет шахматных shortcuts, новых opcode, увеличения исходников/байткода или
сокращения частоты service/ESC/USB. Формат LBV2 v14 и request ABI v13 сохранены.

## Причина холодной регрессии: отдельная C9/NOR-модель

Реальные 11 модулей шахмат, настоящие C9/compiler/verifier/publish, окно
исходника 1488 байт. Это операции модели, **не время и не счётчики платы**.

| Вариант | Чтения NOR | Записано байт | Стирания |
| --- | ---: | ---: | ---: |
| Reader-база | 190394 | 836836 | 2025 |
| Только catalog lookup | 19696 | 333450 | 90 |
| Lookup + bitmap + ленивые scratch-каталоги | 16532 | 262199 | 70 |

Число чтений исходника во всех трёх вариантах — 66. Полная загрузка
исходников в host RAM сама по себе оставляла 2025 стираний: главная проблема
была не в повторном чтении исходника. Регрессионный тест теперь требует
нулевых NOR-мутаций уже при открытии существующего кеша после C9-записи,
а не исключает предварительное «прогревание» FAT-проекции из счёта.

## Куда уходит остаток

Корректный тёплый runtime-профиль варианта C: поиск 41,465 с, отдельно от
обычных замеров. `app.entry.vm` self — **30,650 с**, idle вместе с USB —
**6,091 с**, NOR read — **0,595 с**, OPEN self — **0,064 с**. Вложенные времена
не суммируются. Компиляции, распаковки APP и NOR-записей в этом профиле нет.

Первый диагностический запуск на другом resident ошибочно начинался с
«готовых» страниц от предыдущей прошивки. Build ID входит в fingerprint,
поэтому они закономерно перекомпилировались. Эти 71,736 с исключены из тёплого
анализа. Последующие профили имеют отдельный прогрев и проверку нулевых
`flash.write/verify/erase`, `zx0.decode`, `app.load.basic/input`.

Для более точного выбора следующей оптимизации сделан **изолированный**
1-кГц PC-сэмплер resident. LANGVM.APP побайтно прежний. Настоящий связанный
SysTick wrapper проверен в ARM Unicorn для MSP/PSP и basic/FP frame:
контекст, callee-saved регистры, SP и один tick сохранены. Его диагностическая
сборка 88125006 также проходит все прежние ресурсные gates.

Тёплый поиск с семплером — 39,714 с, **не показатель обычной скорости**.
Получено 34424 семпла внутри VM-вызовов: 23973 в APP, 10451 в resident;
invalid/relocated/overflow/other — 0. Все frame extended. Разрешение — 128
байт: нельзя приписывать общий bucket одной короткой функции.

- Scalar `run`: 8566 семплов, целиком внутри функции — 24,88% всех семплов.
- Диапазон `0x20001280..0x200012FF`: 3939 (11,44%). Он пересекает
  Reader/View read, image_word и View::byte; это **не** точное время image_word.
- Диапазон dword(Cursor)/instruction_after: 1815 (5,27%).
- Integer span: строго внутренние buckets 2750; с пограничными максимум
  4729, то есть примерно 8,0–13,7% всех семплов.

Приоритет следующего PoC — скалярный fetch/декодирование и короткие чтения,
а не ещё одна настройка OPEN/NOR. Простой O2 только для integer_span не прошёл
linker gate: **+636 байт сверх 20480**. Лимит не менялся, этот вариант на
устройство не ставился и его скорость неизвестна.
