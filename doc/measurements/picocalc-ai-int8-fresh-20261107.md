# Свежая Flourish-3M: LUT_FLOAT32, INT8 и SWAR, 7 ноября 2026

Взята последняя готовая на момент начала проверки модель из чата «Harness на PicoCalc»: **harness-debug-v3 / selected-budget / active-best, шаг 1500**. Новый раунд с однотокенными действиями в том чате ещё готовился; его незавершённые веса в этот эксперимент не включены. Предыдущая проверка старого MKA не характеризует эту модель.

3 022 080 параметров, Q4, рабочий и обучающий контекст 1024, 8224 входных токена, 40 разрешённых выходных токенов, до 105 команд МК-61. Использованы её родные русский prompt, HEX-протокол, макросы констант/меток, ревизии кода и внешние инструменты.

**По суммарным результатам все три режима равны.** При этом INT8 потерял две задачи, которые решал LUT, и решил две другие. Поэтому утверждать отсутствие отдельных регрессий нельзя. По заранее выбранному строгому критерию сохранения каждого базового решения переключение основного режима не выполнено; LUT не удалён. Это более строгое инженерное условие, чем равенство общего числа решений.

В сценариях отладки 17 ложных DONE у каждого режима; в циклах с пустого листа ещё по два. Структурный gate проверяет только выполнение открытых запусков, а не правильность математики. Число ложных DONE от INT8 не выросло. Свежая модель сохраняет проблему самостоятельного распознавания неверного результата; это не следствие только квантования активаций.

**SWAR и обычный INT8 функционально совпали во всех 1175 проверках:** токены ответов, программы, история инструментов и результаты проверок одинаковы. Из сравнения исключён только счётчик повторно использованных токенов общего префикса. SWAR не восстанавливает точность FP32-активаций.

## Четыре изменившихся результата

Потери INT8:

- `hf-fresh:93`: требуется `cos(RB) + R3`, причём косинус должен вычисляться подпрограммой. LUT дал `6B 53 06 63 10 50 1D 52`. INT8 поменял регистры: `63 53 06 6B 10 50 1D 52`, то есть вычисляет `cos(R3) + RB`.
- `hf-fresh:230`: требуется квадратный корень текущего X, умноженный на `.375`. LUT решил задачу. INT8 выдал `<write>275 0B 22 50</write><run/>`: `275` не является байтом HEX. Такой ответ отклоняется, произвольное исправление парсером не делалось.

Выигрыши INT8:

- `hf-fresh:182`: выражение `((abs(R0) - R3) - square(abs(square((R0 * R1)))))`.
- `hf-fresh:206`: выражение `abs(((((R1 * R0) + square(R1)) * abs(neg(R3))) + R2))`.

В остальных 1051 одиночных задачах, 72 сценариях отладки и 48 циклах с пустого листа набор пройденных проверок не изменился. Равный агрегат получился за счёт обмена двух успехов на два других, а не полного сохранения поведения.

## Проверка совместимости и метод

До подсчёта качества новый native backend воспроизвёл все **13/13** контрольных генераций проверенного экспорта, сопоставленного автором модели с B200. Повторная проверка с повторным использованием общего KV-префикса тоже дала **13/13**. Длина входа и каждый выходной токен совпали; затем все режимы использовали этот же backend.

Inference выполнен нашим замороженным C++-кодом из SWAR-v5: SRAM-ядро, маска того же выходного набора из 40 токенов, одинаковый greedy-выбор, максимум 512 новых токенов и шесть инструментальных ходов. LUT использует исходную bitplane-укладку, INT8/SWAR — её доказанно без потерь перепакованную ниббловую версию. Квантованные значения весов и scales не менялись.

Prompt и инструменты взяты из готового harness-debug-v3, а не из старого native Agent. В объектах, передаваемых Session, оставлены только условие, параметры исполнения и открытые входы. Скрытые тесты, эталонные программы и ожидаемые выходы передаются только внешнему проверяющему после генерации. Эмулятор исполняет настоящий core МК-61; для продолжений С/П сохраняется и восстанавливается его собственный контекст между сегментами теста.

Модель, исходники протокола, эмулятор и наборы зафиксированы до подсчёта результатов. Критерий строгого перехода — не терять ни одного базового решения и не увеличивать ложные DONE. Обучения, подбора лучшего запуска и изменения правил после результатов нет. Это оценка данного чекпойнта на данных наборах, а не доказательство равенства на любых будущих задачах.

Все процессы завершились с кодом 0 и reaped. Аппаратного I/O и изменения прошивки не было. Основной runtime и UI не переключались на INT8; изолированный backend использован для сравнения качества. Физическая скорость свежей модели здесь не измерялась.

- MKA SHA-256: `7355022789e1ea8632901d25b957cd0d4b9bda67ea65505d50b3c920c90bf3f0`, 2 160 856 байт.
- Ниббловый MKA: `404565dba9f0864c4f1de1d9ef118f21a700d4bf69aef8de5673660fb7ec60f6`, тот же размер.

В нашем backend с двойным буфером workspace на контексте 1024 составляет 20 880 байт. Из них 6144 байта — LUT во внутренней SRAM; исключительно INT8-профиль мог бы уменьшить расчёт до 14 736 байт. Это не выполненное изменение. KV остаётся FP32 во внешней PSRAM: 5120 байт/токен, всего 5 242 880 байт на 1024 токена. Удаление LUT само по себе не увеличивает ни внешнее выделение KV, ни допустимую длину модели.
