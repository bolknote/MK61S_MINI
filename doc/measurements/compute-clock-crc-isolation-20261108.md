# Classic: CRC на 144 МГц — разделение USB и разгона

8 ноября 2026 года. Classic `AEB505B6E0067623`, USB `2068336B4731`.

**Подтверждён отказ режима 144 МГц вне USB.** Неправильный результат формируется в RAM при отключённом USB Screen и запрещённом OTG_FS IRQ. Он повторяется и в коротком блоке с полностью замаскированными прерываниями. Поэтому изменение CDC, которое скрывает пакетный CRC, не делает этот режим корректным.

## Решающий контроль

Один диагностический ELF `A3EEE88D` содержит исходный и альтернативные пути CDC/FIFO. Между вариантами не меняются прошивка и размещение её секций. Профиль загрузки задаёт PLL; диагностический запрос выбирает постоянную или меняющуюся частоту.

При запуске без USB:

1. APP загружается на пониженной частоте.
2. USB Screen закрывается; OTG_FS IRQ запрещается на весь повышенный режим.
3. На постоянной частоте выполняются xorshift, проверки resident `memcpy` с защитными областями и форматирование известного числа. Результаты остаются в RAM; файловых записей нет.
4. Дополнительно по восемь форматирований выполняются при полностью замаскированных IRQ. Максимальная длительность такого блока в серии — 0,176 мс.
5. Перед возвратом в терминал частота снижается, USB IRQ восстанавливается. Наблюдения считываются двоичными сообщениями с проверенным CRC. Текстовый форматтер и файловая система не участвуют в передаче этих результатов.

Три фазы каждого запуска содержат по 64 обычных вызова форматтера и по восемь вызовов каждого IRQ-контроля. Тестовый вход: `1430475313`.

| Частота CPU | Запуски с запрещённым OTG IRQ | Ошибки обычного форматирования за запуск | Ошибки при полностью запрещённых IRQ, каждая фаза |
|---|---:|---:|---:|
| 54 МГц | 2 | 0 / 192 | 0 / 8 |
| 60 МГц | 2 | 0 / 192 | 0 / 8 |
| 72 МГц | 6 | 0 / 192 | 0 / 8 |
| 96 МГц | 8 | 0 / 192 | 0 / 8 |
| 108 МГц | 2 | 0 / 192 | 0 / 8 |
| 120 МГц | 2 | 0 / 192 | 0 / 8 |
| **144 МГц** | **4** | **192 / 192** | **8 / 8** |

Ожидаемые байты: `31343330343735333133` (`1430475313`). На 144 МГц получены `31343331311835333133` (`14311\x185313`, где `18` — управляющий байт). Отдельные короткие проверки с полностью запрещёнными IRQ дают тот же отказ. Ещё два запуска на 144 МГц без экрана, но с разрешённым USB IRQ, также дают по 192 ошибки.

Серия 72→144→72 и матрица 96→120→144→96 повторяют появление и исчезновение ошибки. Xorshift-хеш и проверки копирования в этих запусках совпадают с эталоном: прохождение одного арифметического бенчмарка не квалифицирует весь разгон. ARM-модель исполняет тот же APP и реальный resident `memcpy`; проверки хеша, границ, часов и отсутствия файловых записей проходят.

## Контроль с работающим экраном

На том же ELF выполнены 16 запусков для 96→108→120→96 МГц: динамический профиль и постоянная верхняя частота, по два повтора каждого. Все прошли:

- пакетных CRC-ошибок — 0;
- хеш, копирование, форматирование и атомарные проверки — без ошибок;
- максимальная задержка nonce PONG — 7,243 мс при прежнем пределе 1 с;
- максимальный интервал клавиатуры — 17,830 мс, USB service — 8,500 мс при прежнем пределе 30 мс;
- все восемь каналов опроса имели реальные отсчёты, минимум 140.

Сборщик диагностической матрицы продолжает читать после повреждённого пакета, но помечает строку отказом. Сборка кадров после потери RECT здесь не используется. Это не ослабление штатной проверки полного кадра: финальная рабочая прошивка проверяется прежним строгим HIL.

## Что показали варианты драйвера

Сопоставление из предыдущего отчёта уже доказало, что пакет sequence106 в RAM был правильным, а на компьютере отличался одним битом. В новом образе отдельно проверены: запрет IRQ вокруг TX, однократное чтение свободного FIFO, ручная упаковка слов, атомарная публикация очереди, побайтовая очередь и блоки до 64 байт.

Побайтовая очередь скрыла CRC в одном запуске на 144 МГц, но оставила 64 неправильных форматирования в его повышенной фазе. Следовательно, такой «фикс USB» маскировал бы симптом. DSB после записи FIFO из предыдущего опыта также не помог. Эти варианты не включены в рабочую прошивку.

В [ES0287, §2.12.1](https://www.st.com/resource/en/errata_sheet/es0287-stm32f411xcxe-device-errata-stmicroelectronics.pdf) описан отдельный дефект FIFO при вмешательстве обращений к endpoint-регистрам. Диагностический отрицательный контроль намеренно нарушал это условие и остановил канал; адресный libusb reset восстановил только Classic. Он не объясняет решающий отказ в RAM при полностью неисполняющемся USB-драйвере. Штатный предел F411 — [100 МГц](https://www.st.com/en/microcontrollers-microprocessors/stm32f411.html); все более высокие значения в исследовании являются разгоном.

## Границы вывода

Доказана некорректность **данного режима 144 МГц на этом Classic**. Точный отказывающий аппаратный тракт CPU/памяти этим опытом не установлен. Исправность всех возможных CDC-последовательностей также не заявляется. Но рассматриваемый режим нельзя квалифицировать исправлением только CDC: ошибка воспроизводится с исключённым из исполнения USB и без IRQ.

Рекомендуемый рабочий диапазон не должен включать 144 МГц без отдельного нового доказательства корректности. Прохождение этих тестов на 108/120 МГц относится к этому экземпляру и не заменяет спецификацию ST.

## Артефакты и воспроизведение

Исходная ветка: `feature/compute-clock-20261107`, рабочие изменения настройки частоты. Диагностика — только отдельная копия исходников. `tests/experimental/usb_crc_isolation.patch` добавляет её поверх feature; в рабочую сборку патч не применяется. `tests/experimental/usb_crc_probe.*`, `tests/usb_crc_work_app.c`, `tests/usb_crc_work_arm_self_test.py`, `tests/hil_usb_crc_ram.py` и `tests/hil_usb_crc_transport.py` сохраняют нагрузку и HIL. Диагностический APP занимает менее 20 КиБ; все бюджеты Flash/RAM/стека сохранены.

Собрать APP через `tools/apps/portable/build_portable_app.py --name CRCWORK --source tests/usb_crc_work_app.c`, выполнить ARM self-test, затем HIL с адресованным Classic и диагностическим build ID. Основные режимы:

```
--profiles 0 1 2 3 0 --modes 144 160 --repeat 2 --no-screen
--profiles 0 1 2 0   --modes 0 32    --repeat 2
```

`144` и `160` в `--modes` — битовые флаги диагностики, а не частоты: запрет OTG IRQ плюс постоянная нижняя/верхняя частота. Эти флаги не сохраняются в настройках. Частоты задаются `--profiles`.

Полные ELF/BIN, команды сборки APP, неудачные подготовительные попытки, JSON всех строк и логи находятся в `.build/compute-clock-20261107/crc-isolation-20261108`. Неоконченные и ошибочные попытки настройки не включены в таблицу причинного доказательства. Прочитаны и проверены все 57 файлов и 10 каталогов устройства; тестовые файлы удалены. Рабочая прошивка с исправленным меню возвращается на 96 МГц.

Финальное состояние подтверждено: рабочая `CFD23EE8`, 96 МГц после перезагрузки, firmware CRC valid, CRASH none, MPU layout ok. Строгий штатный HIL с полной проверкой экранных кадров прошёл; CHIP-8 — 59,896 FPS. Хеши всех 57 файлов и список 10 каталогов до и после возврата рабочей прошивки совпадают. CDC закрыт, Classic освобождён. Код USB рабочей прошивки не менялся; исследование и тесты не коммитились.
