# Постраничная VM: локальная проверка сплошных малых образов

Продолжение после переподключения Classic: аппаратные сравнения завершены,
положительные изменения перенесены в рабочую main. Итог свежей сборки —
52,269 с с компиляцией / 36,995 с прогретый / 37,063 с после reset с готовым
кешем. См. [последующий отчёт](chess-paged-recovery-20261018.md).
Ниже сохранён исторический статус локального этапа, до аппаратной проверки.

Статус: **локальный PoC прошёл, аппаратный эффект ещё не измерен**.
Последний подтверждённый результат Classic — 45,780 с; цель около 25 с
и холодная компиляция около 50,8 с не достигнуты. В этом этапе платы не
использовались. Изменения PoC пока изолированы, не включены в main.

## Что удалось отделить

Реальный LBV2 и старый RAM-LBV1 в локальном runner выполнили одинаковые
6 464 181 логических инструкций, 4 045 860 dispatch и 3 131 906 инструкций
внутри fused-блоков. Файлы счётчиков побайтно совпали. Потери целочисленных
оптимизаций компилятором при переходе на LBV2 здесь не обнаружено.

Для трёх одинаковых поисков LBV2 через Reader занял 0,203180 с внутри VM,
тот же LBV2 напрямую из RAM — 0,170664 с, сокращение 16,00%.
Это Clang на desktop, не ARM: здесь не учтены компиляция, подготовка,
M61/OPEN и настоящие C9/NOR/USB. Каждый поиск: e2e3 / оценка 54 / 420 узлов.

## Прототип

Образы до 8192 байт могут занимать соседние кадры **существующего**
resident page-cache. Повторный RUN получает const-указатель, если все кадры
уже готовы; иначе один раз собирает их с проверкой I/O и фоновым опросом
между страницами. Хранится полная физическая последняя страница, включая
padding: это сохраняет договор обычного страничного get().

Кадры удерживаются до завершения RUN, включая выгрузку APP и INPUT/resume.
Смена media epoch инвалидирует ключи, но не перезаписывает удерживаемый
образ. Код, map и prompt текущего RUN читаются из одного снимка; следующий
RUN увидит новую версию. Неудачный fill не публикуется. Нет дополнительных
image-sized аллокаций, изменения формата/ABI или размера APP. Большие образы,
нет кеша и занятый loan — прежний постраничный режим. Частота обслуживания
VM не менялась. Заимствование включено только в тёплый resident путь PoC.

В модели той же последовательности трёх поисков 22 963 из 22 990 запусков
использовали готовый сплошной образ; 27 промахов потребовали 63 чтения страниц.
Пул прежний — 32768 байт, payload 29696 (29 кадров). Сумма 11 образов —
25120 байт, при округлении по 1 КиБ — 30 кадров, включая редко используемый
init. Модель использует фиксированный epoch и не учитывает компиляционные
записи/параллельное постраничное чтение; это не число чтений NOR на плате.

## Размеры и проверки

Чистая база d8b23c262 + уже измеренные Reader/decoder-оптимизации + PoC.
Собран, но **не установлен** resident 90724052: 370872 байта, +672 байта к
предыдущему Reader-варианту; запас 153416 при проверенном минимуме 131072.
LANGVM побайтно прежний: 20444/20480 RAM, SHA
`5bf89886d9967bfa5dd22e5198ef5e18c151ba268013d627783e6de520564f47`.

Resident frame 1928/3072, APP frame 3264/5120; effective APP pool 34880,
lazy 52560, scoped 5184, placement 224 — прежние. Global RAM gate 49152
также пройден. F401 product WS0010 fallback: Flash 239604, свободно 22540
при минимуме 8192; frame 1336/2048. Лимиты не ослаблялись.

- ASan/UBSan: границы, padding, LRU, заполнение всего пула, ошибки I/O,
  отказ service, смена epoch при fill и при удерживаемом образе — PASS.
- Настоящий C9/NOR-модель: большие 200-КБ образы остаются постраничными;
  loan переживает запись/вытеснение, следующий RUN читает новую версию,
  частичный I/O не исполняется, восстановление после отказа — PASS.
- Обе арифметики: raw/paged совпадают по значениям и steps, включая
  массивы, CALL, DATA, INPUT и длинные строки — PASS.
- Реальные ARM APP BASIC/FOCAL: 66225-байтные постраничные образы и
  225-байтные raw/paged, три адреса загрузки, INPUT/выгрузка/resume — PASS.

## Что ещё нужно

Адресный read-only IOKit recovery доказал сохранность установленного
3AB3DD45 после зависания dfu-util, но не квалифицировал запись и восстановление
через DFU. Пользователю предложено переподключить только свободный Classic.
Защитный helper не переделывался в writer, повторных USB/DFU обращений здесь
не было. После восстановления штатного транспорта нужны A/B/A на Classic,
контроль полной доски, 420 узлов, CRC/MPU/стека/USB и восстановление файлов.

Для отдельного холодного профиля HIL получил `--profile-first-compile`:
после обычных измерений удаляется только принадлежащий сценарию derived-cache,
выполняется reset и отдельный профилированный поиск. В обычные времена он
не включается. Сам холодный профиль на устройстве пока не снят.
