# Уплотнение загрузки программ MK61s

23.09.2026. Реализован и испытан общий загрузчик программ ZX0 + basE91.
Команды доступны в терминале и M61; прошивка не содержит специальных правил
для ELITE.

## Реализованный формат

```text
ztart 0000 <CRC32>
zin <Base91>
zin <Base91>
```

Адрес - четыре десятичные цифры. CRC32/ISO-HDLC - восемь hex-цифр,
контрольная сумма распакованных байтов, совместимая с `zlib.crc32`.
Ни размер сжатого образа, ни размер результата не передаются. Конец определяет
маркер ZX0 v2; отдельной команды завершения нет.

Один поток ZX0 продолжается между строками и вложенными M61. Каждая строка
`zin` - самостоятельный блок basE91 (не более 235 символов). Поэтому границы
строк однозначны даже при нечётном числе символов. Упаковщик сначала режет
сжатые байты на блоки по 176 байт, затем кодирует каждый блок. Кавычки и `;`
передаются буквально. Каноническое кодирование проверяется обратным кодированием
блока: лишние символы и ненулевые хвостовые биты не игнорируются.

Распаковка идёт прямо в программные банки; записанные байты служат словарём
повторов ZX0. Размер проверяется при записи, включая доступные слоты банков.
При окончании CRC вычисляется по загруженному диапазону через существующий
`mk61_crc32::Context`: на F411/F401 используется аппаратный блок, доступен
программный резервный путь. CRC не удерживается между строками, чтобы C6 мог
пользоваться им при чтении следующей части.

Ошибки Base91, ZX0, CRC и нехватка памяти блокируют `run`/`cmd`/`kbd` и правку
программы из терминала. Обрыв на `run`, EOF или корневом `ret` останавливает
M61. Вложенная часть может закончиться посередине потока. `reinit` и новый
корневой M61 сбрасывают загрузчик; записи при ошибке не откатываются.

## Результат ELITE

| Показатель | Прежний разреженный hin | ZX0 + basE91 |
| --- | ---: | ---: |
| Текст частей | 6690 байт | 2726 байт |
| Число частей | 5 | 2 |
| autoexec.m61 | 106 байт | 58 байт |
| Части вместе с autoexec | 6796 байт | 2784 байта |
| Распакованный образ | 3584 байта | 3584 байта |

Экономия текста частей - 59,25%. Размеры новых частей: 1349 и 1377 байт;
13 строк `zin` и один `ztart`. Сжатые двоичные данные занимают 2144 байта.
Игровое размещение: 3485 занятых байт и 99 нулевых свободных байт.
Это уменьшение загрузочного представления, а не числа игровых инструкций.

На Classic V3 (F411) с прошивкой `360A410A` измерен путь от команды открытия до
проверенного останова на заставке: 2,131 с до изменения и 1,895 с после.
Это по одному проходу с опросом регистров и паузой проверки 0,4 с;
разницу нельзя считать точным временем самого распаковщика.

## Проверки реализации

- Host с ASan/UBSan: basE91, блоки с нечётными хвостами, ZX0 по одному байту,
  повторяющиеся и случайные данные, перекрывающиеся повторы, границы памяти,
  все обрезанные префиксы контрольного потока и 2000 некорректных потоков.
- M61-runner: загрузка через дочерние файлы, CRC, EOF, корневой `ret`, `run`,
  отмена, `reinit` и повторный корневой запуск. Дополнительно исправлена потеря
  исходного сообщения при повторной обработке ошибки из `ret`.
- ELITE на настоящем ядре: 1608 остановленных состояний, включая 256 миров,
  торговлю, встречу, победу и поражение, дронов, приборы и удержание кадра.
- Classic V3: generic-образ со всеми значениями байтов, пересечение банков,
  ошибки CRC/Base91, предел 9999 и исчерпание 32 слотов, обрывы M61; затем
  24 действия ELITE до победы с проверкой всех страниц данных, регистров
  и единственного обновления индикатора на ход. Возврат на заставку.
- Файлы игры и обе страницы системной справки прочитаны обратно после записи;
  устаревшие части 02..04 удалены после сверки с резервными копиями.

Сборка F411: 354476 байт против 351612, прирост 2864 байта. Глобальные переменные
состояния загрузчика по ELF занимают 43 байта без выравнивания; временный
буфер одного блока - 206 байт на стеке. Копия всего образа не создаётся.

Воспроизведение:

```sh
python3 tools/elite/build.py --check
bash tests/run_program_load_tests.sh
MK61_TEST_SANITIZERS=1 bash tests/run_m61_text_tests.sh
bash tests/run_terminal_tests.sh

```

Общий настольный упаковщик: `tools/program_pack.py input.bin --address 0`.
Аппаратный тест: `tests/hil_program_load.py` с портом, public ID, build ID и
явным `--confirm-ram-overwrite`. Логи, резервные файлы, PNG и аппаратные замеры
текущего испытания: `/private/tmp/mk61-zin-20260923/hardware/`.

Окончательная прошивка устройства - `65CDC4E9`. После приведения типов для
строгой сборки GCC повторены аппаратные проверки загрузчика, сверка всех
файлов и запуск исходного autoexec через памятку до заставки.

Проверена также сборка Classic V3/F401. Она компилируется, но не проходит
линковку по Flash: 4528 байт сверх 256 КиБ в стандартном профиле без USB Screen.
Для сравнения собран чистый HEAD `955008dd` с теми же флагами: превышение
2008 байт существовало до изменений, прирост от загрузчика составляет
2520 байт. С USB Screen текущий профиль F401 превышает лимит на 15512 байт.
Это не готовая поставка для F401; аппаратные испытания выполнены на F411.

## Предварительное сравнение кодировок

Следующие таблицы сохраняют исходные измерения прототипов; условные заголовки
в них отличаются от окончательного `ztart`/`zin`.

### Измеренный размер текста

Учитываются адреса, имена предлагаемых команд, переводы строк и лимит M61
1536 байт. Памятка и `autoexec.m61` не включены. Для обычных кодировок оставлены
те же 37 участков, что у текущего разреженного `hin`; это не поиск оптимального
разбиения под каждый алфавит. ASCII85 использует сокращение `z` для четырёх нулей.

| Вариант | Байт текста | Частей |
| --- | ---: | ---: |
| Текущий `hin`, HEX с пропуском длинных нулей | 6690 | 5 |
| Base64 | 4642 | 4 |
| ASCII85 | 4310 | 3 |
| basE91 | 4244 | 3 |
| Экспериментальный Base94, 13/14 бит на пару символов | 4199 | 3 |
| ZX0 отдельно по 112-байтовым банкам + ASCII85 | 4063 | 3 |
| Общий оптимальный ZX0 + ASCII85, проект потокового формата | 2807 | 2 |
| Общий оптимальный ZX0 + basE91, проект потокового формата | 2755 | 2 |
| Общий оптимальный ZX0 + Base94, проект потокового формата | 2734 | 2 |

Последние три строки предполагают один поток на все банки. Для оценки служебных
расходов использованы условные `zbegin <адрес> <распакованный-размер>
<сжатый-размер> <CRC32>`, `zdata <до-220-символов>`, `zend`. Это эскиз синтаксиса,
не действующие команды. Декодер должен сохранять состояние между строками
и частями. После выбора окончательного интерфейса размеры следует пересчитать.

### Сжатие двоичного образа

Образ из 32 банков занимает 3584 байта, включая свободные нулевые участки;
занятые кодом и данными байты по карте сборщика — 3485.

| Упаковщик | Байт бинарного потока |
| --- | ---: |
| Встроенный bounded-optimal ZX0, каждый банк отдельно | 2882 |
| Встроенный bounded-optimal ZX0, весь образ, окно 256 байт | 2474 |
| Настольный оптимальный ZX0 из tools/.mk61-app/third_party/zx0, весь образ | 2144 |
| Raw DEFLATE, zlib level 9 | 2062 |
| LZMA с заголовком FORMAT_ALONE | 2062 |
| bzip2 | 2101 |

Все использованные сжатые потоки распакованы и побайтно сверены. Оптимальный
ZX0 распакован существующей `zx0::decode` из `code/zx0.cpp` на host. Потоковый банковый загрузчик реализован отдельно в `zx0_stream.cpp`;
прежний декодер C6 и модулей не изменён.

Один поток ZX0 после basE91 содержит 2635 символов данных; 2755 байт в таблице
включают предложенные служебные строки. DEFLATE + basE91 даёт 2537 символов
данных, всего на 98 меньше, но требует добавить распаковщик DEFLATE.

## Цена декодера и ограничения

Изолированный прототип ASCII85 с проверками границ занимает 190 байт ARM-кода
и констант; basE91 — 264 байта. Сборка: Cortex-M4, Thumb, GCC 14.2.1, `-Os`.
Это не полный прирост прошивки: диспетчер команд, проверки адресов, справка,
CRC и потоковая распаковка сюда не входят. Прототип ASCII85 проверен на
336 обратных преобразованиях и некорректных входах; basE91 и Base94 — на
разных длинах, случайных данных, нулях и FF, включая все измеренные потоки.

Только расширение печатного ASCII-алфавита даёт небольшой выигрыш: для длинного
равномерного потока переход от 85 до всех 94 непробельных печатных символов
имеет предел около 2,36%. Нули и короткие хвосты меняют результат отдельных
файлов. Base94 здесь — собственный эксперимент, а не установленный стандарт.

C6 уже прозрачно сжимает M61. При повторной упаковке частей встроенным
bounded-optimal ZX0 полезные данные текущего HEX занимают 3407 байт,
ASCII85 — 3949, ZX0 по банкам + ASCII85 — 3840 (без накладных расходов C6).
Фактическая политика C6 имеет пороги выгоды и может оставить короткие части
несжатыми. Поэтому уменьшение текста само по себе не доказывает уменьшения
расхода Flash. Главная непосредственная выгода — меньше частей при логическом
лимите 1536 байт; общий сжатый поток уменьшает также сами передаваемые данные.

## Вывод

Выбран и реализован общий поток ZX0 с basE91 и проверкой CRC,
без привязки к ELITE. Упаковка выполняется на компьютере, распаковка - при загрузке.
Это около 59% экономии относительно текущих файлов. Base94 экономит ещё
21 байт в выбранном потоке; выигрыш не оправдывает отдельный нестандартный
алфавит. Формат загрузки не изменит размер исполняемой программы и число
шагов игровых вычислений.
