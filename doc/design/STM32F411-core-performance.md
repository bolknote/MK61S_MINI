# Производительность ядра МК-61 на STM32F411

Статус: аппаратный A/B постоянного SRAM-массива и вытесняемого общего кеша
завершён; SRAM→Flash→SRAM проверен на host и F411; packed-byte DSP-кандидат
проверен и отклонён по аппаратному A/B
Дата: 30.08.2026

## Стенд и методика

Плата — STM32F411CE, частота DWT — 96 МГц, профиль
`mini-v3/lcd1602-a00`, Flash ART, оптимизация размера без LTO. Для каждого
варианта выполнялись 20 терминальных `cmd 00`, то есть 40 полных
`core.step`. Все проценты ниже относятся к одному и тому же сценарию.

При включённом `sergey_anvarov_hack_enable` один шаг содержит 280 циклов по
42 микротакта. Исходная схема поэтому делала 35 280 вызовов отдельных
`IK1302/03/06_Tick`, а объединённая — 11 760 вызовов wrapper.

## Что оставлено

1. DWT CYCCNT-профилировщик с точками ядра, idle, дисплея, USB Screen,
   SPI-Flash и ZX0; сбор начинается только по `prof start`.
2. На F401 и F411 микрокоманды, DCW/DCWA и AND/AMK opportunistic копируются в
   общий 8-КиБ `WORKSPACE`; отдельного массива 7232 байта в `.bss` больше нет.
3. Три Tick встраиваются в один `IK130X_Tick_All`, поэтому общая
   ABI-обвязка выполняется один раз на микротакт.
4. Два постоянных расписания микротактов полностью разворачиваются; цена —
   112 байт Flash относительно компактных циклов.
5. Если `WORKSPACE` занят или в нём сохранён язык, ядро оставляет таблицы во
   Flash; после освобождения арены кеш лениво восстанавливается.

Исторические цифры ниже сняты на прежнем отдельном SRAM-массиве. Они остаются
доказательством полезности размещения данных в SRAM; отдельный результат нового
динамического кеша приведён после таблицы.

## Обновление общей SRAM от 02.08.2026

`CoreHotTables` теперь является вытесняемым cache-владельцем `WORKSPACE`.
Reclaimer сначала переводит все внутренние указатели ядра на неизменяемые
таблицы Flash и только затем освобождает память. После восстановления контекста
сырые указатели ребазируются на текущий backend. Host-тест подтвердил побайтовое
совпадение полного состояния до и после SRAM→Flash→SRAM.

Сопоставимые GNU/LTO-сборки от HEAD `3ebcdc3`:

| Профиль | BIN до/после | `.data` до/после | `.bss` до/после | Статическая SRAM |
| --- | ---: | ---: | ---: | ---: |
| F401 A00 | 244556 / 250332 | 2496 / 2912 | 58220 / 58220 | +416 |
| F411 A00 + USB Screen | 299696 / 306048 | 2908 / 3328 | 51552 / 44336 | **-6796** |

F411 освобождает 7216 байт `.bss`, а с учётом 420 байт новых метаданных чисто
освобождено 6796 байт статической SRAM. На F401 постоянная `.bss` не выросла:
кеш использует уже существующий workspace, когда он свободен. Цена всей общей
архитектуры во Flash — +5776 байт F401 и +6352 байт F411, не только кеша.

Копирование таблиц намеренно выполнено через `noinline,noclone` helper: это не
даёт LTO повторно материализовать около 6416 байт констант в Flash.

Adaptive-порог для коротких команд после проверки отклонён. В финальном F411
ELF helper переходит в обычный byte-loop `memcpy` из четырёх инструкций
`LDRB/STRB/CMP/BNE`; даже консервативная оценка всей загрузки 7232 байт остаётся
ниже 0,1 млн тактов. Исторический изолированный A/B Flash→SRAM экономит около
0,60 млн тактов на каждом `core.step`, поэтому кеш окупается уже на первом
шаге. Эвристика лишь добавила бы состояние и случаи непредсказуемого перехода
во Flash.

Для диагностики `mem` показывает `cached`, число `loads`, `evictions` и
`flash_steps`.

## Измерения

### Данные во Flash и SRAM

| Размещение таблиц | Дополнительная SRAM | `core.step`, avg |
| --- | ---: | ---: |
| все таблицы во Flash | 0 | 4 587 756 |
| микрокоманды + DCW/DCWA | 1088 байт | 4 225 034 |
| также AND/AMK | 7232 байта | **3 990 129** |

Малые таблицы дают 7,91% относительно Flash, большие AND/AMK добавляют ещё
5,56%; весь перенос данных уменьшает время шага на 13,03%.

### Вытесняемый кеш общего `WORKSPACE`

На финальной F411-сборке paced-сценарий из 20 `cmd 00` снова дал 40 шагов:

| `n` | min | avg | max | `flash_steps` |
| ---: | ---: | ---: | ---: | ---: |
| 40 | 3 942 062 | **3 952 811** | 3 963 798 | 0 |

Динамический кеш оказался на 13,84% быстрее исторической Flash-точки
4 587 756 и на 0,94% быстрее исторического dedicated-SRAM результата
3 990 129. Поскольку эти точки получены разными сборочными профилями, проценты
нельзя трактовать как строгий изолированный compiler A/B; аппаратный результат
подтверждает главное: совместное владение памятью не съело выигрыш SRAM.

После вытеснения `fsput` ядро безопасно перешло на Flash, а на первом следующем
шаге снова загрузило 7232 байта: `loads=1`, `evictions=1`, `cached=1`,
`flash_steps=0`. Аналогичный цикл несколько раз прошёл при переключении FOCAL и
TinyBASIC без расхождения состояния.

### Организация горячего кода

| Вариант | `core.step`, avg | Решение |
| --- | ---: | --- |
| три отдельных Tick, Flash + ART | 4 380 737 | исходная контрольная точка |
| объединённый Tick + полная развёртка | **3 990 129** | оставить, быстрее на 8,92% |
| объединённый Tick + компактные циклы | 4 193 558 | отклонить, медленнее на 5,10% |
| локальный `optimize("O2")` wrapper | 3 993 467 | отклонить, выигрыша нет |
| вся прошивка `-Os -flto` | 4 077 712 | только size-профиль; ядро медленнее на 2,19% |

### Код в SRAM

Обычная `.RamFunc` по адресу `0x20000000` выполняется через System bus, а не
из быстрого пути Flash + ART. При неизменной исходной схеме Tick среднее время
выросло с 4 380 737 до 5 353 475 тактов, то есть на 22,2%. Такой перенос
отклонён.

## Финальная аппаратная валидация

### Packed-byte DSP: доказанный отрицательный результат

Для самого короткого одинакового участка трёх ИК был реализован кандидат
выбора AMK через packed-byte `USUB8` и `SEL`. Scalar reference формально
задаёт правило `AMK >= 60 && L == 0 ? AMK + 1 : AMK`; exhaustive host-тест
сравнивает все `68^3 * 2^3 = 2 515 456` комбинаций. Дополнительно classic и
expanded ядра прошли full-state differential после каждого шага. ARM ELF
проверен дизассемблером: в кандидате действительно присутствуют `USUB8` и
`SEL`, то есть измерялся настоящий DSP path.

Для воспроизводимого HIL добавлена команда `prof core 40`: она занимает уже
существующий общий context slot, сохраняет живое состояние калькулятора,
создаёт одинаковое временное состояние, измеряет ровно 40 полных шагов DWT,
затем восстанавливает и побайтно проверяет исходное состояние. Пять независимых
серий на STM32F411CE/V3/WS0010 дали:

| Вариант | `core.step`, median avg | Разброс средних | sealed BIN | globals |
| --- | ---: | ---: | ---: | ---: |
| scalar production | **3 550 240** | 3 550 194…3 550 297 | 306 756 B | 28 048 B |
| packed AMK `USUB8/SEL` | 4 390 507 | 4 390 502…4 390 521 | 306 964 B | 28 048 B |

Кандидат медленнее на **23,67%**, добавляет 208 байт Flash и не меняет
постоянную RAM. Причина видна и в дизассемблере: исходные AMK и флаги лежат в
разных объектах, поэтому перед единственной packed-операцией приходится
собирать слово и маску, а затем извлекать три результата. Это дороже трёх
локальных scalar-проверок. Production остаётся scalar; кандидат хранится только
за compile-time switch как воспроизводимый отрицательный эксперимент. Порог
включения 3% не достигнут с большим запасом, поэтому отдельный F401 HIL не
может изменить решение о невключении.

### Длинный профиль и хвост распределения

Непрерывная программа `JMP 00` дала 1480 выборок `core.step`:

| `n` | min | avg | max |
| ---: | ---: | ---: | ---: |
| 1480 | 3 597 897 | 3 603 813 | 4 046 552 |

Этот сценарий проверяет длительную работу, но его абсолютное время нельзя
сравнивать с `cmd 00`: путь микрокода другой. Отчёт сохранён в C5 как
`LONGPROF.TXT`.

Для точного хвоста отдельно выполнены 500 независимых окон `cmd 00` по два
шага. Из `min/max` восстановлены 1000 отдельных аппаратных выборок:

| min | avg | p50 | p95 | p99 | max |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 3 963 872 | 3 993 425 | 3 970 962 | 4 025 260 | 4 025 534 | 4 025 772 |

Все 500 окон содержали ровно по два шага; `p95` выше среднего только на 0,80%,
то есть заметного длинного хвоста у ядра нет.

### USB Screen, дисплей и C5

Headless desktop-клиент одновременно принимал кадры, передавал бинарные
нажатия, выполнял терминальные команды и записывал/считывал 1344-байтовый файл
с проверкой POSIX CRC:

| Кадры | События клавиш | RX | TX | sequence gaps | discarded | rejected |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 52 | 36 | 32 147 байт | 4352 байта | 0 | 0 | 0 |

Профиль того же интервала: `core.step=36`, `display.update=36`,
`usb.service=254105`, `flash.read=2972`, `flash.write=8`. Отчёт сохранён как
`USBPROF.TXT`; тестовый payload после проверки удалён.

Практическое ограничение: предельный 96-байтовый `fsput data` допустим
протоколом, но в attached USB Screen-сеансе длинная терминальная строка может
потеряться. Штатные 48-байтовые блоки MKC прошли весь параллельный стресс.
Поэтому `FS_PUT_CHUNK_BYTES=48` нельзя увеличивать без backpressure или
переработки обслуживания CDC RX.

### Эквивалентность baseline

На исходной Flash+ART-прошивке и на финальной конфигурации выполнена одна и та
же цепочка из 667 операций: ограниченная рекуррентная арифметика, двойная
смена знака, `sqr/sqrt`, заполнение и обратное свёртывание `R0…RE`. Снимки
`stk`, `reg`, `1302` и полного `ring` совпали байт-в-байт:

```text
SHA-256 b6508ebde455e2277c7b7bfe81b70523cf24b89ee1ac3d3d52158ee6ab8a4702
```

После сравнения на устройство снова прошит финальный BIN, версия
`Jul 31 2026 (12:56:19)`, а состояние калькулятора очищено командой `reinit`.

## Вывод по архитектуре

У этой нагрузки три независимых свойства:

- ART хорошо обслуживает линейный код и ветвления из Flash;
- случайные чтения таблиц из Flash конкурируют с выборкой инструкций и заметно
  выигрывают от переноса данных в SRAM;
- выборка инструкций из обычного адреса SRAM идёт менее эффективным путём,
  поэтому классическая `.RamFunc` здесь вредна.

Это означает, что следующие изменения надо выбирать по типу доступа, а не по
общему правилу «RAM быстрее Flash».

## Следующий план

1. **Общие индексы объединённого Tick.** Один раз вычислять `mod42(+1/+2/+3/
   +40/+41)` и адреса текущих ячеек для трёх микросхем; проверять отдельным
   DWT A/B, цель — ещё 2–4% без изменения состояния.
2. **DSP/SIMD-прототип.** Упаковать одинаковые независимые 4-битные операции
   трёх ИК в байты 32-битного слова и проверить `UADD8/USUB8/SEL`; сначала
   доказать бит-в-бит эквивалентность на host-тестах, затем мерить один участок.
3. **DMA только для длинных SPI-передач.** Добавить асинхронный double-buffer
   для кадров USB/FAT и крупных чтений C5; мелкие обращения оставить polling,
   потому что настройка DMA дороже самой передачи.
4. **Таймер вместо программного обслуживания звука/индикации.** Перенести
   периодические фронты в output compare/PWM и измерить уменьшение
   `idle.main`, не вмешиваясь в калькуляторное ядро.
5. **`WFI` в действительно пустом idle.** Засыпать только когда нет USB,
   SPI, звука, клавиатурного debounce и ожидающей перерисовки; цель —
   энергопотребление, а не скорость `core.step`.
6. **SRAM-remap — отдельный рискованный стенд.** Если когда-либо снова
   проверять код из RAM, нужен адрес `0x00000000` через ICode remap, отдельные
   векторы и физические адреса для DMA. Это не следующий production-шаг:
   обычная `.RamFunc` уже дала крупную регрессию.
7. **FPU использовать только там, где допустим `float`.** Аппаратная FPU
   single precision подходит графике и оценочным вычислениям; стек и
   трансцендентная математика МК-61 сохраняют `double`, иначе теряются
   требуемые десять значащих цифр.

Каждый пункт принимается только после host-регрессий, одинакового
40-шагового DWT-сценария и проверки размера Flash/RAM. Одновременно менять
раскладку памяти и алгоритм нельзя: иначе результат нельзя приписать
конкретной возможности процессора.
