# SIGILL при инициализации Unicorn на macOS

Исследован отчёт Python от 2026-11-05 19:32:16 +0300, incident
`706D0608-200D-44BC-909B-8FB63DDC1E4B`. Это проверочный запуск Unicorn
перед ARM-тестами URQ, через `tmp/urq/venv/bin/python -X faulthandler -c ...`.
Падение произошло в первом `Uc.mem_map`, до исполнения гостевого ARM-кода.

Среда: Apple Silicon, macOS 26.7.1, Homebrew Python 3.15.2, Unicorn 2.1.4.
UUID библиотеки в crash report и на диске совпал:
`1D49EF35-60CA-3CCD-90A6-FA5B1D4AB9E6`.
SHA-256 проверенной `libunicorn.2.dylib`:
`7207c8e3d7a63118fb0bca73e01816797fd51b1d8a39a4cbc7abfd562ee59c85`.

## Цепочка сбоя

1. Unicorn запрашивает `sysctlbyname("hw.cachelinesize")`.
2. В sandbox этот запрос возвращает `-1`, `errno=EPERM` (1).
   Контрольные запросы `hw.pagesize` и `hw.machine` при этом успешны.
3. После отказа библиотека переходит к запасному чтению регистра `CTR_EL0`
   инструкцией `mrs x8, CTR_EL0`. На этой системе этот путь завершается SIGILL.
4. Код инструкции `0xd53b0028` совпадает с `Exception Codes` в отчёте.
   Повторный сигнал из Python faulthandler объясняет верхние кадры
   `raise` / `pthread_kill`; точку сбоя нужно искать ниже, в Unicorn.

Дизассемблированный участок установленной библиотеки:

```text
0x10c54  bl   _sysctlbyname
0x10c58  cbnz w0, 0x10c78
...
0x10c78  mrs  x8, CTR_EL0
```

Этот алгоритм также виден в
[исходнике Unicorn 2.1.4](https://github.com/unicorn-engine/unicorn/blob/2.1.4/qemu/util/cacheinfo.c#L60).

## Контрольный запуск

Проверен тот же venv и тот же файл dylib без переустановки или изменения байтов.

| Проверка | Sandbox | Вне sandbox |
| --- | --- | --- |
| `hw.cachelinesize` | EPERM | 128 байт |
| Инициализация и `mem_map` | намеренно не повторялись после отказа sysctl | PASS |
| Исполнение Thumb `MOVS r0,#42` | не запускалось | PASS, R0=42 |

Нового аварийного завершения в ходе исследования не вызывали. Устройства,
прошивки и файлы калькуляторов не затрагивались.

## Следствие для запуска тестов

ARM-тесты с этой библиотекой на данном Mac следует запускать вне sandbox
через обычное разрешение инструмента. Перед нативной инициализацией можно
проверять `hw.cachelinesize`: при EPERM остановиться с понятной ошибкой,
не вызывать `mem_map` и не повторять падающую пробу.

Обновление Python само по себе здесь не обосновано. Независимо от исправления
условий запуска, библиоте достаточно обрабатывать отказ sysctl без опасного
для macOS аппаратного fallback. Это отдельное изменение Unicorn; в рамках
исследования зависимости и системные разрешения не менялись.

## Применённая защита

`tests/unicorn_runtime.py` проверяет доступность `hw.cachelinesize` до создания
нативного двигателя. Все 40 штатных скриптов, напрямую создававших `Uc`,
переведены на этот конструктор. Сам возвращаемый объект Unicorn не изменяется.
Косвенные пользователи общих ARM-моделей наследуют ту же проверку.

`dev/tools/run_arm_test.py` выполняет предварительную проверку и запускает
указанный скрипт тем же Python, сохраняя аргументы и путь импорта. При отказе
среды возвращает код 2. Автоматического повышения прав нет.

Проверка: девять регрессионных тестов guard/launcher проходят без Unicorn и
без выполнения запрещённых инструкций. В sandbox launcher остановился до
создания эмулятора; вне sandbox реальный тест общего runtime прошёл для
Cortex-M0+ и Cortex-M4: по 26 слотов, проверены передача аргументов,
возврат и сохранность регистров. Устройства не использовались.
