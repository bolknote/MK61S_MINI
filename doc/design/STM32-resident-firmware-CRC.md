# CRC целостности resident-прошивки STM32F401/F411

## Назначение и границы защиты

Каждый публикуемый BIN resident-прошивки получает post-link footer и до
инициализации дисплея, внешней C5, USB и watchdog проверяется встроенным
CRC-блоком STM32. Случайно повреждённый или не полностью записанный образ не
продолжает обычную загрузку: прошивка оставляет компактную запись в `.noinit`,
делает reset и сверхранний `.preinit_array`-пролог передаёт управление ROM DFU.

Это проверка целостности, а не secure boot. CRC не содержит секретного ключа;
человек, способный согласованно заменить прошивку и footer, может создать новый
валидный образ. Задача механизма — обнаруживать битые файлы, ошибки передачи и
повреждение внутренней Flash, сохраняя гарантированный путь восстановления.

## Формат footer

Footer имеет стабильный размер 40 байт, выравнивание 4 и magic `MK61FWC\0`:

| Смещение | Поле | Назначение |
|---:|---|---|
| 0 | magic[8] | Поиск единственного footer в BIN. |
| 8 | version, size | Версия 1 и размер 40. |
| 12 | image_start | `0x08000000`. |
| 16 | image_size | Точная длина BIN после линковки. |
| 20 | expected_crc32 | Ожидаемый стандартный CRC-32. |
| 24 | build_id | Content ID, равный `expected_crc32`. |
| 28 | profile_id | FNV-1a идентификатор аппаратного профиля. |
| 32 | flags | Бит `CRC_REQUIRED`. |
| 36 | reserved | Ноль. |

Канонический CRC считается по всему BIN; поля `expected_crc32` и `build_id`
при расчёте считаются восемью нулевыми байтами. Затем одно полученное значение
записывается в оба поля. Благодаря этому ID не зависит от того, в какую секунду
компилировался отдельный `.cpp`, однозначно совпадает в terminal/footer/crash
dump и не создаёт циклическую зависимость CRC от самого себя.

## Сборочная цепочка

`MK61_REQUIRE_RESIDENT_CRC=1` включается только публичными сборщиками. После
линковки `tools/seal-firmware.sh` или `tools/seal-firmware.ps1`:

1. находит ровно один структурно допустимый footer;
2. проверяет профиль, обязательный флаг, reserved и лимит Flash;
3. записывает точный размер, обнуляет CRC/content ID, вычисляет CRC;
4. записывает CRC и тот же content ID;
5. независимо пересчитывает результат и только затем заменяет выходной файл.

Этот шаг обязателен в строгой F411-матрице, Arduino F401 compile gate,
интерактивном сборщике, прямом F401/GCC builder и Arduino IDE board hook.
F401 System APP привязываются уже к запечатанному BIN. Прямой GCC builder
также повторно создаёт HEX из запечатанного BIN, поэтому BIN и HEX идентичны.
Обычная developer-сборка с `MK61_REQUIRE_RESIDENT_CRC=0` может оставаться
незапечатанной и запускаться под отладчиком.

## Последовательность загрузки

Сверхранний ESC проверяется первым в `.preinit_array` и по-прежнему может войти
в ROM DFU до Arduino/HAL и C++-конструкторов. При обычном старте `setup()`
инициализирует crash capture и DWT, затем читает footer через `volatile` и
потоково считает CRC непосредственно из внутренней Flash. `volatile` обязателен:
post-link sealer меняет исходно `const`-объект, и LTO не должен подставить его
нулевые значения из C++ initializer.

Проверка не создаёт копию образа в SRAM. Постоянная цена — 24-байтный failure
breadcrumb в `.noinit`; рабочий `CRC Context` и 40-байтный снимок footer лежат
на стеке только во время проверки. Один глобальный CRC arbiter общий с уже
существующими CRC данных и автоматически умеет перейти на software fallback,
если блок занят.

## Диагностика и измерения

Команда `df` печатает status, обязательность, длину/смещение footer,
expected/build/actual, backend и DWT cycles. На F411/96 МГц для WS0010 image
297768 байт десять аппаратных проходов дали 877043–880421 cycles, среднее
879064 cycles, то есть около 9,16 мс. Все три значения ID/CRC были
`2AB5F3C8`.

На F401 mini V3/A00 direct GCC+LTO получен image 239024 байт и RAM
47028/65536 байт. По отношению к зафиксированному baseline 47000 байт итоговая
разница составляет 28 байт; 24 байта принадлежат failure breadcrumb, остальные
4 байта — чистая разница выравнивания/размещения `.data/.bss` всего текущего
линка. Большого framebuffer или постоянного CRC-буфера нет.

Host-тесты проверяют обе реализации sealer побайтно, повторное запечатывание,
повреждение payload/content ID, duplicate footer и лимиты F401/F411. Build
policy test не позволяет публичному builder пропустить обязательный macro или
post-link проверку.
