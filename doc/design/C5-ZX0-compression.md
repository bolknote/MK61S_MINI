# Прозрачное сжатие файлов C5

Статус: RAW/ZX0 для C5 реализован; FMK2 оставлен отдельным этапом
Дата: 29.07.2026

Этот документ фиксирует выбранную архитектуру прозрачного сжатия файлов в C5.
Он дополняет текущее описание хранилища в
`doc/src/MK61s-mini-Storage.md` и описывает фактический формат новой
прошивки. Раздел про FMK2 фиксирует следующий этап, который ещё не включён.

## Краткое решение

C5 получает только два физических представления пользовательского файла:

- `RAW` — payload хранится без преобразования;
- `ZX0` — payload хранится одним потоком ZX0.

Общий C5-кодек RLE не вводится. LZSS не рассматривается. Сжатие APP внутри
контейнера остаётся отдельным форматом и не смешивается со сжатием C5.

Встроенный ZX0-кодировщик:

- не использует heap;
- имеет максимальное смещение 256 байт;
- при достаточном workspace выполняет bounded-optimal DP для новых offset;
- учитывает дешёвый last-offset при восстановлении пути;
- при меньшем workspace переходит на детерминированный greedy-разбор;
- работает с материализованным непрерывным входом;
- один раз готовит план и побитно одинаково выдаёт его для CRC и записи;
- сохраняет RAW, если ZX0 не даёт существенного выигрыша или доступного
  workspace недостаточно для безопасного разбора.

Сжатие полностью прозрачно для USB FAT, редакторов и обработчиков файлов:
внешний пользователь всегда видит исходные байты и логический размер.

## Цели

1. Уменьшить число записываемых и читаемых байтов SPI NOR.
2. Уменьшить заполнение data log, частоту GC и число erase.
3. Не добавлять второй буфер максимального размера файла.
4. Сохранить обычные расширения и содержимое файлов в USB FAT.
5. Поддержать как обычные C5 records, так и large storage.
6. Выполнять проверку CRC и распаковку одним проходом по flash.
7. Не ухудшить горячее фрагментарное чтение M61 до проведения отдельного
   эксперимента.

## Не входит в это решение

- внутреннее `NONE`/`ZX0` представление payload в `.APP`;
- сжатие каталогов, inode, WAL, locator, settings и USB staging;
- общий RLE-кодек C5;
- LZSS;
- произвольный seek внутрь единого ZX0-потока;
- совместимость старой прошивки с новыми сжатыми records.

## Термины и размеры

В C5 уже существуют разные размеры, их нельзя объединять:

| Значение | Место | Смысл |
| --- | --- | --- |
| `data_len` | inode | Логический размер, видимый API и USB после распаковки |
| `stored_len` | record header или large descriptor | Число физических байтов payload |
| `record_len` | inode | Полная длина малого record: header, имя и payload |

Для малого RAW-файла:

```text
stored_len = data_len
record_len = RECORD_HEADER_SIZE + name_len + data_len
```

Для малого ZX0-файла:

```text
stored_len = zx0_size
record_len = RECORD_HEADER_SIZE + name_len + zx0_size
```

`record_len` нужен каталогу и GC без дополнительного чтения record header.
`data_len` нужен для FAT directory entry, проверки выходной ёмкости и строгой
проверки результата ZX0.

Новых полей размера в inode добавлять не требуется.

## Представление в inode и record

Предлагаемый флаг:

```cpp
static constexpr u8 INODE_FLAG_LARGE_FILE = 0x01;
static constexpr u8 INODE_FLAG_ZX0       = 0x02;
```

Флаги независимы:

| `LARGE_FILE` | `ZX0` | Представление |
| ---: | ---: | --- |
| 0 | 0 | Малый RAW record |
| 0 | 1 | Малый ZX0 record |
| 1 | 0 | Большой RAW payload |
| 1 | 1 | Большой ZX0 payload |

Header и имя файла всегда остаются RAW. В поле длины малого record header
хранится `stored_len`. Для RAW оно совпадает с `inode.data_len`, для ZX0 —
нет. Проверка record должна учитывать флаг inode.

CRC record сохраняет нынешний смысл: он покрывает стабильные поля header, имя
и именно сохранённые физические байты. Декодер дополнительно проверяет
структуру ZX0 и точный логический размер.

## Выбор small или large

Логический размер не определяет способ размещения. Сначала выбирается RAW или
ZX0, затем по `stored_len` выбирается физическое хранилище.

```text
logical source
      |
      +-- оценка ZX0 --> выбор RAW/ZX0
                              |
                              +-- stored payload помещается в малый record
                              |       -> обычный data log
                              |
                              +-- не помещается
                                      -> large storage
```

Начальная безопасная граница малого payload — 1600 байт. Она гарантирует, что
record с максимальным именем и header сохраняет действующие ограничения data
log.

Логически большой файл может стать физически малым. Пример из корпуса:

```text
games/echo8.ch8:
RAW                 2039 байт, нынешний large storage
оптимальный ZX0     около 1,25 КиБ, помещается в малый record
```

Для large ZX0 descriptor должен хранить:

- логический `data_len`;
- физический `stored_len`;
- число физических блоков по `stored_len`;
- адреса этих блоков.

Единый ZX0-поток последовательно разбивается между large blocks. Отдельный
ZX0-stream на каждый блок в первой версии не используется.

## Политика типов

Начальная политика:

| Тип | C5 ZX0 | Причина |
| --- | --- | --- |
| FOCAL | Да | Загружается целиком |
| TinyBasic | Да | Загружается целиком |
| TEXT | Да | Обычно читается целиком |
| MK61_STATE | Да | Читается целиком |
| MARKDOWN | Да | Читается целиком |
| IMAGE1/WBMP | Да | Читается целиком |
| CHIP8 | Да, включая логические файлы больше 1600 байт | ROM загружается целиком, максимум 3584 байта |
| FONT | Пока нет | Включается только вместе с переходом на raw-only FMK2 |
| MK61 | Пока нет | Исполнитель запрашивает части по 64 байта |
| APP | Нет внешнего C5-сжатия | Контейнер имеет собственный `NONE`/`ZX0` |

Новый тип по умолчанию остаётся RAW, пока явно не определён его профиль
чтения.

## Решение о выгодности

Начальный порог:

- экономия не менее 64 байт;
- экономия не менее 10% логического payload.

Оба условия обязательны. Пустой файл всегда RAW.

Порог не является частью дискового формата и может быть изменён после
измерений на F401. Уже сохранённые ZX0 records от изменения порога не
зависят.

Нехватка workspace до начала записи считается допустимым RAW fallback.
Ошибка любого `emit()` после уже принятого решения ZX0 не считается RAW
fallback: операция записи завершается ошибкой. Сам `Prepared` остаётся
пригодным для повторного `emit()`, пока input и workspace не изменились.

## Кодировщик ZX0

Оптимальный host-кодировщик APP требует динамической памяти и не подходит для
F401. Для C5 реализован отдельный ограниченный кодировщик.

Требования:

1. Максимальное смещение — 256 байт.
2. Нет heap и больших постоянных таблиц.
3. Вход кодировщика непрерывен; `FileSource` при необходимости сначала
   материализуется в уже имеющийся scratch/cache.
4. Результат детерминирован.
5. Повторные `emit()` одного `Prepared` создают побитно одинаковый поток.
6. `prepare()` сообщает точный размер без пробной записи в sink.
7. `emit()` умеет писать в абстрактный sink:
   - RAM;
   - CRC;
   - flash writer.

При workspace не меньше `4 * (data_len + 1)` кодировщик хранит для каждой
позиции две 16-битные стоимости: продолжение literal и match. Это даёт точный
DP для новых offset в окне 256. Last-offset не входит в состояние DP, но при
равной стоимости предпочитается во время восстановления пути. Поэтому режим
называется bounded-optimal, а не полным оптимумом ZX0.

Если workspace меньше, используется greedy-разбор. Он нужен прежде всего для
максимального CHIP-8 на F401: 8 КиБ недостаточно для полного DP на 3584
логических байта, но достаточно для устойчивого greedy-плана.

`prepare()` один раз строит DP/greedy-план, восстанавливает токены и формирует
control bytes прямо в workspace:

```text
materialized source -> bounded-optimal/greedy plan -> tokens + controls
```

После него без записи в sink известны `stored_len`, режим кодировщика, record
layout и решение RAW/ZX0. Если выбран RAW, подготовленный план просто
отбрасывается.

Если выбран ZX0, `Prepared` сохраняет ссылки на неизменяемые input и workspace.
Каждый `emit()` только воспроизводит уже подготовленный поток и не запускает
DP/greedy повторно:

```text
Prepared tokens + controls -> CRC / RAM / SPI NOR
```

Для small record готовый поток сохраняется одним `emit()` в свободном scratch,
если он доступен. Иначе первый `emit()` считает CRC, а второй пишет тот же поток
прямо во flash. Large ZX0 использует один `emit()` в large blocks. Второго
буфера размером с максимальный файл нет. Input и workspace остаются
зарезервированными и неизменными до последнего `emit()`, в том числе если
между CRC и записью запускается GC.

Совместимая обёртка `encode()` оставлена для тестов и одиночных вызовов; внутри
она выполняет `prepare()` и один `emit()`.

Во время USB commit грязные сектора уже находятся в устойчивом staging
journal. Поэтому чистый sector cache можно временно разделить на непрерывный
вход и workspace. На графической плате дополнительно одалживается внешний
8-КиБ кеш; на LCD1602 используется primary cache, а обычная запись из RAM
имеет локальный 1024-байтный greedy fallback. Перед GC lease
`shared_scratch` можно не освобождать: GC обходит inode пакетами прямо из
каталога и больше не занимает общий буфер. Поэтому сохранённый payload rename
и перенос records не могут взаимно заблокироваться.

### Качество bounded-кодировщика

На использованном корпусе файлов:

| Вариант | Размер | От RAW |
| --- | ---: | ---: |
| RAW | 18 311 | 100% |
| встроенный bounded ZX0, окно 256 | 11 083 | 60,526% |
| desktop optimal ZX0, окно 256 | 10 676 | 58,304% |

Встроенный результат больше desktop-optimal на 3,81%. Это заметно лучше
проверенного ранее LZSS (около 64,8% от RAW), поэтому отдельный LZSS-кодек не
нужен.

## Полное чтение

`read_id()` использует тот же строгий range-декодер, что и `read_range_id()`,
с диапазоном от нуля до полного логического размера. Это оставляет один
проверяемый C5-путь чтения; декодер держит 256-байтную кольцевую историю.

Один проход одновременно:

1. читает не более `stored_len` физических байтов;
2. считает CRC сохранённого payload;
3. распаковывает ровно `data_len` байт;
4. проверяет ZX0 end marker;
5. проверяет точное потребление `stored_len`;
6. сравнивает CRC.

Предварительный `verify_record_crc()` для ZX0 не выполняется: CRC физических
байтов считается тем же reader, который подаёт поток декодеру.

## `read_range()`

В единый ZX0-поток нельзя безопасно перейти по произвольному физическому
смещению: match ссылается на уже распакованные байты. Поэтому сжатый
`read_range(offset, length)` начинает декодирование с логического нуля.

Используется range target с кольцевой историей 256 байт:

```text
stored ZX0
    |
    v
decoder from logical offset 0
    |
    +-- последние 256 байт -> ring history
    +-- output < offset    -> отбросить
    +-- требуемый диапазон -> скопировать вызывающему
    +-- остальной output   -> продолжить для CRC и строгого конца
```

Алгоритм:

1. Проверить inode, header, `data_len`, `stored_len` и границы запроса.
2. Создать физический reader payload.
3. Инициализировать CRC стабильными полями record и именем.
4. Декодировать поток с начала.
5. Каждый полученный байт заносить в ring history.
6. Копировать только пересечение с запрошенным диапазоном.
7. Продолжать до end marker даже после заполнения результата.
8. Проверить логическую длину, физическое потребление и CRC.

История не занимает `shared_scratch`: во время USB-сеанса он используется
секторным кешем. В реализованном пути это локальный 256-байтный массив.
Статическая проверка F401-кода показывает около 2024 байт суммарных
stack-frame на самом тяжёлом пути записи (включая 1024-байтный fallback и
`emit()`), на 432 байта меньше прежней реализации. Аппаратный high-water тест
всё ещё полезен перед релизом.

Для малого record физический reader читает непрерывный участок data log. Для
large storage тот же интерфейс преобразует физический offset ZX0-потока в
блок и смещение внутри блока. Сам ZX0-декодер не знает о размещении.

### Стоимость диапазонного чтения

Стоимость одного compressed `read_range()` — `O(data_len)`, а не `O(length)`.
Для нынешних размеров это допустимо:

- CHIP-8 — не более 3584 байт;
- остальные выбранные типы — около 1600 байт.

Нынешний RAW `read_range_id()` уже читает весь record для CRC перед отдельным
чтением диапазона. Новый ZX0-путь заменяет это одним проходом по меньшему
физическому payload и добавляет работу CPU.

USB читает секторами по 512 байт. Для максимального CHIP-8 это не более семи
range-вызовов и примерно 25 КиБ логически декодированных данных в простейшем
варианте. Это нужно подтвердить измерением, но порядок величины мал для
84-МГц F401.

### Почему MK61 пока RAW

`m61_text` использует кеш всего 64 байта и может многократно обращаться к
одним и тем же участкам сценария. Повторный ZX0-проход с начала станет горячей
операцией.

Если позже понадобится сжатие MK61, рассматриваются отдельно:

1. независимые restartable ZX0-блоки по 256 или 512 логических байт;
2. кеш состояния последовательного декодера;
3. загрузка полного сценария в отдельный RAM-буфер.

Первый вариант даёт настоящий произвольный доступ, но требует таблицы блоков,
теряет межблочные совпадения и не относится к первой версии.

## CRC, повреждения и атомарность

Запись сохраняет нынешний C5-порядок:

1. определить формат и физическую длину;
2. зарезервировать место;
3. записать record в состоянии `WRITING`;
4. записать и аппаратно проверить header, имя и payload;
5. перевести record в `ACTIVE`;
6. опубликовать новый inode COW-транзакцией.

При сбое питания незавершённый record не публикуется.

Чтение ZX0 считается успешным только при одновременном выполнении всех
условий:

- record header согласован с inode;
- CRC сохранённых байтов совпадает;
- все offset ZX0 находятся в разрешённом окне;
- декодер выдал ровно `data_len`;
- декодер потребил ровно `stored_len`;
- присутствует корректный end marker;
- отсутствует физический хвост.

Повреждённый поток не должен возвращать частично подтверждённые данные как
успешный результат.

## GC, rename и сравнение содержимого

GC переносит сохранённые физические байты без распаковки и сохраняет флаги
inode. Это относится и к малым records, и к large blocks.

Rename не должен распаковывать и повторно сжимать payload. Он создаёт новый
header и имя, переносит `stored_len` байт как есть и пересчитывает CRC record.

Оптимизация «новое содержимое совпадает со старым» сравнивает логические
байты. Реализация читает старый ZX0 диапазонами и сравнивает с повторяемым
`FileSource`; одинаковая запись не создаёт новую версию и не программирует
flash. Это пока `O(n²)` по объёму декодирования, потому что каждый диапазон
начинается с логического нуля. Максимальные файлы малы, а корректность и
сохранение no-op семантики здесь важнее; при необходимости это можно заменить
одним compare-target проходом без изменения формата.

## FONT и отказ от внутреннего RLE

Этот раздел описывает следующий, ещё не реализованный этап. Текущая прошивка
продолжает читать FMK1 с per-glyph RLE/RAW и хранит FONT в C5 как RAW.

Целевой формат FONT — raw-only FMK2:

- bitmap каждого глифа хранится сырыми битами;
- per-glyph mode bit удалён;
- внутреннего RLE нет;
- весь FMK2 сжимается общим C5 ZX0;
- после загрузки глифы читаются без повторной RLE-распаковки.

Это требует нового content magic (`FMK2`) или другого однозначного признака
формата. Повторное использование семантики `FMK1` без mode bit запрещено.

### Эксперимент

Проверены четыре системных шрифта:

- Arial;
- Courier New;
- Monaco;
- SF Mono.

Использованы 13 конфигураций, помещающихся в нынешний логический лимит:
моноширинные и пропорциональные 5x8, 6x10 и 8x12, ASCII и
ASCII с кириллицей.

Все текущие FMK1 проверены firmware-парсером. Для гипотетического FMK2
проверена логическая идентичность метрик и bitmap. Каждый ZX0-поток прошёл
обратную распаковку.

Основной результат для оптимального host ZX0 с окном 256:

| Представление | Суммарный размер | От нынешнего auto-RLE |
| --- | ---: | ---: |
| FMK1 RAW | 14 405 | 107,6% |
| Нынешний FMK1 auto-RLE | 13 387 | 100% |
| FMK1 RAW -> ZX0-256 | 11 025 | 82,4% |
| FMK1 auto-RLE -> ZX0-256 | 12 112 | 90,5% |
| FMK2 raw-only без mode bit -> ZX0-256 | 9 625 | 71,9% |

Raw-only FMK2 с внешним ZX0 победил во всех 13 случаях.

Влияние окна на raw-only FMK2:

| Максимальное смещение | От raw-only FMK2 |
| ---: | ---: |
| 128 | 70,3% |
| 256 | 67,9% |
| 512 | 64,5% |

Окно 256 выбрано как начальный компромисс между размером и workspace
`read_range()`. Для FONT окно 512 выгоднее, но отдельный параметр окна в
дисковый формат пока не вводится.

Причина преимущества не сводится к удалению примерно одного бита на глиф.
Mode bit сдвигает последующие bitmap относительно байтовых границ и ухудшает
поиск повторяющихся фрагментов между похожими глифами. В raw-only потоке ZX0
видит сходство разных символов.

### Большие логические FMK2

Некоторые пропорциональные 8x12-шрифты после удаления RLE имеют логический
размер 1590--1745 байт, хотя их физический ZX0 занимает 1154--1260 байт.
Нынешний путь сначала читает FONT в 1600-байтный `shared_scratch`, поэтому
одного изменения формата недостаточно.

Активный шрифт уже хранится в `exclusive_buffer` размером 8192 байта.
Установка FMK2 должна:

1. заранее захватить `exclusive_buffer`;
2. распаковать C5 непосредственно в него;
3. открыть `fmk::Face` на окончательных байтах;
4. не делать промежуточную копию через `shared_scratch`.

Точный новый логический лимит FONT нужно выбрать после проверки preview,
USB-сессии и остальных владельцев `exclusive_buffer`.

Целевой вариант удаляет поддержку RLE из firmware и converter. Существующие
FMK1 с RLE потребуется пересобрать в FMK2. Если будет принято решение читать
старые FMK1, RLE-декодер останется в resident и часть выигрыша от упрощения
исчезнет.

## Совместимость C5

Новый firmware продолжает читать старые RAW records: отсутствие
`INODE_FLAG_ZX0` однозначно задаёт нынешнее представление.

Переформатирование C5 только ради сжатия не требуется. Reserved inode flags и
раздельные `data_len`/`record_len` уже позволяют расширение.

Старая прошивка не обязана читать новые ZX0 records. Она может увидеть том, но
не должна молча трактовать compressed payload как исходный файл. При
реализации нужно проверить mount validation и добиться явного отказа на
неизвестном флаге.

## Проверки

### Codec tests

- RAW и ZX0 round-trip для размеров 0..максимума каждого типа;
- побитная идентичность повторных `emit()`;
- неизменность workspace во время `emit()` и повтор после ошибки sink;
- offset 1, 127, 128, 255 и 256;
- overlapping matches;
- literal-only и incompressible данные;
- усечённый поток;
- неверный end marker;
- offset больше 256;
- лишний физический хвост;
- неверный логический размер;
- повреждение каждого байта короткого потока.

### Program store tests

Реализованы и входят в `tests/run_all_tests.sh`:

- чтение прежних RAW records и legacy large descriptor v1;
- small ZX0, large ZX0 и логически большой CHIP-8, ставший small;
- замена такого small ZX0 CHIP-8 при полностью занятой квоте inode с
  переиспользованием его логических FAT-extents;
- диапазоны в начале, середине, конце и через границу large block;
- rename с сохранением физических ZX0-байтов;
- rename, который прямо во время операции запускает GC и стирает сектор
  исходной ZX0-записи;
- no-op запись по логическому содержимому;
- USB import/readback как с внешним 8-КиБ кешем, так и с primary cache;
- детерминированный mixed-order churn: RAW, small ZX0 и large ZX0,
  write/replace/rename/delete, периодический reboot и полная сверка с RAM
  model;
- контроль верхней границы page-program/erase amplification в churn;
- перебор обрыва после каждой flash mutation при замене small и large ZX0:
  после reboot должна читаться целиком старая либо целиком новая версия,
  затем повторная запись обязана завершиться;
- существующие GC power-cut тесты, теперь работающие и при наличии ZX0.

Отдельные targeted corruption-тесты для каждого поля inode/header/descriptor
ещё стоит расширить; общий отказ на неверных флагах, CRC, длинах и ZX0-tail
уже проверяется codec/store тестами.

### Target measurements

На STM32F401 ещё нужно измерить на реальном устройстве:

- циклы bounded/greedy encode;
- циклы полного decode;
- циклы range decode;
- stack high-water;
- физические прочитанные и записанные байты;
- число page program;
- число erase/GC на серии обновлений;
- время editor save;
- время USB commit;
- время последовательного USB read;
- время загрузки CHIP-8.

Диагностический host-бенчмарк не заменяет эти измерения, но подтверждает
архитектурный эффект. Для трёх последовательных выдач одного потока на корпусах
1536, 3584 и 4095 байт переиспользование `Prepared` ускорило кодирование в
7,8–12,2 раза. Инкрементальный расчёт gamma-cost сам по себе дал 2,2–3,0 раза.
Размер и 64-битный hash ZX0-потока во всех трёх случаях совпали с реализацией до
оптимизации. Отдельный дифференциальный прогон старого и нового кодировщиков на
2120 сочетаниях размера, структуры данных и bounded/greedy workspace также не
нашёл ни одного отличающегося потока.

Проверенная сборка `mini-v3-a00`, LTO + CORE math:

```text
mini-v3-a00 resident text = 190952 bytes
mini-v2-a00 resident text = 191000 bytes
resident data             =   2292 bytes
resident bss              =  50896 bytes
FOCAL.APP SRAM            = 19464 / 20480 bytes
```

Для mini-v3 добавка относительно того же HEAD без C5 ZX0 составляет 6240
байт `.text` и 8 байт `.bss`. Это проверка компоновки, а не измерение скорости
или аппаратного stack high-water.
