# System APP ABI 4

Все APP используют [общий публичный API](APP-SERVICES.md). Этот документ
описывает адаптеры существующих модулей и их жизненный цикл. Старое имя
System API осталось для совместимости исходников и уже выпущенных APP.

FOCAL, BASIC, WBMP, Markdown, CHIP-8 и SETUP используют тот же контейнер ABI 4,
что и пользовательский `main()`: 64 байта заголовка, виртуальная база
`0x20000000`, максимум 20 КиБ образа вместе с BSS, ZX0 или BCJ + ZX0.
Поля 40/44 задают размер сжатого образа и число релокаций.
Фактический адрес выбирает загрузчик сверху свободной SRAM, ниже защиты
стека; арендуется размер образа и BSS с выравниванием 32 байта. Постоянного
20-КиБ резерва нет. Имена и числовые команды System APP
сохранены; формат C5 и исходные программы языков не меняются.

## Инициализация и состояние

При загрузке System APP загрузчик вызывает:

```c
entry(INITIALIZE, (uint32_t)system_api, (uint32_t)app_api, image_crc32, 0);
```

`app_api` — публичная таблица `code/loadable_app_api.h`, версия 1:
прежний префикс 104 байта и добавленный `query_service`, всего 108 байт.
Новые адаптеры получают сервисы через `mk61_app_get_services(app_api, 0)`.
`system_api` передаётся для совместимости со старыми APP; это та же
28-байтовая таблица версии 1. `code/loadable_system_api.h` содержит алиасы
к публичным определениям `code/loadable_app_services.h`.
Новые адаптеры требуют `query_service` и не обращаются к прежнему аргументу.
Запуск новых APP на старых прошивках не поддерживается.
При несовместимом magic/version/size или отсутствии обязательной функции
APP возвращает ошибку, и загрузчик запрещает запуск.

`INITIALIZE` с ненулевым первым аргументом только подключает таблицы.
Явный `INITIALIZE(0, 0, 0, 0)` сбрасывает состояние FOCAL/BASIC, как раньше.
Загрузчик сохраняет образ System APP между командами; после вытеснения
заново восстанавливает его `.data`/BSS. Пользовательский APPLICATION по-прежнему
получает свежие `.data`/BSS при каждом запуске.

Программы и переменные языков находятся в прежней workspace-арене, отдельно
от кода. Резидентные аренды сохраняют и восстанавливают её через существующий
механизм обмена. CRC образа языка служит дополнительным ключом совместимости:
после установки другой версии APP прежний снимок интерпретатора сбрасывается.
Сохранённые файлы исходных программ при этом не удаляются.

Как и до переноса, обмен работает только в RAM: один неактивный runtime
сжимается в общую арену BULK. Это позволяет менять FOCAL и BASIC местами,
пока снимки помещаются. Третий потребитель workspace или занятие BULK
может вытеснить снимок; тогда переменные сбрасываются. Это кэш состояния,
а не постоянное хранение всех запущенных программ.

## Сервисы

Таблица предоставляет дисплей и клавиатуру, C5 и файловые диалоги, аренду
workspace/scratch, редактор, меню, встроенные шрифты, регистры МК‑61,
арифметику и форматирование. Структуры пересекают границу только в описанном
C-виде. Объекты `MK61Display`, `program_store::Entry` и C++-аренды прошивки
не передаются приложению. В командах WBMP объект файла заменён его C5 id;
дисплей всегда выбирает прошивка.

`sdk/portable/system` адаптирует прежние исходники к этому API. Фасады
внутри APP не содержат адресов C++-объектов прошивки. Обработчик редактора
сериализует буфер/клавиши/режимы, а языковые макросы вызывает обратно через
C-callback. Сохраняются родной алгоритм SMS-ввода и аппаратный сдвиг LCD.

Стандартные ARM EABI-функции для `double`, 64-битного деления и часть ISO C
строковых функций имеют отдельную таблицу. Порядок задаётся единственным
`code/loadable_system_runtime.def`; ассемблерные переходники сохраняют
исходное соглашение вызова, включая два результата `__aeabi_uldivmod`.
Это исключает копии libgcc из крупных языковых APP. Трансцендентные функции
используют настроенный математический backend прошивки.

`MK61_SYS_SETUP=25` сохраняет прежний номер. Операция
`MK61_SERVICE_CAPABILITIES=26` возвращает доступные группы сервисов.
Прежние номера и размер таблицы сервисов (28 байт) сохранены;
публичный API расширен со 104 до 108 байт только в конце.
SETUP сначала проверяет версию сервиса (1). Через него доступны снимок
оборудования, RTC, калибровка, профиль и предпросмотр шрифта. Реальный
дисплей, часы, сохранение настроек и диагностические фазы остаются в resident.
Один SETUP работает с обеими раскладками и обычными/расширенными настройками
шрифта; возможности запрашиваются во время выполнения.

`MK61_SETUP_FEATURES` возвращает маску: `0x01` — совместимые настройки
моноширинной текстовой поверхности, `0x02` — их расширенные параметры,
`0x04` — независимый шрифт UI (`MK61_SETUP_UI_FONT_READ/APPLY`),
`0x08` — доступное сейчас переключение в живой UI-контекст физического
дисплея (`MK61_SETUP_TEXT_MODE`), `0x10` — отдельный фиксированный индикатор
калькулятора, `0x20` — каталог `Fonts/*.FMK` и операции выбора по имени.
Флаги имеют имена `MK61_SETUP_FEATURE_*` в общем C-заголовке.
Флаг `0x10` выдаёт каждая прошивка UC1609, включая F401: тип основного
индикатора определяется экраном, а не моделью STM32.
Флаги `0x04` и `0x08` доступны только на F411/UC1609; `0x04` описывает наличие
API и остаётся установленным в USB Screen,
а `0x08` снимается на время USB Screen с моноширинной отрисовкой.
Операции добавляются в конец enum без изменения прежних номеров;
`TEXT_MODE` следует за `UI_FONT_APPLY`, а каталог занимает append-only номера
17–21 (`UI_FONT_COUNT`, `UI_FONT_ITEM`, `UI_FONT_CURRENT`,
`UI_FONT_APPLY_ITEM`, `UI_FONT_STEP`).
Для `TEXT_MODE` аргумент `a=0` выбирает обычный моноширинный контекст,
`a=1` — контекст UI; успешный вызов возвращает 1. При активном USB Screen
`a=1` возвращает 0 без смены контекста, а `a=0` по-прежнему доступен.
Другие значения `a` и все вызовы на других дисплеях возвращают 0.
`b` и `payload` не используются.
Операция меняет только контекст отрисовки, не настройки шрифтов и не их
сохранение. Вызывающий код восстанавливает нужный контекст после предпросмотра.
На физическом UC1609 экран выбора начинает с семейства UI. `5x8` имеет
единственный фиксированный растр, а нативный Ark Pixel — размеры 12/14/16.
Каждый непосредственный файл `Fonts/*.FMK` является отдельным пунктом с
собственной высотой 12/14/16 и названием из имени файла без расширения; у него
нет отдельного поля размера.
OK меняет выбранное значение, обычные стрелки переходят между полями; UI-шрифт
виден сразу на выровненном нижнем образце. На UC1609 индикатор
калькулятора является отдельной фиксированной ролью и через этот API не
настраивается.

`UI_FONT_COUNT` возвращает число прошедших предварительную проверку файлов.
`UI_FONT_ITEM` принимает индекс в `a` и заполняет 40-байтовый
`mk61_setup_ui_font_item`: стабильный `key`, высоту `size` и нуль-завершённое
`name[32]`. `UI_FONT_CURRENT` заполняет тот же объект для активного внешнего
пункта. `UI_FONT_APPLY_ITEM` принимает `key` в `a`, заново находит и полностью
проверяет файл, применяет его и помечает настройки изменёнными. Индекс служит
только для перечисления; сохраняется ключ имени, поэтому перестройка каталога
не меняет выбор. Неизвестный/неоднозначный ключ, неверная высота, CRC или тело
FMK возвращают 0 и не выбирают случайный файл.
`UI_FONT_STEP` за один линейный проход возвращает в `payload` следующий
(`b=1`) или предыдущий (`b=UINT32_MAX`) пункт относительно ключа `a`; `a=0`
означает первый/последний пункт. Экран настроек использует эту операцию вместо
повторного получения и сортировки всего списка при каждом нажатии.

Не сохраняйте адреса кода или BSS APP в workspace между выгрузками.
Перемещение FOCAL → BASIC → FOCAL по разным адресам входит в ARM-тест.

## Сборка и варианты

```sh
python3 tools/build_portable_app.py --system focal \
  --arm-toolchain-bin /path/to/arm-gcc/bin --output-dir .build/FOCAL
python3 tools/build_portable_app.py --system markdown-viewer --text-only \
  --arm-toolchain-bin /path/to/arm-gcc/bin --output-dir .build/MARKDOWN
```

Сборщик не читает resident ELF/BIN. Он проверяет отсутствие неразрешённых
символов, глобальных конструкторов, потерянных ELF-секций и превышения
лимита 20 КиБ для образа вместе с BSS. Сохраняется прежний порог кадра стека
System APP — 5120 байт;
анализ выполняется отдельной компиляцией и не меняет выпускаемый образ.
Рядом с APP остаются ELF, BIN, MAP, JSON размеров и отчёт стека.

По умолчанию Markdown включает графику и WBMP, а при символьном дисплее
умеет показать текст. `--text-only` убирает графический компилятор документа
и WBMP для меньшего файла. Комплектные сборщики выбирают вариант по
возможностям целевой прошивки. Остальные APP одинаковы для раскладок
Classic/Mini; соответствие клавиш приходит из таблицы прошивки.

## Исторические размеры ABI 3

Текущие размеры, стоимость загрузчика и запас F401: [ABI 4](RELOCATION-RESULTS.md).

GCC 14.2.1, `-Oz`, LTO, 05.09.2026. Размер файла включает 64-байтовый
заголовок; во всех шести вариантах упаковщик выбрал BCJ + ZX0.

| Модуль | APP, байт | Образ + BSS в SRAM, байт |
| --- | ---: | ---: |
| FOCAL | 13 620 | 20 140 |
| BASIC | 11 522 | 17 252 |
| WBMP | 1 616 | 1 924 |
| Markdown с графикой | 12 080 | 15 324 |
| Markdown только текст | 3 812 | 4 652 |
| CHIP‑8 | 2 563 | 3 356 |

В этих сборках ABI 3 окно APP составляло 20 480 байт; стек и workspace
в эти числа не входили. У FOCAL оставалось 340 байт окна; максимальный
измеренный кадр стека составлял 4896 байт при лимите 5120.

При контрольной сборке режимов ABI 2/3 на исходниках после переноса
для одинакового профиля `mini-v3-a00` (F401, FOCAL/BASIC/текстовый Markdown,
математическое ядро CORE) резидент ABI 2 занимает 235 452 байта, ABI 3 —
240 020 байт: переход добавляет **4568 байт Flash**. Статическая RAM в обоих
случаях — 47 108 байт. FOCAL.APP стал меньше на 366 байт, BASIC.APP — на 276,
текстовый MARKDOWN.APP вырос на 481 байт. Это сравнение всей конфигурации,
включая загрузчик, API и оптимизации линковки; у других профилей цена отличается.
Все восемь конфигураций F401 проходят прежние бюджеты. Минимальный остаток
Flash среди них — 536 байт при обязательных 512.

Сравнение с настоящим коммитом **до** переноса, включая все пять модулей,
оба Markdown, SRAM и отдельный эффект BCJ, приведено в
[SIZE-COMPARISON.md](SIZE-COMPARISON.md). Это другая исходная точка,
поэтому размеры старого resident и сжатых ABI 2 могут отличаться.

## Проверки

`tests/run_portable_app_tests.sh` проверяет C/ARM layout структур, все виды
контейнеров, CRC, ZX0/BCJ, BSS, чтение формата прежних ABI 2/3,
повреждённые релокации и разные адреса. Исполняющий загрузчик без резерва
принимает только ABI 4; поддержка чтения старого формата в инструментах
не означает разрешения его установки или исполнения.
`tests/run_portable_system_arm_tests.py` исполняет шесть APP по трём адресам на двух реальных
ELF прошивок. Для этого набора нужны отдельные тестовые сборки с
`MK61_MATH_BACKEND=0` (LIBM), с таблицей символов ELF. Арифметика, форматирование,
шрифты и обработчик клавиш редактора тоже исполняются из прошивки.
Периферия/C5 и хранение снимков workspace имитируются.
Инициализация ядра калькулятора и STM32 bit-band в этой модели отсутствуют;
CORE-сборка поэтому отклоняется до запуска тестов. Продуктовый backend менять
не нужно: настоящие вычисления CORE и сохранение состояния отдельно проверяет
`tests/run_mk_math_tests.sh` с таблицами во Flash и вытесняемой SRAM.
Отдельный режим `--ui-only` разрешает точные продуктовые CORE-сборки: только
трансцендентное выражение BASIC заменяется обычной арифметикой, остальные
проверки сохраняются. Результат явно помечается как квалификация UI, а не
полный прогон математического набора.
Проверяются вычисления, переключение языков, возврат состояния, редакторы,
точные WBMP-пиксели, Markdown, CHIP-8 и служебные экраны SETUP, границы
выделенного блока и сохранение регистров.

Полный набор host-тестов запускается с ASan/UBSan. Комплектные сборщики
используют общий SDK; проверка актуального ABI 4 описана в отчёте выше.

Предыдущие пять модулей ABI 3 проверены на физическом F411: см.
[аппаратный отчёт 2026-09-06](HIL-2026-09-06.md). Он включает вычисления,
обмен переменными FOCAL/BASIC, редакторы и запись файлов, пиксели,
повреждённые APP и побайтовую сверку установленной прошивки.
Исторический `HIL-2026-09-05.md` относится к эксперименту HELLO/CHECK/WBMP.
