# Блочные буферы и PSRAM для APP

PicoCalc 0.8.14 предоставляет необязательный сервис `MK61_SERVICE_BUFFER`.
ABI APP остаётся 6, версия общей таблицы — 2. Существующие `MEMORY_ACQUIRE`,
`MEMORY_DATA`, `malloc`, стек и прямые указатели сохраняют прежнее поведение.
Старые прошивки и STM32, не объявляющие новую возможность, возвращают отказ;
приложение проверяет capability до вызова. Старые APP продолжают работать.

`MK61_SERVICE_CAP_BUFFERS` означает наличие блочного API,
`MK61_SERVICE_CAP_EXTERNAL_BUFFERS` — доступный внешний backend.
На PicoCalc используется общий диспетчер `shared_memory::Buffer`:

| Режим | Размещение | Указатель из INFO |
|---|---|---|
| `MK61_BUFFER_DIRECT` | SRAM | Прямой указатель |
| `MK61_BUFFER_BLOCK` | PSRAM, при отсутствии/нехватке — SRAM | `NULL` для PSRAM |
| `MK61_BUFFER_EXTERNAL` | Только PSRAM | `NULL` |

Новый буфер содержит неинициализированные байты. Обязательный блок может
вытеснить необязательные VM/SD-кеши. Другие обязательные блоки сохраняются.
Текущая реализация допускает четыре буфера и два окна на одно выполнение APP.

```c
const mk61_app_services* s = mk61_app_get_services(mk61_api,
    MK61_SERVICE_CAP_BUFFERS);
mk61_service_buffer buffer = mk61_app_buffer_request();
if (s && mk61_app_buffer_acquire(s, 12800, MK61_BUFFER_BLOCK, &buffer)) {
    uint8_t bytes[512] = {0}; /* заполнить данные */
    /* Передавать не более MK61_BUFFER_IO_BYTES за вызов. */
    mk61_app_buffer_write(s, buffer.handle, 0, bytes, sizeof(bytes));
    mk61_app_buffer_read(s, buffer.handle, 0, bytes, sizeof(bytes));
    mk61_app_buffer_release(s, buffer.handle);
}
```

Каждый вызов возвращает 1 при успехе и 0 при отказе. Для общего вызова
`services->call(MK61_SERVICE_BUFFER, operation, 0, sizeof(request), &request)`
используется `mk61_service_buffer`; поля описаны рядом со структурой
в `code/loadable_app_services.h`. C helpers находятся в `mk61_app.h`,
Rust `repr(C)`-структура и константы — в `sdk/portable/rust/mk61_app.rs`.

READ/WRITE/FILL и WINDOW_OPEN ограничены 4096 байтами на вызов. Длинные
операции разбиваются на порции; между ними APP вызывает `mk61_api->service()`
для обработки клавиатуры и USB. Границы проверяются с защитой от переполнения.
FILL заполняет диапазон значением `flags` от 0 до 255.

WINDOW_OPEN копирует диапазон в SRAM, возвращает `window` и `data`, закрепляя
родительский буфер. `MK61_BUFFER_WINDOW_WRITABLE` разрешает явный
WINDOW_COMMIT; ошибка записи возвращается вызывающему коду. WINDOW_CLOSE
отбрасывает несохранённые изменения. RELEASE при живом окне отказывает.
Изменение копии окна для чтения не меняет исходный блок.

Все буферы и окна принадлежат одному выполнению APP. При возврате они
освобождаются автоматически, сначала окна, затем блоки. Идентификаторы
не переиспользуются: старый handle нельзя применить к новому выполнению APP.
Прямые указатели живут только до освобождения соответствующего буфера/окна.

## Кадры в PSRAM

В нативном режиме 320×320 APP может подготовить несколько монохромных кадров
в одном внешнем буфере. Каждый кадр занимает 12800 байт в том же страничном
LSB-формате, который принимает `graphics_present`.

После `graphics_begin()` запрос PRESENT с `handle`, `offset` и `size=12800`
копирует готовый кадр порциями в существующий заимствованный буфер дисплея
и публикует его целиком. Дополнительного полного SRAM-кадра нет. Если чтение
PSRAM завершилось ошибкой, публикуется пустой кадр вместо частичного.
Проверка параметров до копирования не меняет экран. Старый режим APP 192×64
использует прежний `graphics_present`; PRESENT в нём возвращает 0.

LCD продолжает выводить изменившиеся области через две SRAM-строки и DMA.
Физическая PSRAM не отображена в адресное пространство RP2040, поэтому
контроллер DMA не получает прямой указатель на неё.

`tests/picocalc_buffer_probe.cpp` — пример настоящего APP: обязательные 6 МиБ,
окно с commit, проверка границ, две страницы в PSRAM и автоматическое
освобождение при возврате. `tests/hil_picocalc_app_buffers.py` проверяет
три показанных кадра по независимому эталону и CRC источника LCD DMA.
