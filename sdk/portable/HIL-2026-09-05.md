# Portable APP: аппаратное испытание 2026-09-05

Результат: один набор APP без пересборки прошёл полный прогон на двух
экспериментальных прошивках физического МК61. Исходная прошивка и все
пользовательские файлы восстановлены и проверены.

## Прибор и сборки

Classic V3, UC1609 192×64, STM32F411CE, 128 КиБ SRAM, 512 КиБ внутренней
Flash; C5 на внешней NOR EF3013 объёмом 512 КиБ. Public ID прибора:
`AEB505B6E0067623`. Исходный build: `4AC27AA8`.

Resident собран Arduino CLI с STM32 Core 2.12.0, xPack ARM GCC 14.2.1,
FQBN `STMicroelectronics:stm32:GenF4:pnum=BLACKPILL_F411CE,upload_method=dfuMethod,xserial=none,usb=CDCgen,opt=osstd`.
Обе сборки включают `MK61_ENABLE_PORTABLE_APPS=1`,
`MK61_ENABLE_LOADABLE_MODULES=1`, `MK61_ENABLE_USB_SCREEN=1`,
`MK61_REQUIRE_RESIDENT_CRC=1`, `MK61_BOARD_CLASSIC_V3`.
TinyBasic, Markdown, штатный WBMP и CHIP-8 выключены; math backend — 0.
Различие между сборками — FOCAL: 0 в A, 1 в B.

Для этой лабораторной F411-сборки штатный linker script варианта
`STM32F4xx/F411C(C-E)(U-Y)` преобразован
`tools/.mk61-gcc/portable-layout.py`; Arduino `build.ldscript` указывает
на полученный файл относительно каталога варианта. Overlay занимает
`0x20000000..0x20005000`. MPU использует 4/8 областей, сохраняет запрет
исполнения остальной SRAM и 256-байтовую защиту 16-КиБ стека.
В штатную Arduino/release-матрицу эта конфигурация не добавлена.

| Параметр | A | B |
| --- | --- | --- |
| Build / CRC | `07143BAB` | `315ECCED` |
| Запечатанный BIN, байт | 283164 | 301020 |
| `api_file_read`, адрес кода | `0x0800AE80` | `0x0800AF7C` |
| `api_graphics_present`, адрес кода | `0x0800AE5C` | `0x0800AF58` |
| `api_graphics_begin`, адрес кода | `0x0800AE70` | `0x0800AF6C` |

Адреса приведены из ELF; Thumb-указатели в таблице API имеют установленный
младший бит. Переносимость проверялась при реальном изменении адресов функций.

## Установленные APP

Приложения собраны отдельным `tools/build_portable_app.py`, без resident
ELF/BIN. Все файлы установлены в созданный для опыта `/PAPPTEST`; после
замены A на B каждый файл прочитан обратно и сравнен с предыдущей копией.

| APP | Байты | Сжатие | SHA-256 |
| --- | ---: | --- | --- |
| HELLO | 204 | ZX0 | `ffc0e317f5a7675cd2d483d8b9b8f71d3535d2b09e4086a016cbdf44e600879d` |
| CHECK | 297 | ZX0 | `7d7acc8cf98f94282487dcad83ce79b593061a6b2ba66fb1d6bcfe05404bd430` |
| WBMP | 893 | ZX0 + BCJ | `f9651f94a14edd8c402d62eb5869e459ca988e15f1f15124a37a8381538e0528` |

Полный повторяемый прогон использует CHECK и WBMP. CHECK написан на C,
проверяет начальное значение `.data` и всё своё BSS, меняет их и рисует
контрольный кадр. При ошибке он рисует другое изображение, поэтому тест
не зависит от того, показывает ли терминал код возврата `main()`.

## Проверки на каждой прошивке

- Десять последовательных запусков CHECK и ещё один после WBMP: каждый
  раз весь кадр совпал с эталоном, включая повторную инициализацию данных.
- Три открытия WBMP 208×48: проверены все пиксели при x = 0, 8, 16, 8.
- Три открытия WBMP 144×80: проверены все пиксели при y = 0, 16, 0.
- Ещё одно открытие WBMP: переход USB → физический UC1609 → USB,
  восстановление просмотра и работа прокрутки после смены дисплея.
- После каждого приложения — выход через ESC и возврат терминального
  приглашения без `Open failed!`.
- В конце: `CRASH none`, `MPU enabled=1 layout=ok`, `MEM invariant=ok`,
  валидный аппаратный CRC resident.

Итого на A и B: **22 запуска CHECK, 14 запусков WBMP, 70 точных сравнений
полных кадров 192×64**. Дополнительно проверена целостность передачи 110
кадров по CRC16. На каждой прошивке минимальный остаток стека по watermark
проверяется в сохранённом отчёте `mpu status`; нарушений защиты не было.

Пиксели получены через USB Screen с настоящего микроконтроллера. Это
проверка загрузчика, распаковки, исполнения ARM, API, чтения C5 и обработки
клавиш. Переключение на UC1609 выполняет физический путь вывода, но оптическая
проверка пикселей LCD не проводилась. Физический F401 в этом опыте не участвовал.

Попытка дополнительного аппаратного теста повреждённых APP остановилась
до загрузки файлов: простой терминальный клиент не отделил фоновые OFFER
USB Screen от приглашения. Проверки повреждённых контейнеров пройдены
на хосте; аппаратный отказ повреждённого APP этим опытом не подтверждён.
DFU-утилита также один раз зависла при выходе после записи B; сама B
запустилась, её build и аппаратный CRC затем подтверждены отдельно.

## Восстановление и остальные проверки

Все 524288 байт исходной внутренней Flash прочитаны до опыта, восстановлены
через DFU и повторно прочитаны. Совпадение побайтовое, SHA-256:
`d2904e1622b8f3963446be479f003ab289d40dbd190f0f800f572993597ad43c`.
Прибор снова сообщает build `4AC27AA8`, валидный CRC и исходную
конфигурацию MPU 3/8. Проверены все 13 пользовательских файлов C5, состав
каталогов и исходные пустые регистры, стек и программа. Пять временных
файлов и каталог `/PAPPTEST` удалены.

Общий набор `MK61_TEST_SANITIZERS=1 bash tests/run_all_tests.sh` прошёл.
Предельная сборка F401 WS0010 + USB с выключенным PortableApps после
изменения MPU сохранила BIN 261632 байта, свободную Flash 512 байт и
прошла ограничение на размер кадра стека 2048 байт.

Исключение MPU компилируется только для F411. После окончательного
ограничения этого кода по MCU повторная сборка F401 с PortableApps дала
237024 байта BIN и 49108 байт статической RAM: +272 байта Flash к
контрольной сборке без ABI 3, без роста RAM. Предобработанный код MPU
для обеих F411-сборок полностью совпал с испытанным на приборе.

Локальные исходные журналы этого опыта находятся в `.build/portable-hil/`:
`test-a/`, `test-b/`, `pre-b-c5.json`, `post-b-c5.json`,
`restored-c5.json`, `restoration.json`; снимки Flash не входят в Git.
Общий журнал тестов: `/tmp/mk61-portable-hardware-full-tests.log`.

Компактность сжатия оценивается отдельно: в WBMP BCJ уменьшил APP лишь
с 896 до 893 байт. Главный подтверждённый результат — самостоятельная
сборка и запуск одного сжатого APP после изменения прошивки.
