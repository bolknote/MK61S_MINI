# Самодостаточные модули и RAM-кеш VM

Реализация 2026-10-08. Это кеш байткода BASIC/FOCAL, а не кеш нативных APP.
Compiler APP, cold `LANGIN.APP` и hot `LANGVM.APP` по-прежнему загружаются
общим APP runtime. RAM-кеш не пишет файлы и не меняет C6/C8.
Отдельный экспериментальный файловый кеш описан ниже; по умолчанию он выключен.

## Контракт

Сохранённые BASIC и FOCAL кешируются при явных RUN по ID, имени и выбранному
индексу, включая интерактивный BASIC RUN. Имя разрешается тем же способом,
что и в прежнем frontend; новой семантики путей нет. Запуск из меню/редактора
не кешируется под ID сохранённого файла: там может находиться черновик.

На промахе исходник читается один раз, sizing и EMIT используют один снимок.
EMIT пишет непосредственно в BUILDING-запись. После выгрузки compiler APP
cold verifier проверяет весь образ; только затем resident публикует READY
и передаёт управление hot VM. Ошибка RUN или отмена не удаляет корректную
READY-запись.

На попадании не загружается compiler APP и не повторяется полная проверка.
Код, строки PRINT и подсказки INPUT находятся в RAM. За текстовыми ресурсами
нет обращений к ФС. Явные файловые операции программы и проверка метаданных
этим контрактом не запрещены. INPUT может загрузить cold APP и вычислить
временное выражение; это не повторная компиляция сохранённой программы.

Переменные, массив, RNG и продолжение не входят в образ. Каждый RUN получает
новое состояние исполнения с прежними правилами сохранения значений.
Исходная длина сохраняется для SIZE и квоты массива.

## Wire format v4

Все слова little-endian; opcode остаётся 8-битным. Образ не содержит native
указателей. Магия `LBV1` сохранена, поле версии равно 4. Образы v1/v2/v3 отвергаются.

| Смещение | Размер | Значение |
| --- | --- | --- |
| 0 | 4 | `LBV1` |
| 4 | 1 | Версия 4 |
| 5 | 1 | BASIC=1 / FOCAL=2 |
| 6 | 1 | Требуемое число значений на стеке |
| 7 | 1 | Флаги: expression=1, RF=2, resources=4, owned resources=8 |
| 8 | 2 | Полный размер |
| 10 | 2 | Начало кода |
| 12 | 2 | Число строк |
| 14 | 2 | Длина исходника M8 |
| 16 | 4 | CRC исходника |
| 20 | 4 | CRC образа после заголовка |
| 24 | 6 | Для owned: нули; для SOURCE: ID и media revision |
| 30 | 2 | Конец кода при наличии ресурсов, иначе нули |

После заголовка находятся таблица строк и код. Таблица BASIC содержит
`[u16 line, u16 pc]`, FOCAL — `[u32 address, u16 pc]`; диагностические
SOURCE_POS остаются в коде. Бюджет заголовка, карт и кода — 6144 байта.
Полный owned-образ ограничен 9728 байтами; лимиты исходников и runtime stack
не увеличены. Legacy SOURCE-образ целиком ограничен прежними 6144 байтами.

`GOTO_DIRECT` и `GOSUB_DIRECT` (92/93) содержат `u16 pc`, разрешённый
компилятором для простого положительного номера строки BASIC. `0xFFFF`
обозначает отсутствующую строку: ошибка возникает только при исполнении.
Вычисляемый номер, включая побочные эффекты INPUT(), использует прежние
GOTO/GOSUB и прежнюю проверку номера. Cold verifier проверяет границы pc.

Три составные инструкции v4:

| Opcode | Операнды | Действие |
| --- | --- | --- |
| 94 LOAD_ARRAY_FIXED | u16 index | Загрузка массива без промежуточной константы/стека |
| 95 COMPARE_FALSE | u8 mask, u16 pc | Сравнить два значения, перейти при ложном результате |
| 96 UPDATE_LOCAL | u8 variable, u8 rhs | Обновить локальную переменную ADD/SUB без стека |

COMPARE_FALSE использует биты less/equal/greater/unordered; маски EQ/NE/LT/LE/GT/GE
равны 2/13/1/3/4/6. Cold verifier отвергает старшие биты и неверные границы pc.
UPDATE_LOCAL: rhs bits 0..5 — число/индекс, bit 6 — индекс переменной вместо
числа, bit 7 — SUB вместо ADD. Индексы проверяются и cold, и hot; конечность
операндов/результата проверяется до записи. Компилятор первого этапа эмитирует
только RHS-переменную или CONST_0..15 и только точную последовательность
`A=A+B`/`A=A-B`/`A=A+1`: не пересекает SourcePos, ссылки, массивы, I/O или
дополнительную арифметику. Группировка, overflow promotion и signed zero прежние.

LOAD_ARRAY_FIXED эмитируется только для голого unsigned integer 16..65535;
ошибка превышения квоты остаётся runtime-ошибкой на исходном `@`. Для 0..15
прежняя двухбайтная пара компактнее и сохраняется. Динамические индексы,
INPUT(), дроби и отрицательные числа не меняются. LOAD_ARRAY_FIXED разрешён
также в INPUT expressions; остальные составные инструкции там запрещены.
CHECK (29) в v4 зарезервирован и отвергается: все producing operations уже
проверяют конечность, компиляторы v3 его тоже не эмитировали.

Каталог и пул объединены в компактную последовательность
`[u16 length][length готовых M8-байтов]`. PRINT_RESOURCE и INPUT_RESOURCE
содержат `u16` смещение записи относительно конца кода. Это не ссылка на
исходник. Одинаковые итоговые строки, в том числе составные подсказки,
интернируются внутри модуля. Пустая строка допустима; INPUT по-прежнему
ограничен 95 байтами. PRINT использует существующий ограниченный вывод.

Cold verifier проверяет весь каталог, границы ссылок и длины. Bitmap
инструкций остаётся 768 байт: увеличенный пул не раздувает bitmap на C-стеке.
Проверенный сертификат 16 байт не содержит указателей на cold APP.

Внутренний compiler/runtime request ABI равен 7, ARM Request — 40 байт,
CompilerContext — прежние 240 байт, ExecutionState — прежние 1520 байт.
Compiler/VM/input и language-flow context magics обновлены. Размер union
сам по себе не гарантирует совместимость смещений CompilerStage.
После изменения нужно устанавливать
согласованный resident и каталог System; старый language APP несовместим.
Внешний APP container ABI по-прежнему 6.

## Общий быстрый путь VM

Оптимизации не зависят от игры или файла и работают в BASIC и FOCAL:

- Проверка конечности числа выполняется в каждой производящей операции.
  Повторные CHECK не эмитируются; NaN/Inf по-прежнему дают MATH до STORE
  или следующей операции. В v4 неиспользуемый CHECK удалён из executor.
- SOURCE_POS — диагностический префикс. Он сохраняет столбцы ошибок, но
  пропускается перед основным dispatch и не входит в счётчик steps/limit.
  Service вызывается до первой и каждой 32-й полезной инструкции,
  включая пустые FOR: отдельный повторный опрос на NEXT не нужен.
  Сканирование префиксов ограничено
  размером образа, их границы проверяются.
- Таблица длин заменяет второй switch и повторное чтение opcode. Проверки
  переменных записей, стека, массивов и целей переходов остаются.
- Бинарная арифметика использует два уже существующих элемента стека с
  одной проверкой глубины; точность, overflow promotion и signed zero прежние.
- Фиксированные побитовые копии чисел используют builtin memcpy даже при
  APP `-fno-builtin`. Это перенос представления, не изменение арифметики.
- Восемь direct-mapped записей кешируют точную расшифровку CONST_DEC8/16:
  80 байт временного C-стека, без static RAM, malloc и роста байт-кода.
  Кеш действует только внутри одного run; INPUT/resume строит его заново.

Этот быстрый путь не превращает CORE transcendental math в APP FLOAT и не
заменяет LIBM. Выбранный math backend и числовой ABI остаются прежними.

### Составные операции: первый этап

Выбор сделан по host-профилю неизменённого Turochamp (2/8, без книги), а не
по отдельным именам файлов в runtime. До слияния: 7272816 полезных dispatch;
составные операции дали около 12% сокращения. Это количество инструкций VM,
не device cycles или обещание такого же процента времени всей игры.

115 модулей компилируются; ни один owned-образ не вырос. Сумма 54662 → 53797
байт, High Noon 6992 → 6975, Turochamp 40232 → 39488 (39568 aligned).
Пакет шахмат всё ещё не помещается в payload 23888; увеличение кеша, межмодульный
CALL/RUN, замена cache policy и JIT в эту итерацию не входят.

Статические массивы/ABI states не добавлены. Compiler emission хранит только
два предыдущих коротких opcode в своём временном объекте; sizing и EMIT
пользуются одной схемой, без дополнительной копии всего кода/IR. Поля cold
compiler обнуляются общим initializer; fixed numeric bit copies не вызывают
APP memcpy, большой int32 token упаковывается через один Value, не два.

Цена loaded APP против предыдущего этапа: BASIC 18216 → 18488, FOCAL
18588 → 18604, LANGVM 12876 → 13060, LANGIN 10960 → 11216 байт. APP FLOAT
LANGVM 15356 → 15540. Это разные фазы, их нельзя суммировать как одновременно
занятую RAM. Общий APP arena по-прежнему 20 КиБ; бюджет cache 24576 не меняется.
Hot CORE/LIBM size gate вырос на один 32-байтный allocation quantum:
13056 → 13088, потому что реальный образ на 4 байта превышает прежний ceiling.
FOCAL storage/memory и APP FLOAT ceilings сохранены. Это небольшая цена
native executor/компилятора за меньшие модули и меньшее число dispatch, не
нулевая цена динамической RAM.

Регрессионные проверки покрывают IEEE order/unordered, NaN/Inf, signed zero,
int32 overflow, ошибки/диагностику, точный sizing, invalid operands/targets,
INPUT whitelist, resume и bounded cancellation. Host ASan/UBSan, полный
Turochamp (правила/поиск/UI/книга) и 24624 High Noon cases прошли.
Профилировщик LANGUAGE_VM_TRACE — только host build: в shipping APP нет
счётчиков, callback-полей или дополнительных firmware imports.

Matched baseline исходников `488eaa248` (VM в нём — `b81f5e617`). Согласованные
полные сборки F401 CORE/cache0 и F411 LIBM/cache24576: sealed Flash 256664 →
256664 и 358580 → 358588; ELF static RAM/dynamic pool неизменны — 37904/22760
и 83708/32256 соответственно. Внешние APP-файлы суммарно +764 байта, не
внутренняя Flash. APP FLOAT и CORE/LIBM имеют отдельные loaded-image ceilings.

Matched ARM instruction gate (500 итераций, включает initial validation,
без I/O/загрузки APP): integer/array, mixed, wide, decimals и compound BASIC,
mixed FOCAL — ×1,038..1,053; IF/GOTO BASIC ×1,690; GOSUB BASIC ×1,557;

### Профиль и политики кеша

Актуализация 11.10.2026: diagnostic detail дополнен внешними scope
`m61.runner` (обработка сценария M61) и `vm.invoke` (резидентная обвязка
запуска VM). Они вложены в обычное дерево self/total, а не дополнительные
времена, которые можно прибавлять к включающим totals. При выключенном
runtime detail обе точки отсутствуют; прежние 17 точек сохранены.

На Classic `AEB505B6E0067623` проверен исходник
`1c41bec6c67db68e6a8c3daca1830d2a6f620c1d` с неизменными четырьмя языковыми
APP и Turochamp: LIBM, 96 МГц, Os/no-LTO, density/cache24576, USB Screen.
Исходная установленная `7B7D50A3` не содержит USB Screen; временный baseline
`F482A729` включает измерительный экран. Это не замер исходной firmware без
USB. Baseline: **72,503 / 70,622 / 70,849 с**, warm median **70,735 с**.

Диагностическая `3AAAF1D2`: **73,912 / 72,034 / 72,237 с**. Warm self:
VM entry 21,557 с, BASIC compiler 8,699 с, idle/main 7,040 с, Flash read

прежних 3,400 с: выборочная очистка стеков теперь не приоритетная гипотеза.
Повторный ход по-прежнему имеет 58 misses/232 ZX0 calls; board21/search21.

Расширенная диагностическая `E95A973E`: cold **74,032**, repeat **72,175 с**.

**21,569 с**. Сумма всех scoped self **71,643 с**, остаток до финального

#### Ускорение M61 по этому профилю (11.10.2026)

Дополнительные diagnostic scope: `m61.read.line`, `m61.command`,
`m61.operand`, `m61.open`, `terminal.lookup` (49 точек только при detail=1).
До оптимизации повторный ход `93F1E88B`/`6EF670F8` показал примерно
5,91 с self чтения строк, 5,24 с обработки команд, 4,06 с операндов,
2,64 с lookup команд и 1,24 с обвязки открытия файла. Это разбиение M61
с дополнительной стоимостью измерения: его сумму нельзя напрямую сравнивать
с 17,94 с более грубого профиля или прибавлять к `m61.command total`.

Изменено только общее исполнение сценариев, без правок Turochamp или VM ABI:

- M61 потребляет проверенное окно локальным курсором. Ревизия проверяется
  перед строкой и каждой подгрузкой; внутри участка нет вызовов обработки
  событий/записи ФС. Сохраняются CR/LF/CRLF/NUL, EOF, лимит строки и бюджет
  восемь строк за service. Границы окон 64/1024 и изменение исходника
  покрыты ASan/UBSan-регрессиями.
- Короткие целые литералы и нормализованные однозначные целые регистры
  не проходят повторный десятичный разбор. Другие формы идут прежним путём.
  LIBM/CORE проверены побитно против старого преобразования, включая -0,
  все порядки -99..99, ошибочные символы и alias входа/выхода. Грамматика
  сохраняет <=18 цифр и |порядок|<=99: допустимые числа заведомо конечны
  в binary64, поэтому повторные soft-double проверки NaN/Inf не нужны.
- Частый `if` определяется до линейного прохода, но его имя/ID получены
  constexpr из единственного каталога. Порядок help и проверки разрешений
  script/trap не менялись; второго диспетчера или хеш-таблицы нет.
- Повторяющийся разбор префикса и цели `run :label` для trap/bind вынесен
  в общие функции, также используемые open?/loadfont. Это компенсирует
  место ускоряющих веток во Flash.

Кооперативные вложенные Scope расширяют CYCCNT до 64 бит, поэтому один

оборотов DWT сам по себе не восстанавливает. Reset/generation не позволяет
старому Scope или decode context перезаписать новую сессию профиля.

После аппаратной и общей языковой квалификации resident использует
`CachePolicy::REUSE_DENSITY` по умолчанию:
`MK61_LANGUAGE_VM_CACHE_DENSITY=1`. Значение `0` явно возвращает исходный LRU;
bundle builder проверяет и передаёт этот переключатель. При cache=0 политика
не инстанцируется, малопамятный путь F401 не меняется.
Повторные hit повышают ограниченный счётчик reuse (максимум 255);
жертва имеет минимальное reuse/allocated-byte, при равенстве выбирается LRU.
Сравнение целочисленное, без float/division. После каждого вытеснения reuse
стареет вдвое, чтобы прошлый hot set не закреплялся навсегда. Pinned объекты
по-прежнему не вытесняются. Счётчик занимает прежнее reserved u16 в Entry:
каталог 688, payload 23888 и общий бюджет 24576 байт не меняются.

## Бюджет и lifetime

### DSP-поиск CR/LF в компиляторах

2026-10-09: `language_source_scan.hpp` заменяет только поиск конца физической
строки в общем `Compiler::index_lines()` BASIC/FOCAL. Пропуск пробелов,
ключевые слова, обратный поиск диагностической колонки и арифметика не менялись.
На little-endian ARM с SIMD32 работает один общий helper: безопасный
`memcpy` четырёх байтов только при оставшейся длине ≥4, маска первого CR/LF
и прежний побайтовый хвост. Остальные платформы используют скалярный путь.
На Cortex-M4 ELF содержит две пары USUB8/SEL; их GE-lane semantics описаны в
[документации Arm CMSIS](https://arm-software.github.io/CMSIS_6/main/Core/group__intrinsic__SIMD__gr.html).
Helper занимает 86 байт кода, не требует выравнивания, padding, malloc или
постоянного буфера. Форматы bytecode v4/request ABI7 и compiler context прежние.

Первоначальный отдельный APP-эксперимент дал около ×2,14 на самой функции,
но не на компиляции/VM целиком. Production-перенос измерен на настоящих
System APP F411 `AEB505B6E0067623`, 96 МГц, с отдельным diagnostic resident
`C84E8759`. Семь cold запусков каждого исходника на блок,
baseline → candidate → baseline; cache miss/source read ровно по одному.
Метрика — `app.entry.basic/focal self`: реальный frontend+sizing+EMIT,
без вложенных source/Flash/APP reads и decode, без времени исполнения VM
или ожидания конечной клавиши. Это не wall-time полного RUN и не скорость шахмат.

| Compiler self, мс | Baseline до | Новый | Baseline после | Меньше времени |
| --- | ---: | ---: | ---: | ---: |
| Turochamp search BASIC |106,112|105,611|106,112|0,472%|
| High Noon intro BASIC |57,403|56,644|57,404|1,323%|
| Statistics FOCAL |41,208|40,651|41,227|1,376%|

Процент считается относительно медианы обеих baseline-серий (14 значений).
В успешной серии 63 образца, 314 CRC-valid кадров, ноль отброшенных пакетов
и повторов чтения. Первые попытки нового стенда выявили единичные пропуски
CDC/неполный экранный пакет и ошибочную проверку UTF-8 HELP вместо stored M8;
они исключены, артефакты сохранены. HIL теперь отвергает повреждённый экран,
восстанавливает сборку только с нового CRC-valid FRAME_BEGIN и явно считает
пропуски. DWT ASCII-метрики проверяются отдельно; CRC/offset-invalid fsget
никогда не принимается за fingerprint. Это изменение стенда, не ослабление
CRC/verifier продукта.

Сопоставимые обычные overlay-сборки F411 и F401 CORE/cache0 сохранили MCU
побайтно: `C1D1CF6A`/358876 и `109C89EE`/256704 соответственно, static RAM
83708/37904 прежняя. Изменились только два внешних System APP:

| APP | Stored до → после | Цена stored | Loaded RAM до → после |
| --- | ---: | ---: | ---: |
| BASIC |13251 → 13333|+82|18488 → 18568|
| FOCAL |13799 → 13856|+57|18604 → 18668|

Итого +139 байт внешней Flash; BSS обоих APP прежняя (52/104). Загруженный
машинный код занимает дополнительно 80/64 байта RAM, не одновременно:
обычный APP arena остаётся 20 КиБ. Это не нулевая цена loaded RAM, хотя
постоянная RAM и объём программ/байткода не выросли. Измеренный storage ceiling
компилятора FOCAL явно обновлён 13800 → 13880, memory ceiling 18688 не менялся;
обычные не-VM интерпретаторы имеют прежние ограничения.

Host ASan/UBSan покрывает все соседние пары байтов/полосы, M8 high bytes,
alignment=0..3 и точные хвосты до 3584 байт; скалярный и эмулированный DSP пути.
Компилятор проверен с LF/CR/CRLF/LFCR, пустыми строками, EOF без разделителя,
owned/inline ресурсами и прежними диагностическими курсорами. Полный VM suite

guards сохранились. Измеренный вложенный compiler/service C-stack 6908 байт,

`MK61_LANGUAGE_VM_IMAGE_CACHE_BYTES` теперь означает **общий** бюджет,
а не только байты образов. При 24576 байтах:

- 16 записей каталога;
- 688 байт метаданных и счётчиков;
- 23888 байт payload;
- `sizeof(ImageCache<24576>) == 24576`, без второго массива и malloc.

Для стандартных 16 слотов ненулевой бюджет должен включать хотя бы 688 байт
метаданных и 32 байта образа; меньшая конфигурация отвергается static_assert.

Ключ — язык, file ID и общая media revision. Формат/компилятор/числовой ABI
зафиксированы самой сборкой и её проверками совместимости; кеш только RAM
и не переживает замену firmware. Параметры RUN не создают дубли образа.
Версии отдельных файлов пока не используются: изменение постороннего файла
консервативно инвалидирует READY-записи.

Handle содержит номер слота и поколение. BUILDING невидим для lookup;
reservation закреплена до публикации/отката. READY закрепляется на весь RUN,
INPUT, resume и finish. Обе политики вытесняют только незакреплённые записи, уплотнение
разрешено только без pins. Все операции выполняются в foreground, не IRQ.

Изменение ФС делает закреплённый образ STALE: текущий RUN завершает свой
снимок, но новый lookup его не получает. После последнего release запись
освобождается. Изменение версии до публикации отменяет BUILDING. При возврате
в BASIC-редактор после изменения исходника показывается предупреждение,
старые координаты не применяются.

## Малопамятный путь

На F401 кеш штатно выключен. При выключенном/переполненном кеше сначала
пробуется временный owned-образ в существующих разрешённых аренах. Если
резерв невозможен либо owned sizing переполнился, тот же исходник используется
для SOURCE-образа с прежним чтением строковых ресурсов. Повторно открывать
редактор/выбор программы или перечитывать source для retry не нужно.

Fallback не является cache hit и не обещает автономность ресурсов. Это
best effort: при отсутствии памяти даже для прежнего пути остаётся BUSY.
`cache_diagnostics()` предоставляет бюджет/занятые байты и счётчики
lookup/hit/miss/reservation/failure/publication/eviction/invalidation;
при отключённом кеше возвращает false. Счётчики загрузок compiler и чтений
source/resources пока проверяются тестовыми трассами, а не отдельными
постоянными firmware-счётчиками.

## Пакеты — следующий слой, не часть текущего runtime

High Noon уже целиком помещается как четыре независимые записи с прежней
семантикой RUN. Межмодульная дедупликация дала бы **максимум 118 байт** до цены
каталога/заголовка пакета. У Turochamp 40232 байт owned-образов, экономия
общего пула максимум 121 байт, один только код/карты — 38750 байт. Целиком
в 24-КиБ кеше он не помещается даже без строк.

Пакетный runtime, manifest/preload API и общий межмодульный пул пока не
реализованы. Не считать сумму образов исполняемым пакетом и не объединять
семантику отдельных RUN. Для Turochamp сейчас работает ограниченный density-
кеш отдельных модулей с явным LRU override. Нет автоматической загрузки
шрифтов, картинок и всей папки.

## Файловый кеш байткода — проверенный прототип, 2026-10-12

`MK61_VM_FILE_CACHE=1` в resident включает необязательный обычный APP
`/System/VMCache/VMSTORE.APP`, собираемый через
`tools/build_portable_app.py --system vm-file-cache`. Флаг по умолчанию **0**:
автоматической установки или включения в штатные bundles пока нет.
Отсутствие helper сохраняет прежний RAM-кеш/компиляцию.

Выбрано автоматическое заполнение после успешной компиляции/верификации
сохранённого файла. Корректность байткода не зависит от успешного завершения
самой программы. На RAM hit файловых операций кеша нет. На RAM miss helper
проверяет исходник и кеш, резервирует BUILDING-запись, повторно проверяет и
копирует образ, выполняет полный VM verifier и публикует READY. Sizing/EMIT
и загрузка compiler/cold APP на этом пути не нужны. Повреждение, устаревание,
OOM, отсутствие helper и отказ записи дают прежний путь компиляции.

Ключ включает CRC проверенных первых **60** байт C6-заголовка compiler APP,
CRC/длину M8 исходника, source ID, язык, VERSION=7 и версию кеша. Полные 64
байта вместе с собственной CRC заголовка хешировать нельзя: получается
фиксированный CRC residue; регрессионный тест замены компилятора это ловит.
При изменении media revision во время чтения/резервирования образ не
исполняется как актуальный. Удаление/перезапись источника под тем же ID
проверяется по содержимому. Сертификат из файла не принимается на веру.
После A/B добавлена защита записи: publication epoch занимает временно
неиспользуемое поле INPUT union (sizeof/offsets прежние). Смена compiler
или любого файла до STORE/во время чтения его заголовка отменяет запись;
старый образ не маркируется новой версией компилятора. RUN сохраняет
обычную семантику выполнения уже проверенного снимка.

Запись `VMC-xxxx.APP` — обычный валидный C6 контейнер, без изменения C9,
нового типа файлов или дополнительных потоков NTFS. Внутри 24-байтный ключ,
готовый owned LBV1 с ресурсами и четырёхбайтный Thumb entry, отвергающий
INITIALIZE. Открытие кеша как APP не исполняет байткод как ARM. Payload —
канонический literal-only ZX0: reader проверяет recipe/все CRC и копирует
литералы без распаковки. Это не новый компрессор; надбавка порядка 100 байт
на файл. Сам байткод не раздувается и остаётся byte-exact.

Кеш ограничен 32 файлами / 64 КиБ. Новые записи при заполнении квоты
пропускаются, автоматического вытеснения нет. Заменяется только валидная
собственная запись данного source ID/языка; чужой файл с совпавшим именем
и нераспознанный повреждённый файл не перезаписываются. Данные переживают
перезагрузку. Запись NOR нужна при первом заполнении/изменении источника
или компилятора, на последующих попаданиях — только чтение.

Ограничения прототипа: только сохранённые RUN с работающим RAM-кешем и
retained owned image; codec/file/source используют прежние 4176 байт
compiler workspace, не values tail. Большие кеш-файлы не помещаются в этот
буфер и безопасно идут через компилятор. Весь исходник ещё читается один
раз на файловом попадании, чтобы проверить CRC: устранена **компиляция**,
но не все source decodes. Каждый собственный write меняет общий media
revision и временно сбрасывает RAM working set при первом заполнении.

## Единый handoff RAM/файлового кеша — 2026-10-12

Убран вложенный `execute_overlay/run_flow` на файловом попадании. Холодный,
RAM- и файловый запуск используют один `CompilerContext` и один cooperative
цикл; pin, обработка результата и editor position также общие. Файловый APP
после передачи prefix продолжает фазу `START_LOADED`, связывает сертификат и
состояние, затем использует прежний HOST `PUBLISH_IMAGE`. Заголовок/байткод и
размер контекста (240 байт) не меняются. ID helper занимает прежние два
reserved байта, поэтому его не нужно повторно искать после компиляции.
Файловое попадание публикуется в RAM, но не записывается обратно в NOR.

`prepare_compiled_flow()` до верификации устанавливает только язык: полный
reset делает START ровно один раз. После STORE отдельный reset остаётся
необходим: writer действительно использовал тот же prefix для упаковки.
Warm RAM использует workspace lease внутри Transfer, не второй lease.
Хостовые тесты проверяют один контекст и один reset на файловом попадании,
включая INPUT/ESC. Новая гонка между HOST commit и START выявила зависший
VM lease при возврате к компилятору; rollback теперь освобождает и reservation,
и workspace. Регрессия проверяется для LIBM/CORE, USB=0/1 и с санитайзерами.

Первый аппаратный вариант E0C2762A намеренно сохранён как отрицательный замер:
передача памяти выгружала VMSTORE, а START загружал его снова. В A/B/A прежний
CC91917F дал 50,543/50,547 с на повторах, этот вариант — 52,401 с (+3,68%).
Получилось 232 распаковки вместо 174. Исправление: `retain_image(..., false)`
разрешено только для уже проверенного файлового образа; Buffer helper
освобождён до HOST, поэтому helper не нужно выгружать ради его workspace.
Компилятор по-прежнему обязательно выгружается перед переиспользованием
prefix. Новый тест запрещает такую лишнюю eviction на файловом попадании.

## Штатный файловый кеш и неизменённые бюджеты — 2026-10-12

Кеш включён по умолчанию при overlay VM и ненулевом RAM image cache.
F411 получает его автоматически; F401 и explicit cache=0 — нет.
`MK61_VM_FILE_CACHE=0` остаётся явным выключением для A/B. Резидент с
активным кешем, но без helper, использует обычную компиляцию.

После публикации следующий target выбирает APP, не отдельная native
политика. Target и publication revision занимают прежний временный INPUT
union; контексты 184/240 байт, persistent values 4016 и VM state 1584
не увеличились. Откат HOST освобождает pin/workspace и возвращает управление
helper, который очищает временную transfer/certificate и выбирает frontend.
Tagged zeros всех 501 значений инициализируются одним byte-copy циклом
вместо memset и трёх отдельных циклов. Представление всех чисел прежнее;
проверка физических tagged zeros входит в RAM cache regression.

Приватный `FLOW_CONTEXT_MAGIC` стал 0x36564C46: предыдущие APP не могут
молча прочитать новый publication contract. Bytecode VERSION=7, C6 ABI=6,
request ABI=8 и filesystem C9 не меняются. Нужно обновлять BASIC/FOCAL,
LANGVM/LANGIN согласованным комплектом. Старый persistent bytecode cache
проверяется по новому CRC compiler APP, поэтому корректно пересоздаётся.

Штатный F411 Classic sealed **393196**, свободно **131092** при прежнем
required **131072**: 224 байта сняты с прошлого варианта 393420, остаток

## Числовые операнды IF без format/parse — 2026-10-15

После ускорения M61 IF следующий кандидат убирает промежуточную строку при
чтении числового регистра. Resident reader разбирает восемь цифр мантиссы,
знаки и порядок непосредственно из ringM. Он используется в IF и общем
mk61_ref::read; переносимый ABI и байткод не меняются.

Быстрый путь допускает только десятичные цифры и канонические знаки 0/9.
Необычные тетрады, недоступный RF и отрицательный сохранённый порядок 00
сохраняют прежнее поведение. При отказе reader не изменяет результат;
вызывающая сторона использует собственный старый formatter/parser. Это
существенно: IF проверяет всю строку, а общий reference reader исторически
допускает частичный atof. Правила знаков у R и стека также различаются для
неканонических слов.

Мантисса собирается точно в u32. Для целого частного в диапазоне порядков
0..7 применяется точное целочисленное деление; остальные значения используют
тот же порядок операций, что mk_math::strtod: перевод полной мантиссы в
binary64 и одно умножение/деление на pow10_int с показателем |E-7|.
Предварительное деление мантиссы на 1e7 не используется из-за дополнительного
округления. Отрицательный ноль сохранён. На целях без binary64 reader
возвращается к старому пути.
