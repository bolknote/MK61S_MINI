# Самостоятельные APP: SDK ABI 5

Практическое руководство: [как писать программы на C/C++, собирать и запускать
APP](../../doc/src/MK61s-mini-APP-Programming.md). Этот README описывает
технический контракт SDK. Исторические размеры до и после переноса System APP
сопоставлены в [отчёте ABI 4](RELOCATION-RESULTS.md).
Предыдущее сравнение ABI 2/3 сохранено в [SIZE-COMPARISON.md](SIZE-COMPARISON.md).

SDK собирает обычный `int main(void)` на C/C++ или `extern "C" fn main()` на
Rust в `.APP` без resident ELF, BIN и `--just-symbols`. Один файл запускается на
разных F401/F411-прошивках с ABI 5 и совместимой таблицей API.
Первый перенесённый
пример — просмотрщик WBMP: исходный декодер `code/wbmp.cpp` используется
без изменений, экран, файлы и клавиатура доступны через C API.

## Сборка приложения

Нужны Python 3.10+, ARM GCC и нативный C++17-компилятор для упаковщика.
Проверен xPack ARM GCC 14.2.1 из STM32 Core. Положите его `bin` в `PATH` или
добавьте `--arm-toolchain-bin /путь/к/bin` в команды ниже. Все команды
выполняются из корня репозитория.

```sh
python3 tools/build_portable_app.py --name HELLO \
  --source examples/portable-apps/HELLO/main.c \
  --output-dir .build/portable-apps/hello

python3 tools/build_portable_app.py --name WBMP \
  --source examples/portable-apps/WBMP/main.c \
  --source examples/portable-apps/WBMP/viewer.cpp \
  --source code/wbmp.cpp --handled-magic I1 \
  --output-dir .build/portable-apps/wbmp
```

Для Rust дополнительно нужен `rustup`. Установите целевую библиотеку и
соберите готовый `#![no_std]` пример:

```sh
rustup target add thumbv7em-none-eabihf
python3 tools/build_portable_app.py --name HELLO_RS \
  --source examples/portable-apps/HELLO-RUST/main.rs \
  --output-dir .build/portable-apps/hello-rust
```

Модуль `sdk/portable/rust/mk61_app.rs` описывает полный 108-байтный базовый
API, текущий вид и CRC образа, а также публичный `common_services()`. Поэтому
Rust APP имеет тот же доступ к расширенным сервисам, что C/C++ System APP и
обычная C/C++ APP; отдельного закрытого System API нет.

На Windows используйте `python` и запишите команду в одну строку либо
примените продолжение строки вашей оболочки. Для сборки упаковщика нужен
PowerShell 5.1+; принимается также готовый `--packer PATH`.

`--source` принимает `.c`, `.cpp`, `.rs` и `.S`; `--include` добавляет каталог
заголовков, `--library` — статическую ARM-библиотеку. Библиотеки должны быть
собраны для Cortex-M4 Thumb, hard-float `fpv4-sp-d16`. SDK добавляет startup,
`memcpy`, `memmove`, `memset`, `memcmp` и нужные функции `libgcc`.
Опция `--shared-runtime` использует общие ARM EABI/строковые подпрограммы
прошивки и проверяет их наличие до `main()`. Линкер
отклоняет образ свыше 20 КиБ и глобальные C++ конструкторы/деструкторы;
сборщик также отклоняет неупакованные секции ELF и неразрешённые символы.

Результат: `NAME.APP`, ELF и map для диагностики, исходный образ `NAME.bin`
и `NAME.json` с размером контейнера, образом, BSS, релокациями и сжатием.
Именно `.APP` устанавливается на устройство.

## Подготовка прошивки и память

Текущая раскладка, сравнение восьми F401-сборок и аппаратная проверка:
[APP без фиксированного резерва](DYNAMIC-RAM-RESULTS.md).
Последующее сокращение расхода стека и проверка порога 12 КиБ на F411:
[результаты испытаний стека](STACK-RESULTS.md).

Во всех GCC, Arduino CLI и Arduino IDE профилях F401/F411 единый переносимый
ABI 5 обязателен. System APP и обычные APPLICATION проходят один runtime и
получают один публичный API; отдельного разрешения для пользовательских файлов
нет. При переходе на ABI 5 обновите прошивку и
скопируйте весь комплект `System`, включая `SETUP.APP`, `HELP0.TXT` и
`HELP1.TXT`. Прошивка без фиксированного резерва отклоняет ABI 2/3/4 до записи
payload в RAM: прежний адрес теперь занят обычными данными resident.
Пересоберите такие APP в ABI 5.

Отдельного 20-КиБ массива APP в `.bss` больше нет. Линкер сохраняет штатный
порядок `.data`, `.bss`, `.noinit` и экспортирует границы свободной RAM:
`__mk61_dynamic_begin = align8(_end)` и `__mk61_dynamic_end` непосредственно
перед защитой стека. Верхняя граница равна `0x2000E700` на F401 и
`0x2001BF00` на F411; бюджеты стека остаются 6 и 16 КиБ соответственно.
В штатной release-сборке эти границы проверяются linker ASSERT. При прямой
сборке Generic STM32F4 из Arduino IDE, где стандартный linker script не
экспортирует `__mk61_dynamic_*`, resident вычисляет те же границы из `_end` и
профиля F401/F411. Это совместимый fallback без статического резерва APP;
если `.data`/`.bss` уже дошли до защиты стека, динамический пул остаётся
пустым вместо переполнения размера.

APP получает `align32(memory_bytes)` сверху этого участка; 20 КиБ остаются
пределом размера одной программы. Выравнивание 32 байта нужно для MPU.
Системная куча и временные staging-буферы используют нижнюю часть. Загрузка
APP сохраняет адрес и содержимое занятого нижнего буфера; при нехватке места
возвращается ошибка. Выгрузка возвращает весь блок APP в свободный промежуток.
Статические WORKSPACE/SCRATCH/BULK сохраняют собственные адреса.

Новый `_sbrk` учитывает обе границы. Пока нижний буфер арендован, системная
куча не может менять размер; `_sbrk` не вызывает вытеснение из libc.
Неисполняющийся кэш APP может уступить память временным буферам, но активный
вызов APP закреплён до возврата. Одновременно загружен один APP.

На F411 загрузчик после проверки CRC разрешает исполнение только выделенного
блока APP и отзывает это разрешение перед освобождением. До пяти областей MPU
с подрегионами точно покрывают блок; вместе с SRAM XN, нулевым адресом и
защитой стека используются восемь областей. Стек и свободная RAM остаются XN.
F401 и F411 используют одинаковую linker-разметку и выносят включённые System
компоненты в C5. Внутреннего альтернативного варианта и отдельной опции
«Пользовательские APP» нет.

Установите пример как `/Apps/WBMP.APP` через обычный менеджер C5. Сигнатура
`I1` в заголовке регистрирует обработчик WBMP. Штатные WBMP/Markdown имеют
приоритет перед пользовательскими обработчиками, поэтому в тестовой
прошивке выше они отключены; старые `/System/WBMP.APP` и
`/System/MARKDOWN.APP` также не должны перехватывать открытие. Прямой запуск
WBMP.APP выводит подсказку, просмотр начинается при открытии файла WBMP.
Графический пример рассчитан на UC1609 192×64 или USB-экран того же размера.

## Контракт ABI 5 и сжатие

Заголовок имеет 64 байта, `format=1`, поля little-endian.
`kind=APPLICATION` обозначает пользовательскую программу; существующие
номера System APP сохранены, `SETUP=7` добавлен в конец.

| Поле, смещение | ABI 5 |
| --- | --- |
| ABI, 12 | `5` |
| compression, 15 | `1` — ZX0 |
| flags, 16 | `5` — standalone + relocations; `7` — также Thumb BCJ |
| load_address, 20 | `0x20000000`, виртуальная база линковки |
| stored_size, 24 | Сжатый образ + таблица релокаций |
| image_size / memory_size, 28 / 32 | Образ / образ вместе с BSS |
| entry_offset, 36 | Смещение Thumb-точки входа от начала образа |
| code_stored_size, 40 | Длина сжатого образа без таблицы |
| relocation_count, 44 | Число исправляемых 32-битных слов |
| stored_crc32, 48 | CRC32 сжатого образа и таблицы вместе |
| image_crc32, 52 | CRC32 исходного образа до BCJ и релокаций |
| header_crc32, 60 | CRC32 первых 60 байт заголовка |

Таблица следует сразу после сжатого потока. Исправления отсортированы
по смещению; каждая запись кодирует промежуток от конца предыдущего
4-байтового слова (для первой записи — от начала образа). Используется
канонический unsigned LEB128 длиной 1–3 байта. Невыровненные слова разрешены,
пересекающиеся — нет. Каждый исходный указатель должен попадать в образ/BSS
или ровно за его конец. К нему прибавляется разница фактической и виртуальной
базы. Thumb-бит функции сохраняется. Таблица читается блоками по 64 байта;
её отдельная полная копия в SRAM не нужна.

SDK линкует с `--emit-relocs` и `-mword-relocations`, извлекает `R_ARM_ABS32`
внутри APP и проверяет, что PC-relative связи остаются внутри него.
`SHN_ABS` сохраняет явно заданные постоянные адреса. Неподдерживаемая
релокация останавливает сборку: похожее на адрес целое число никогда
не исправляется по догадке. Статические ARM-библиотеки также должны
поддерживать этот набор релокаций.

ABI 5 — единственный исполняемый формат. Исторические ABI 3 использовал
фиксированную базу и нули в полях 40/44, а ABI 2 хранил там размер/CRC точной
прошивки. Они распознаются инструментами диагностики, но loader их не принимает.

Упаковщик делает два варианта: `ZX0(image)` и `ZX0(BCJ(image))`. Выбирает
строго меньший; при равенстве остаётся обычный ZX0. BCJ — стандартное
преобразование ARM-Thumb из
[XZ Embedded](https://github.com/tukaani-project/xz-embedded/blob/master/linux/lib/xz/xz_dec_bcj.c)
для полного образа, с начальной позицией фильтра 0. Оно меняет подходящие
пары полуслов вызова BL, не меняет длину и обратимо даже на данных, случайно
совпавших с шаблоном команды. Лицензия адаптированного фильтра — 0BSD.

Загрузка: динамическая аренда блока → ZX0 → обратный BCJ на месте → проверка CRC
исходного образа → исправление адресов и проверка CRC всего payload →
обнуление BSS → `INITIALIZE` → `main()` либо `mk61_app_open_file(id)`.
Любая ошибка запрещает вызов точки входа. BSS хранится только размером.
Повторный запуск того же inode и заголовка использует вытесняемый кэш и
сохраняет `.data`/BSS — одинаково для APPLICATION и System APP. После вытеснения
образ заново распаковывается и инициализируется.

## Общий API и дополнительные сервисы

`mk61_app.h` открывает один API для пользовательских и штатных APP.
Базовая таблица ABI v1 сохраняет прежние 104 байта и добавляет в конец
`query_service` (всего 108 байт на ARM). Размер проверяется до чтения нового
поля; startup новых APP требует актуальную 108-байтовую таблицу.
Запуск новых APP на прежних прошивках не поддерживается.

`mk61_app_get_services(mk61_api, MK61_SERVICE_CAP_...)` возвращает таблицу
дополнительных сервисов или `NULL`. Через неё доступны C5, память,
редактор и диалоги, настройки, математика и общие подпрограммы компилятора.
Набор определяется сборкой, а не видом APP. См. [контракт и примеры](APP-SERVICES.md).
Пример [SERVICES](../../examples/portable-apps/SERVICES/main.c) собирается
обычным `--source`, в том числе с `--shared-runtime`.

## Ограничения SDK

Это freestanding C/C++ для микроконтроллера. Здесь ещё нет полного libc,
`printf`, `malloc`, `fopen`, аргументов командной строки, динамической
линковки. Ввод-вывод программы нужно адаптировать к
`mk61_app_api` из `code/loadable_app_api.h`, получаемому как `mk61_api`.
SDK проверяет magic, версию и размер API; приложение проверяет необходимые
capabilities перед использованием функций.

Приложение разделяет стек с прошивкой и периодически вызывает `service()`.
Этот запуск рассчитан на обычные приложения и файловые обработчики.
Все шесть System-модулей используют тот же ABI 5. Состояние языков находится в
отдельной workspace-арене и переживает вытеснение кода. См. [общий API](APP-SERVICES.md).

## Проверки и измерения

Предыдущие пять System APP ABI 3 прошли [аппаратные проверки 2026-09-06](HIL-2026-09-06.md):
вычисления, обмен состояниями языков, редакторы и сохранение, графика,
повреждённые APP и сверка установленной прошивки после перезапуска.
Исторический ABI 4 отдельно прошёл [аппаратный прогон](HIL-ABI4-2026-09-06.md):
три адреса загрузки C-пробы, две прошивки, все шесть System APP, повреждённые
релокации и справка. После проверки исходный комплект ABI 3 восстановлен.
Размеры и границы остальных проверок — в [отчёте](RELOCATION-RESULTS.md).

```sh
MK61_TEST_SANITIZERS=1 bash tests/run_portable_app_tests.sh
MK61_TEST_SANITIZERS=1 bash tests/run_all_tests.sh
```

Первая команда проверяет 4096 вариантов BCJ с контрольными границами памяти,
выбор обоих способов сжатия и равенство размеров, повреждения контейнера,
отказ старых форматов и пиксели WBMP по независимой формуле, включая
прокрутку, смену экрана и ошибки API. Публичный SDK компилируется как C11
для ARM также с Clang.

Дополнительный тест исполняет машинный код из готового APP в Unicorn
(проверен 2.1.4). Он берёт настоящие таблицы API из двух разных собранных
resident ELF, а периферию заменяет макетами:

```sh
python3 tests/run_portable_app_arm_tests.py \
  --arm-toolchain-bin /путь/к/bin \
  --resident-elf /путь/к/прошивке-a/resident.elf \
  --resident-elf /путь/к/прошивке-b/resident.elf
```

Обе прошивки должны иметь ABI 5 и графический API; например,
различаться опцией FOCAL. Проверяются неизменность одного APP при смене адресов API, повторный
запуск по трём адресам, начальные значения `.data`/BSS, указатели функций
и упакованных структур, пиксели, выход, сохранение регистров и границы памяти. Это проверка кода ARM с макетами, а не испытание прибора.

Аппаратный прогон для Classic V3 с UC1609 использует настоящий загрузчик,
код ARM и периферию; пиксели сравнивает через USB-экран:

```sh
python3 tools/build_portable_app.py --name CHECK \
  --source tests/portable_app_hil_check.c \
  --output-dir .build/portable-apps/check
python3 tests/hil_portable_apps.py \
  --write-fixtures .build/portable-apps/fixtures

# После установки CHECK.APP, WBMP.APP, Wide.wbmp и Tall.wbmp в /PAPPTEST:
python3 tests/hil_portable_apps.py --port /dev/cu.usbmodem... \
  --public-id PUBLIC_ID --output-dir .build/portable-hil/result
```

Тест не перепрошивает прибор и не пишет в C5. Он временно забирает дисплей,
передаёт клавиши и при завершении возвращает физический экран. Прошивка
должна поддерживать ABI создаваемого APP (сейчас ABI 5) и USB Screen. Для проверки независимости от
прошивки запустите тест на двух сборках с разными адресами API, сохранив
те же файлы APP. На 2026-09-05 этот прогон прошёл на физическом F411:
22 проверки начального состояния C-программы и 14 запусков WBMP в сумме
на двух сборках. Условия и границы проверки — в
[аппаратном отчёте](HIL-2026-09-05.md).

Исторические замеры исходного прототипа ABI 3 до переноса System APP (ARM GCC 14.2.1, `-Os -flto`):

| Пример | Образ | Образ + BSS | APP с заголовком | Сжатие |
| --- | ---: | ---: | ---: | --- |
| HELLO (C) | 144 | 152 | 204 | ZX0; BCJ дал тот же размер |
| WBMP (C/C++) | 877 | 4020 | 893 | BCJ + ZX0; обычный ZX0 даёт 896 |

Прежний ABI 2 WBMP на той версии исходников: APP 1185 байт, overlay 1320 байт
плюс отдельные общие буферы файла/экрана. Новый WBMP держит оба буфера внутри
своих 4020 байт, поэтому размеры overlay этих вариантов напрямую не равны
общему расходу памяти.

До переноса System APP, в паре `classic-v3`, FOCAL/BASIC/WBMP включены, Markdown выключен,
`MK61_MATH_BACKEND=1`, USB-экран выключен,
поддержка ABI 3 вместе с BCJ увеличила resident BIN с 236752 до 237024 байт
(+272), статическая RAM осталась 49108 байт. При выключенной опции
предельная проверка F401 WS0010 + USB сохранила прежние 261632 байта BIN
и 512 байт свободной Flash. Значения зависят от профиля и версии компилятора.

Текущий перенос всех System APP и его отдельная стоимость описаны в
[System API](SYSTEM-API.md).
