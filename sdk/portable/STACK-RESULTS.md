# Расход стека C5 и APP: 6 сентября 2026

Исходная точка — `09d62fa`, APP ABI 4 без фиксированного резерва.
Машиночитаемые результаты: [STACK-RESULTS.json](STACK-RESULTS.json).
На одном физическом F411 воспроизведён прежний минимум **11136 байт**
свободного стека. После изменений минимум составляет **12328 байт**:
выигрыш **1192 байта**. Порог 12288 байт пройден с запасом 40 байт
в описанном ниже прогоне. Это измерение конкретных сценариев, а не
гарантия максимальной глубины стека произвольного C-приложения.

Бюджеты стека и MPU-барьеры сохранены: F401 6 КиБ, F411 16 КиБ,
отдельный барьер 256 байт. Нового постоянного буфера не появилось.

## Что изменено

- Чтение уже завершённой терминальной загрузки использует её существующий
  буфер WORKSPACE. Узкий индекс staging расположен за первыми 512 байтами
  и сохраняется. Проверяется действующая аренда нужного владельца.
- Локальный 1-КиБ fallback-план сжатия и последующая транзакция каталога
  используют общие байты union. Активный член переключается после полного
  сохранения payload. Параметры сжатия и формат C5 сохранены.
- Обработка больших файлов вынесена из общего кадра записи через `noinline`.
- Кодирование записи WAL выполняется отдельным вызовом после checkpoint,
  поэтому его секторный буфер не лежит на стеке во время переноса каталога.
- После записи таблицы checkpoint использует тот же буфер для заголовка.
  Размеры передач Flash и буфер проверки записанных байтов сохранены.

Анализ GCC отдельным проходом `-fstack-usage` не меняет прошивочный ELF:

| Кадр | До, байт | После, байт |
| --- | ---: | ---: |
| `write_file_from_source` | 2032 | 1488 |
| `read_staged_file_upload` | 544 | 56 |
| `append_transaction` | 568 | 40 |
| `checkpoint` | 680 | 616 |

Новый `append_transaction_record` использует 560 байт только в своей фазе.
Размеры кадров нельзя складывать без учёта цепочки вызовов; итоговый
выигрыш подтверждён аппаратным watermark.

## Испытания

На Classic V3 / UC1609, public ID `AEB505B6E0067623`, сравнивались прошивки
`EDFFB94F` и `B07CC4CB`. Начальный прогон записи и замены файлов воспроизвёл
11136 байт. Окончательная прошивка прошла:

- 26 терминальных записей с полным чтением обратно: несжатые и сжимаемые
  данные, размеры 1/511/512/513/1023/1536 байт, одинаковая повторная запись,
  большой CHIP-8 на 3584 байта, удаление временных файлов.
- 6 запусков C-пробы, 7 запусков WBMP с точным сравнением пикселей,
  2 переключения USB/LCD.
- 12 запусков языков, 6 восстановлений переменных, 3 запуска CHIP-8,
  3 просмотра Markdown с проверкой прокрутки.
- SETUP hardware/date/calibration/font с отменой правок; ABI 3 и пять
  повреждённых APP отклонены без изменения видимого C5; справка проверена
  в полном, отсутствующем, устаревшем и восстановленном состоянии.

После всего прогона: `MEM invariant=ok`, `CRASH none`, MPU `layout=ok`,
минимальный остаток стека 12328 байт. Регрессионные проверки C5 и VFAT
с ASan/UBSan прошли, включая 587 вариантов изменений FAT.
После окончательной правки повторно прошёл полный `tests/run_all_tests.sh`
с `MK61_TEST_SANITIZERS=1`.

Новый `tests/hil_c5_stack.py` сохраняет этот сценарий. Во все три аппаратных
теста добавлен явный порог; 12288 предназначен для 16-КиБ стека F411:

```sh
python3 tests/hil_c5_stack.py \
  --port "$PORT" --public-id "$PUBLIC_ID" --directory /STACKTEST \
  --minimum-stack-remaining 12288 --output-dir .build/hil-c5-stack
```

Каталог должен существовать; имена `STACKIO.txt` и `STACKIO.ch8` должны
быть свободны. Тест удаляет только созданные им файлы. Аналогичный параметр
поддерживают `tests/hil_portable_apps.py` и `tests/hil_portable_system_apps.py`.
APP и их таблицы релокаций не менялись; прошивка испытывалась с ранее
собранными контейнерами.

Испытанные 302852 байта BIN сверены чтением обратно; SHA-256:
`2331f60582fd9223df9ebbe811136d27c5c75bdff1bf37883ada99ff08c0f161`.
Восстановлена исходная прошивка `2504D75A`, все 524288 байт Flash побайтно
совпали с резервной копией. Восстановлены 18 исходных файлов, регистры,
стек и программа; удалены 16 временных файлов. Второй прибор не изменён.
