# МК-61: локальный помощник на PicoCalc

Нативный харнесс для PicoCalc с Pico H (RP2040) и 8 МиБ PSRAM. Модель работает
на самом Pico. Обучение и сервер для исполнения не нужны. Лаунчер `MK61AI.APP`
вызывает резидентный сервис прошивки; веса и KV-кэш находятся в PSRAM.

## Установка

1. Установить собранную вместе с комплектом прошивку `mk61s-picocalc-pico-h.uf2`.
2. Скопировать содержимое каталога `sd` в корень SD-карты.
3. Запустить `/Apps/MK61AI/MK61AI.APP` из проводника.

Файл модели размером 2 МБ копируется через кардридер или штатный режим
USB-диска с безопасным извлечением. Одна нативная транзакция `fsput` ограничена
журналом восстановления из 512 секторов, включая служебные изменения FAT;
для целой модели этот путь не подходит. После извлечения USB-диска SD снова
переходит во владение прошивки.

Модель читается из `/AI/MODEL.MKA`. Каталоги `/AI/SESSIONS` и `/AI/Exports`
создаются при первом запуске. Существующие задачи при обновлении комплекта
сохраняются. Если на SD уже есть `/AI/PROMPT.TXT`, он заменяет стандартный
префикс: для воспроизведения проверенного поведения следует убрать этот файл
или использовать тот же префикс, что при проверке модели.

Для моделей 3M Q4 из опытов `spec-translation-clean-v1` и `spec-natural-v1` рядом с весами
нужен `/AI/MODEL.PRO` с содержимым `MK61SPEC1` и переводом строки. Модель выбирает
операции, аргументы и регистр назначения в компактной SPEC; харнесс переводит
это дерево в команды МК-61 и исполняет их через обычное ядро. Числа извлекаются
из текста в том же порядке, что при обучении. Вычисление ответа выполняет
калькулятор. Профиль использует INT8 арифметику и сокращённую выходную
голову; дополнительные токены служебного заголовка учитываются как входные.
Эта модель выдаёт одну программу на запрос; свободное объяснение и исследовательский
цикл самопроверки SPEC в этом профиле не включены. Старые XML-модели работают
без `MODEL.PRO`. При замене модели сохраняйте соответствие весов и этого файла.

Для выбранной LoRA-ветки `spec-natural-v1` проверка известных запросов, точных
токенов, программы и результата ядра воспроизводится так:

```sh
MK61_AI_SPEC_ARITHMETIC=1 bash tests/run_mk61_ai_spec_tests.sh /path/to/MODEL.MKA \
  tests/data/mk61_ai_spec_natural.tsv
```

Без второго аргумента проверяется прежняя полная модель `spec-translation-clean-v1`.

## Управление

| Клавиша | Действие |
| --- | --- |
| F1 | Развернуть или свернуть программу в ленте |
| F2 | Перенести программу в калькулятор |
| F3 | Править программу; после принятия запустить через ядро МК-61 |
| F4 | Сохранить программу в BIN |
| F5 | Запуск или пауза; повторное нажатие продолжает вычисление |
| F6 | Вернуться к последнему сообщению и вводу уточнения |
| F7 | Развернуть или свернуть реальные счётчики токенов и времени |
| F8 | Русская / английская раскладка |
| Tab | Действия с задачей, примерами и программой |
| Enter | Отправить сообщение и начать вычисление; принять форму или выбранный пункт |
| Esc | Пауза, закрыть форму, перейти к списку задач, выйти |
| Стрелки, Home, End, Backspace, Delete | Выбор, прокрутка и редактирование |

На старте доступны новая задача, импорт BIN, текущая программа калькулятора и
сохранённые задачи. Новая задача сразу открывает строку ввода. Режимы «исправить»
и «объяснить» доступны через Tab → Режим задачи; при объяснении модель не может
заменить код.

Основной экран — тёмная лента диалога 320×320: сообщение, счётчики, программа и
ответ настоящего ядра МК-61. Стрелки ↑/↓ листают ленту; старые сообщения
подгружаются из журнала SD, в RAM остаются четыре сообщения. Ввод закреплён внизу.
F7 раскрывает обработанные входные токены, повторно использованный контекст,
выходные токены, время чтения запроса, генерации и исполнения, а также измеренную
скорость генерации. Первый выходной токен, полученный при чтении запроса,
тоже учитывается. Время запроса измеряется часами PicoCalc и включает загрузку
модели; время паузы исключается. Оценка «4,66 с/токен» для счётчиков не используется.
Сводку в `/AI/METRICS.JSON` сохраняет Tab → Сохранить замеры в JSON.

Без контрольного примера используется текущая угловая единица калькулятора.
Число в блоке «Ответ МК-61» берётся только из завершённого исполнения текущей
версии программы. Наличие ответа само по себе не означает, что модель правильно
решила задачу: для этого служат контрольные примеры. Счётчики и полученный ответ
сохраняются вместе с сообщением и восстанавливаются при открытии задачи.

Пример задания: `X = R0 + R1.`. Контрольный пример вводится так:

```text
R0=7 R1=5 => X=12; ATOL=2e-6 RTOL=2e-6 ANGLE=RAD STEPS=256 FRAMES=2048
```

Доступны R0…RE и стек X/Y/Z/T, как для входов, так и для ожидаемых значений.
Можно проверить несколько результатов и сохранность входных регистров:

```text
R0=7 R1=5 => X=12 R0=7 R1=5 PRESERVE=R0,R1
```

После первой остановки можно выполнить до четырёх следующих шагов, разделённых
`|`. Шаг задаёт один новый вход (необязательно), клавишу и один ожидаемый выход.
По умолчанию нажимается R/S; `KEY=29` — та же клавиша. Например, для счётчика:

```text
R0=5 => X=6 R0=6 | => R0=7 | R0=10 => X=11 | KEY=29 => R0=12
```

`KEY` использует физические координаты МК-61 в HEX: `41` — цифра 2, `51` —
цифра 3, `29` — R/S. Общие лимиты команд и кадров действуют на весь сценарий.
`PUBLIC=0` перед первым `|` скрывает входы и ожидаемые значения от модели;
эти проверки всё равно учитываются в результате. Трасса для модели использует
только публичный пример.

`X=?` оставляет результат наблюдением и не засчитывает его как пройденный тест.
Углы: DEG, RAD, GRAD. До восьми примеров в задаче. Код редактируется как HEX
через пробел; распознаются также мнемоники из штатного терминала.

Модель создаёт версии программы и вызывает настоящий эмулятор МК-61. Только
эмулятор выставляет результаты проверок. Изменение условия или примера
снимает прежний результат; изменение программы создаёт новую версию. История
версий позволяет вернуться к сохранённому коду. Полные запросы, ответы,
результаты инструментов и последние 16 шагов каждой трассы пишутся на SD.
Открытие журнала и настроек сохраняет приостановленное продолжение. Номера
задач выдаёт счётчик на SD, устойчивый к перезагрузке. Старые сессии `M61SES1`
читаются, новые записываются в `M61SES2`.

Ответ модели ограничивает грамматика: `<write>HEX</write><run/>` записывает
программу до 105 команд; `<patch>AA:HEX;BB:HEX</patch><run/>` меняет выбранные
участки текущей страницы, адреса заданы в HEX. Перекрывающиеся правки запрещены.
Допускаются `<trace/>`, `<done/>`, короткий `<plan>…</plan>` и `<ask>…</ask>`.
План можно отключить в настройках; это формат рабочего текста, его полезность
зависит от обучения модели. Грамматика обеспечивает формат, а эмулятор проверяет
смысл программы.

Харнесс запоминает неудачные кандидаты, останавливает повтор одного решения
и при исчерпании попыток возвращает лучшую проверенную версию. Общий префикс
следующего запроса повторно использует KV-кэш.

Перенос в калькулятор выполняется отдельным действием с подтверждением. Нужны
остановленный калькулятор, классический режим 105 команд и банк 0. Исходная
программа сохраняется в резервный BIN, регистры остаются прежними. Проверки
исполняются в отдельном состоянии эмулятора и восстанавливают состояние
пользователя, в том числе при паузе или исчерпании лимита.

## Сборка

```sh
python3 tools/apps/mk61ai/build_mk61ai.py \
  --weights /path/to/model.mkq4 \
  --hf /path/to/matching/hf \
  --build-firmware
```

Нужны GNU Arm GCC, CMake, Ninja и Pico SDK 2.2.0. Поддерживаются параметры
`--toolchain /path/to/bin`, `--sdk /path/to/pico-sdk`, `--output-dir` и
`--build-dir`. SDK можно предварительно получить штатным сборщиком прошивки
с флагом `--fetch-sdk`. Для включения уже собранной прошивки используется
`--firmware /path/to/mk61s-picocalc-pico-h.uf2`.

Экспорт читает замороженные MKQ4v1/MKQBv1 и соответствующий `tokenizer.json`,
сохраняет коды квантования и переставляет их в битовые плоскости для LUT.
Поддерживается проверенная архитектура Flourish/Qwen3 с общими весами
эмбеддингов и выходного слоя. Другие архитектуры явно отклоняются.

## Память, проверка и ограничения

- Проверочный пакет Flourish-3M Q4 занимает 2 093 896 байт, FP32 KV
  на 512 токенов — 2 621 440 байт. Рабочая область v3 — 17 104 байта SRAM;
  у аппаратно проверенного образа B0/v2 она составляла 15 344 байта.
- Полная история хранится на SD. В контекст входят условие, текущий код,
  до двух публичных примеров и последняя обратная связь. Если обязательный
  контекст не помещается, интерфейс просит сократить условие.
- Ответу доступен остаток контекста после фактического запроса; фиксированного
  предела 160 токенов нет. Для полной страницы доступна адресная правка.
  Лимиты попыток и исполнения эмулятора
  ограничивают длительность работы; это не обещание решения любой задачи.
- Обычный диалог использует INT8, два ядра, 28 строк в плитке и DMA-предвыборку.
  На время генерации включаются 270 МГц; завершение, пауза и выход возвращают
  исходную частоту. Подготовленные активации переиспользуются в Q/K/V и gate/up,
  а соседние query-головы совместно читают KV. Для быстрого INT8 нужен пакет
  Q4 с парными полубайтами; битовые плоскости остаются совместимыми.
  FP32 и LUT-режимы доступны в параметрах для сравнительных замеров.
- Спектрум и харнесс запускаются по очереди. Прошивка STM32, UART и звуковой
  протокол этим изменением не затрагиваются.

В указанном проверочном пакете матрицы весов уже квантованы в **Q4** во всех
четырёх режимах. Названия FP32/INT8 в настройках описывают арифметику:
FP32 использует вещественные активации; INT8 дополнительно квантует входы
линейных слоёв до 8 бит и использует целое накопление скалярных произведений.
Нормировки, нелинейности и KV-кэш сохраняют FP32. Режим INT8 не меняет файл
модели и требует отдельной проверки качества.

`AIBENCH.APP` запускает сервис диагностики версии 2 и записывает
`/AI/DIAG/BENCH.JSON`. Он выполняет 8 шагов prefill и 4 decode в трёх режимах:
FP32, LUT FP32 на той же последовательности токенов и LUT FP32 с грамматикой.
Также проверяет максимальную сессию при резидентных модели, KV и интерфейсе.
На приборе доступны пик занятой кучи, верхняя оценка расхода стека, максимальная
пауза между обслуживанием и время выхода из forward после Esc. Скорость
измеряется при коротком контексте 8–12 токенов. Она не описывает полный диалог
на 512 токенов. В host-сборке `device=false`, аппаратные поля не выдаются
за измерения прибора.

На Pico H/RP2040 125 МГц, образ `B0CF78C9` / CRC `96B1D0E2`, полный
прогон 36 шагов прошёл. Веса Q4, контекст при decode — 8–12 токенов:

| Арифметика | Секунд на выходной токен |
| --- | ---: |
| FP32 | 39,45 |
| LUT FP32 | 16,90 |
| LUT FP32 с грамматикой | 16,96 |

LUT ускорил decode примерно в 2,33 раза. Загрузка модели заняла 15,86 с.
В полном прогоне измерены пик занятой кучи 66 432 из 96 232 байт и верхняя
оценка расхода стека 20 380 из 32 768 байт. Максимальная сессия прошла
транзакционную запись/чтение одновременно с резидентными моделью, KV и UI.
В отдельном тесте паузы ключ дошёл до обработчика за 56,8 мс; после обработки
ключа `forward` вернулся за 303 мкс. Полный SHA-256 модели проверен на приборе.
Эти результаты подтверждают нативное исполнение, а скорость остаётся слишком
низкой для привычного диалога. Скорость INT8 на приборе этим тестом не измерена.

Фиксированный пакет модели с SHA-256
`45ebc482d2247d36d386c9563becb89d3ca08868db66aad001afa977703b0166`
решил 6 из 20 заранее объявленных русских условий со скрытыми проверками,
как с разрешённым планом, так и без него. Все 42 ответа в каждом режиме
прошли разбор протокола. Циклы, исправление кода и игровой сценарий не решены.
Это результат конкретного checkpoint и промпта, а не предел архитектуры.
Парное сравнение на тех же уже опубликованных 20 условиях с LUT INT8 дало
5/20 и 43/43 допустимых ответа; потеряна задача на деление. Это сравнение
арифметики на известном наборе, а не новая независимая оценка обобщения.
Для такого запуска у `evaluate.py` есть `--arithmetic lut-int8`.

## Вычислительный режим v3

Матмулы получают восемь строк весов за раз. Первое ядро читает их из PSRAM,
затем оба ядра считают непересекающиеся половины по общей неизменяемой LUT.
Второе ядро получает только указатели в SRAM: модель, токенизатор и KV остаются
во владении первого ядра. После каждого задания первое ядро дожидается его
завершения, в том числе при численной ошибке. Ввод и отмена обслуживаются между
небольшими блоками; незавершённый токен не продвигает позицию KV.

Во время `forward` приостановлена отрисовка, картинка остаётся на LCD.
Клавиатура, USB и watchdog продолжают обслуживаться. По завершении или отмене
отрисовка возобновляется. F5 и Esc сохраняют обычное поведение паузы и продолжения.
Если второе ядро ещё заканчивает передачу LCD, блок может быть рассчитан первым
ядром. Потери задания или обращения второго ядра к PSRAM при этом нет.

Ядро Q4 развёрнуто отдельно для LUT FP32, LUT INT8 и прямого INT8. Оно собрано
в вариантах Flash и SRAM; SRAM-вариант занимает 2848 байт. Основной режим v3 —
полный словарь 8192, Q4-веса, LUT FP32, два ядра и замороженный экран.
Предварительный отбор строк выходной матрицы по грамматике остаётся отдельным
экспериментом. При запросе полного массива логитов этот отбор не применяется.

Проверки на компьютере включают два настоящих потока, побитовое сравнение
полных логитов, все 512 позиций контекста и всех 2 621 440 байт KV, отмену и
повтор, ошибки чтения, численную ошибку на втором потоке и отказ очереди.
Нативная проверка интерфейса контролирует неизменность изображения между
заморозкой и разморозкой. Эти проверки не являются замером скорости RP2040.

На тех же известных 20 русских задачах оптимизированный LUT и предварительный
отбор токенов сохранили 6/20 с теми же исходами каждой задачи. Прямой INT8 дал
5/20. Пробное удаление половины словаря даёт пакет 1 671 628 байт и 6/20,
но теряет два прежних решения и добавляет два других. Тексты условий требуют
на 8,8% больше токенов. Словарь 2048 даёт 1 463 560 байт и 3/20.
Эти варианты не заменяют основной пакет автоматически.

Экспорт вариантов:

```sh
python3 tools/apps/mk61ai/export_model.py --weights model.mkq4 \
  --tokenizer tokenizer.json --output nibble/MODEL.MKA --layout linear
python3 tools/apps/mk61ai/export_model.py --weights model.mkq4 \
  --tokenizer tokenizer.json --output vocab4096/MODEL.MKA --layout lut --vocab-limit 4096
```

`AIBENCH.APP` с файлом `PERF.CFG` в диагностическом каталоге запускает отдельное
парное сравнение и пишет `PERF.JSON`. Файл строго задаёт ядро вычислений,
арифметику, число ядер, заморозку, грамматику, частоту и размер прогона.
Диагностическая `MODEL.MKA` в том же каталоге позволяет проверить вариант
модели без изменения `/AI/MODEL.MKA`. Хеш проверяется отдельным приложением.
`prepare_perf.py` собирает пакет конечных фаз на компьютере и не открывает
устройство. Контроллер `hil_mk61_ai_perf.py` требует отдельного допуска на
точные хеши каждой фазы; первая прошивка остаётся неисполняемым черновиком,
пока не указаны build/CRC актуального освобождённого устройства.

Разгон доступен только в отдельной сборке `build_picocalc.py --ai-overclock`.
Она загружается на 125 МГц и допускает диагностические 200/250/300 МГц при
штатном напряжении. Flash работает с делителем 6, PSRAM — с целым делителем,
не превышая исходную частоту PIO. SYS, частота периферии и скорости интерфейсов
возвращаются перед записью отчёта и выходом, включая отмену и обычные ошибки.
USB намеренно отключается на время перехода PLL, чтобы не нарушать RP2040-E16.
Аппаратное зависание не может быть исправлено таким программным возвратом:
контроллер останавливается в HOLD, дальнейшие частоты не запускаются.

Числа скорости выше относятся только к B0/v2. Скорость и устойчивость v3 на
приборе отмечаются отдельно после аппаратного прогона. Пакет фаз включает
повтор исходного B0, раздельные варианты Flash/SRAM/двух ядер, INT8, словарей,
Esc/F5 и ограниченные нагрузки CPU/принадлежащего тесту участка PSRAM при разгоне.

Наборы разработки и проверки разделены:

```sh
python3 tools/apps/mk61ai/evaluate.py --build \
  --package /path/to/MODEL.MKA \
  --cases tests/data/mk61_ai_holdout_v2.jsonl \
  --output /path/to/new-evaluation-directory
```

Для парного сравнения используется `--no-plan` и другой выходной каталог.
До запуска фиксируются SHA модели, условий, исполняемого файла и исходников.
Все объявленные условия учитываются, ошибки и нехватка контекста считаются
неудачами. Тесты с подставным inference backend отдельно проверяют возможности
контроллера; они не входят в оценку качества модели.

Проверки модели: `tests/mk61_ai_model_test.py`. Проверки ядра харнесса:
`tests/run_mk61_ai_tests.sh /path/to/MODEL.MKA`. Проверки нативного интерфейса:
`bash tests/run_picocalc_tests.sh --ai-native`.
