# Optional STM32 backend

The native harness can reserve two rows of each eight-row linear tile for the
STM32 and split the remaining six rows across the two RP2040 cores. Select
`Ядра: 2 Pico + STM32` in the harness settings. The default remains two Pico
cores. Enabling STM32 selects LUT FP32; changing arithmetic disables STM32.

The SD bundle includes `/AI/M3LINE.S3M`. Build it separately with
`python3 tools/apps/mk61ai/build_m3_linear.py`. This is a native SRAM module
for our installed Southbridge runtime, not a replacement keyboard firmware.
Code and BSS occupy 4580 of the runtime's 6144 bytes; the vector capacity is
512 FP32 columns. Every native STEP handles one group of32 columns. The
resident's cooperative per-call limit is2000µs. No overclock is requested.

Weights remain Q4 bit planes with FP16 group scales; activations, LUT and
accumulation remain FP32. The module builds one group's LUT at a time and
keeps the same addition order as `linear_batch_sram`. A complete activation
vector is transferred once per matrix. Each tile then transfers the selected
weight/scale rows; the RP cores compute while STM32 runs. Every remote job is
joined before using output or reusing a tile. Failed jobs are drained, the
backend is disabled, and those rows are recomputed locally.

UART1 GP8/GP9 runs at the existing runtime's2.25Mbaud. The AI client uses no
Pico DMA channels. Opening requires inactive M3 audio, unused UART/pins and an
EMPTY resident. It never unloads a foreign module. Successful ownership ends
with UNLOAD, EMPTY verification, UART/pin restoration and release of temporary
UART sleep clocks. Lost replies replay the identical sequence; a START is not
executed twice. Keyboard/I²C and Pico's cancellation service remain active.

`tests/run_mk61_ai_m3_tests.sh` checks native-module arithmetic, full-model
logits/KV/row-hash equality, concurrent prefetch, refusal/fallback/cancellation,
and the real Pico backend through SDK framing and the resident loader with
an in-memory UART. `tests/mk61_ai_m3_arm_self_test.py` executes the exact
relocated Thumb-2 soft-float code against an independent FP32 oracle. These
HOST/ARM checks do not measure physical speed.

For hardware A/B, AIPERF2 `cores=3` is deliberately limited to LUT FP32,
controlled comparisons at125MHz with no stress/overclock. Both passes use the
same two-core kernel and prefetch settings; only target passes enable STM32.
All activation/weight/result UART traffic is inside forward timing. Module
setup is outside it and reported separately. The report includes remote work,
fallbacks, UART bytes, native slice time, memory and unload errors. All row
hashes/tokens and the complete KV allocation checksum must match. A diagnostic
PASS requires actual remote jobs and zero fallback or transport/cleanup errors.

`tools/apps/mk61ai/prepare_m3_perf.py` prepares a short four-forward phase
against an exact installed firmware manifest. It opens no port and performs
no flash. Execution requires the existing exclusive hardware handoff and
fresh hash-bound coordinator grant. The module is uploaded under the phase's
private SD directory and removed with the diagnostic artifacts afterwards.
Physical speed results belong to the measurement receipt, not this document.
